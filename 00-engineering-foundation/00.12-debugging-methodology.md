# 00.12 — Debugging Methodology

## 1. Why This Exists

Debugging is the process of turning an observed failure into a verified explanation and a validated fix.

Strong engineers do not debug by randomly changing code until the symptom disappears.

They follow a disciplined loop:

    Observe
      ↓
    Reproduce
      ↓
    Localize
      ↓
    Form hypothesis
      ↓
    Gather evidence
      ↓
    Isolate cause
      ↓
    Fix
      ↓
    Verify
      ↓
    Prevent regression

Debugging is therefore a reasoning skill, not merely a tooling skill.

---

## 2. Problem It Solves

Without a systematic debugging process, engineers tend to:

- guess
- make unrelated changes
- hide symptoms
- introduce secondary bugs
- waste time
- lose production evidence
- repeat incidents

The objective is not:

> Make the error disappear.

The objective is:

> Explain why the failure occurred, fix the underlying cause, and produce evidence that the system is now correct.

---

## 3. Core Concept

Every debugging investigation should separate:

### Symptom

What is visibly wrong?

### Trigger

What conditions caused the behavior?

### Mechanism

What sequence of events produced the failure?

### Root cause

Which incorrect assumption, state, dependency, or implementation decision allowed the failure?

### Fix

What changes the mechanism?

### Prevention

What stops the same class of failure from returning?

Example:

    Symptom:
    API returns 500.

    Trigger:
    Database connection pool exhausted.

    Mechanism:
    Connections were not released after a timeout.

    Root cause:
    Incorrect lifecycle handling.

    Fix:
    Correct cleanup and timeout behavior.

    Prevention:
    Regression test + pool metrics + alerting.

---

## 4. Debugging Mental Model

Model the system as:

    Input
      ↓
    State
      ↓
    Transformation
      ↓
    Dependency
      ↓
    Output

A failure means one or more assumptions about this path are wrong.

Ask:

1. What input existed?
2. What state existed?
3. What code executed?
4. What dependencies were contacted?
5. What output was produced?
6. Where did actual behavior diverge from expected behavior?

---

## 5. Reproduction

A reproducible failure is easier to investigate.

Start with:

- exact input
- environment
- version
- configuration
- timestamp
- request ID
- dependency state
- expected result
- actual result

Then reduce the reproduction.

Example:

    production failure
          ↓
    staging reproduction
          ↓
    minimal request
          ↓
    minimal input
          ↓
    minimal failing function

The smallest reliable reproduction is extremely valuable.

---

## 6. Deterministic vs Intermittent Bugs

### Deterministic

Same conditions reliably produce the same failure.

These are usually easier to isolate.

### Intermittent

Failure occurs only under some conditions.

Common causes:

- race conditions
- timing
- concurrency
- resource exhaustion
- network behavior
- randomness
- load
- distributed state

For intermittent failures, increase observability rather than blindly retrying.

---

## 7. Evidence Before Hypothesis

A common mistake is:

    "I think Redis is broken."

Then every investigation step is designed to confirm Redis.

Better:

    observed:
      latency increased
      error rate increased
      Redis timeout rate increased

    hypothesis:
      Redis saturation may be contributing

    next evidence:
      connection count
      command latency
      CPU
      network
      application pool usage

Good debugging tries to disprove hypotheses.

---

## 8. Hypothesis-Driven Debugging

Use:

    Observation
        ↓
    Hypothesis
        ↓
    Prediction
        ↓
    Experiment
        ↓
    Result
        ↓
    Update hypothesis

Example:

    Observation:
    API is slow.

    Hypothesis:
    Database query is slow.

    Prediction:
    Query latency should increase with API latency.

    Experiment:
    Measure query duration.

    Result:
    Query remains fast.

    Conclusion:
    Investigate another layer.

This prevents random code changes.

---

## 9. Binary Search the Failure

Large systems contain many layers:

    Client
      ↓
    API gateway
      ↓
    Service
      ↓
    Cache
      ↓
    Database
      ↓
    External provider

Find the first boundary where expected behavior becomes incorrect.

For example:

    client → correct
    gateway → correct
    service → correct
    cache → incorrect

Now the search space is dramatically smaller.

---

## 10. Logging

Logs should answer:

- what happened?
- when?
- where?
- for which operation?
- with what result?
- with which dependency?

Useful fields:

- timestamp
- level
- service
- operation
- request ID
- correlation ID
- error code
- duration
- dependency
- safe contextual identifiers

Avoid logging secrets or sensitive payloads unnecessarily.

---

## 11. Structured Logging

Prefer structured events:

    {
      "event": "payment_failed",
      "requestId": "...",
      "provider": "...",
      "durationMs": 420,
      "errorCode": "TIMEOUT"
    }

over unstructured messages that are difficult to query consistently.

Structured logs improve incident investigation.

---

## 12. Metrics

Metrics reveal system-level behavior.

Useful categories:

### Traffic

- requests/sec
- jobs/sec

### Errors

- error rate
- failure count

### Latency

- p50
- p95
- p99

### Resources

- CPU
- memory
- connections
- queue depth

### Business

- successful payments
- completed jobs
- failed workflows

Metrics help identify patterns that individual logs cannot.

---

## 13. Tracing

Distributed tracing connects events across boundaries.

Example:

    request
      |
    API
      |
    Auth
      |
    Orders
      |
    PostgreSQL
      |
    Payment provider

A trace can reveal:

- where latency accumulated
- which dependency failed
- retry amplification
- unexpected call paths

Tracing is particularly useful for distributed systems.

---

## 14. Stack Traces

A stack trace shows the execution path associated with an error.

Read it from:

- error message
- relevant application frame
- caller
- root dependency
- original cause

Do not assume the topmost visible application line is the root cause.

The actual cause may be earlier state or a dependency failure.

---

## 15. Error Chains

Preserve causal information.

Example:

    OrderService
       ↓
    PaymentGateway
       ↓
    Provider
       ↓
    timeout

An error should retain useful context without exposing sensitive internals.

Use error causes or structured error metadata where supported.

---

## 16. Debugger Usage

A debugger can inspect:

- variables
- call stack
- execution path
- breakpoints
- conditional breakpoints
- watch expressions

Use it to answer a specific question.

Bad:

> I will step through everything.

Better:

> Why does this state become null after this function returns?

Focused debugger questions reduce investigation time.

---

## 17. Breakpoints

Useful breakpoint types include:

### Line breakpoint

Stops at a location.

### Conditional breakpoint

Stops only when a condition is true.

### Exception breakpoint

Stops when an error is thrown.

### Watchpoint

Stops when a value changes, where supported.

Conditional breakpoints are especially useful for rare failures.

---

## 18. Time-Based Debugging

Many failures depend on order.

Reconstruct:

    t0 request received
    t1 database query started
    t2 cache updated
    t3 event published
    t4 worker started
    t5 timeout
    t6 retry
    t7 duplicate effect

A timeline often reveals problems that source inspection alone cannot.

---

## 19. Concurrency Bugs

Concurrency failures often appear as:

- lost updates
- duplicate work
- inconsistent state
- deadlocks
- race conditions
- out-of-order events

Debugging strategy:

1. capture timestamps
2. capture operation IDs
3. capture entity/version
4. reconstruct interleaving
5. identify unsafe shared state
6. test the suspected interleaving

Do not assume execution order from source-code order.

---

## 20. Database Debugging

When a database-backed operation fails, inspect:

- SQL
- parameters
- query duration
- indexes
- locks
- connection pool
- transaction state
- isolation behavior
- row counts
- execution plan

For slow queries:

    reproduce
      ↓
    EXPLAIN
      ↓
    inspect plan
      ↓
    identify bottleneck
      ↓
    change
      ↓
    measure again

---

## 21. N+1 Debugging

A common performance pattern:

    fetch 100 users
       ↓
    query orders for each user
       ↓
    101 queries

Debugging approach:

1. count queries
2. inspect request trace
3. identify repeated query pattern
4. replace with batch/join strategy
5. benchmark

Do not optimize from intuition alone.

---

## 22. Network Debugging

For network failures inspect:

- DNS
- connection establishment
- TLS
- request timeout
- response timeout
- status code
- retries
- payload size
- connection pool
- proxy/load balancer
- remote service health

A timeout does not necessarily mean the remote operation failed.

It may have succeeded but the response was lost.

This distinction matters for idempotency.

---

## 23. Configuration Debugging

Many production failures are configuration failures.

Compare:

    expected configuration
          vs
    actual runtime configuration

Check:

- environment variables
- secrets
- feature flags
- endpoints
- ports
- timeouts
- credentials
- environment-specific overrides

Never print secrets merely to confirm configuration.

Log safe metadata instead.

---

## 24. Dependency Debugging

When an external dependency fails, separate:

    application failure
        vs
    dependency failure
        vs
    interaction failure

Inspect:

- dependency status
- request rate
- latency
- error codes
- retries
- timeouts
- circuit state
- connection state

This prevents blaming the wrong layer.

---

## 25. Memory Debugging

Memory problems may appear as:

- rising RSS
- heap growth
- GC pressure
- allocation spikes
- out-of-memory crashes

Investigation:

1. measure memory over time
2. identify whether heap or external memory grows
3. inspect allocation/retention
4. identify references preventing collection
5. reproduce under controlled load
6. verify memory returns toward baseline

Do not conclude "memory leak" solely because memory increased.

---

## 26. CPU Debugging

For CPU saturation:

1. confirm CPU is actually saturated
2. identify process/thread
3. profile hot functions
4. inspect algorithmic complexity
5. inspect serialization/parsing
6. inspect synchronous blocking
7. optimize
8. benchmark

Common causes:

- O(n²) work
- expensive JSON processing
- compression
- cryptography
- regex
- image processing
- model inference

---

## 27. Queue Debugging

For queue-based systems inspect:

- queue depth
- enqueue rate
- processing rate
- oldest message age
- worker count
- worker errors
- retry count
- dead-letter queue
- visibility/lease timeout

A useful mental model:

    arrival rate > service rate
             ↓
        queue grows

If this continues, the queue eventually becomes a failure boundary.

---

## 28. Distributed-System Debugging

Distributed failures often involve partial failure.

Example:

    Service A → Service B
                  |
              database

Service B may:

- receive the request
- perform the operation
- fail before responding

Service A sees:

    timeout

The operation may still have succeeded.

Therefore debugging must include:

- request IDs
- idempotency keys
- durable operation state
- downstream evidence

---

## 29. AI Debugging

AI systems add nondeterministic and multi-stage behavior.

Possible pipeline:

    request
      ↓
    preprocessing
      ↓
    retrieval
      ↓
    prompt construction
      ↓
    model
      ↓
    tool call
      ↓
    tool result
      ↓
    model
      ↓
    final output

When output is wrong, determine which stage diverged.

Do not immediately blame the model.

---

## 30. RAG Debugging

For a retrieval-augmented system inspect:

1. query normalization
2. embedding generation
3. vector search
4. filters
5. retrieved documents
6. ranking
7. context construction
8. prompt
9. model output

A poor answer may originate from retrieval rather than generation.

Capture enough diagnostic information to investigate without leaking sensitive documents.

---

## 31. Agent Debugging

Agents can fail because of:

- bad planning
- invalid tool selection
- malformed arguments
- repeated tool calls
- state corruption
- context overflow
- timeout
- tool failure
- termination failure

Trace:

    agent step
      ↓
    model decision
      ↓
    tool selection
      ↓
    arguments
      ↓
    tool result
      ↓
    next state

Agent traces should make each transition observable.

---

## 32. Debugging by Differential Comparison

Compare:

    working version
        vs
    failing version

Compare:

- inputs
- configuration
- dependency versions
- database state
- environment
- logs
- timing
- generated artifacts

The difference often reveals the causal change faster than reading the entire system.

---

## 33. Git Bisect

When a regression was introduced somewhere in history:

    known good
       |
       | many commits
       |
    known bad

Use binary search over commits to find the first bad revision.

Then combine:

    commit diff
       +
    regression test
       +
    runtime evidence

to establish causality.

---

## 34. Minimal Reproduction

A minimal reproduction removes unrelated complexity.

Example:

    full production workflow
             ↓
       isolated service
             ↓
       single endpoint
             ↓
       single input
             ↓
       failing function

A minimal reproduction is useful for:

- bug reports
- library issues
- performance experiments
- race conditions
- AI evaluation failures

---

## 35. Five Whys

Five Whys repeatedly asks why a failure occurred.

Example:

    Why did the job fail?
    → worker timed out.

    Why did it time out?
    → database query was slow.

    Why was it slow?
    → missing index.

    Why was the index missing?
    → migration was not included.

    Why was migration not included?
    → deployment process did not verify schema version.

The exact number five is not mandatory.

The objective is to move from symptom to system-level cause.

---

## 36. Root Cause Analysis

A useful incident analysis separates:

### Direct cause

Immediate technical failure.

### Contributing factors

Conditions that made failure possible.

### Detection gap

Why it was not caught earlier.

### Recovery gap

Why recovery was slow.

### Prevention

What changes reduce recurrence.

Avoid blaming an individual when the goal is improving system reliability.

---

## 37. Fix vs Workaround

A workaround reduces the immediate symptom.

A fix addresses the underlying cause.

Example:

    restart worker

may restore service.

But if workers leak connections, restarting does not solve the underlying problem.

Production incidents may require:

    mitigation first
       ↓
    root-cause fix second
       ↓
    prevention third

---

## 38. Safe Production Debugging

Production debugging must minimize additional risk.

Prefer:

- read-only inspection
- sampled logging
- controlled diagnostics
- feature flags
- canaries
- reversible changes

Avoid:

- arbitrary database writes
- logging sensitive payloads
- disabling security controls
- uncontrolled load generation

---

## 39. Observability-Driven Debugging

Observability should allow engineers to infer internal state from outputs.

Three major signals:

    Logs
    Metrics
    Traces

Combine them.

Example:

    Metric:
    p99 latency increased.

    Trace:
    database span dominates.

    Logs:
    query timeout errors increased.

Together they provide stronger evidence than any one signal.

---

## 40. Debugging Checklist

### Before changing code

- [ ] What exactly failed?
- [ ] Can I reproduce it?
- [ ] What changed?
- [ ] What evidence do I have?
- [ ] What are the possible failure boundaries?

### During investigation

- [ ] Have I formed a falsifiable hypothesis?
- [ ] Am I measuring rather than guessing?
- [ ] Can I reduce the reproduction?
- [ ] Where is the first incorrect state?

### Before closing

- [ ] Is the root cause understood?
- [ ] Is the fix verified?
- [ ] Is there a regression test?
- [ ] Is observability sufficient?
- [ ] Is prevention documented?

---

## 41. Trade-offs

| Technique | Benefit | Cost |
|---|---|---|
| Logging | Rich event detail | Storage/noise |
| Metrics | Fast trend detection | Limited detail |
| Tracing | Cross-service visibility | Instrumentation/storage |
| Debugger | Deep local inspection | Limited production suitability |
| Fault injection | Resilience evidence | Operational risk |
| Reproduction | High confidence | Setup effort |
| Binary search | Efficient localization | Requires comparable revisions |
| More telemetry | Better diagnosis | Cost/privacy complexity |

---

## 42. When to Use

Use hypothesis-driven debugging when:

- the failure has multiple possible causes
- the system is complex
- evidence is available

Use tracing when:

- requests cross service boundaries

Use profiling when:

- CPU or memory is suspected

Use database plans when:

- query performance is suspected

Use git bisect when:

- a regression can be reproduced across historical revisions

Use fault injection when:

- resilience behavior needs verification

---

## 43. When NOT to Use

Avoid:

- random code changes
- adding logs everywhere without a question
- debugging from stale evidence
- restarting systems repeatedly without investigation
- changing multiple variables simultaneously
- disabling safeguards just to reproduce a failure
- treating the first plausible explanation as the root cause

---

## 44. Common Mistakes

### Mistake 1 — Guessing

The engineer changes code before establishing evidence.

### Mistake 2 — Fixing symptoms

The immediate error disappears but the underlying failure remains.

### Mistake 3 — Ignoring timing

Concurrency and distributed systems often depend on event order.

### Mistake 4 — Missing the first divergence

Investigating the final error instead of where state first became incorrect.

### Mistake 5 — No regression test

The bug can return.

### Mistake 6 — Over-logging

Sensitive or high-volume telemetry creates new operational problems.

---

## 45. Failure Modes

| Failure | Root cause |
|---|---|
| Long investigation | Large search space |
| Wrong fix | Weak hypothesis |
| Repeated incident | No prevention |
| False diagnosis | Correlation mistaken for causation |
| Production damage | Unsafe debugging |
| Missing evidence | Poor observability |
| Flaky reproduction | Uncontrolled nondeterminism |
| AI misdiagnosis | Model blamed without pipeline inspection |

---

## 46. Security

Debugging can create security vulnerabilities.

Risks include:

- secret logging
- PII exposure
- production database modification
- disabled authorization
- debug endpoints
- verbose stack traces exposed to users

Debug information should follow least-privilege and data-minimization principles.

---

## 47. Performance

Debugging instrumentation can alter system behavior.

Examples:

- verbose logging increases I/O
- tracing adds overhead
- profilers may change timing
- debug builds may behave differently

When diagnosing performance, account for instrumentation overhead.

---

## 48. Scalability

A debugging strategy must work as systems grow.

For distributed systems, use:

- correlation IDs
- consistent structured logs
- centralized telemetry
- service-level dashboards
- dependency maps
- trace sampling

For high-volume systems, sampling may be necessary to control cost while retaining useful evidence.

---

## 49. Cost

Debugging has direct and indirect cost:

- engineer time
- telemetry storage
- incident downtime
- customer impact
- cloud resources

Better observability often has upfront cost but can substantially reduce incident investigation time.

## 50. Scenario-Based Questions

### Scenario 1 — 500 Error

An API suddenly returns 500 for 2% of requests.

Questions:

1. What evidence do you collect first?
2. How do you determine whether the failure is input-specific?
3. How do logs, metrics, and traces work together?
4. What would distinguish application failure from dependency failure?

### Scenario 2 — Intermittent Race

Two concurrent requests sometimes overwrite each other.

Questions:

1. How would you reproduce the race?
2. What state should be recorded?
3. Which invariant is violated?
4. What synchronization or database mechanism could enforce correctness?

### Scenario 3 — Memory Growth

RSS increases continuously during a long-running worker.

Questions:

1. What evidence distinguishes a leak from legitimate caching?
2. How would you inspect heap vs external memory?
3. How would you create a minimal reproduction?
4. What regression evidence would you retain?

### Scenario 4 — RAG Quality Drop

Users report that answers became less relevant after a deployment.

Questions:

1. How would you isolate retrieval from generation?
2. What artifacts should be compared?
3. How would you reproduce the failing queries?
4. What evaluation should be added?

### Scenario 5 — Timeout With Possible Duplicate Payment

The payment provider times out after receiving a request.

Questions:

1. Did the provider actually process it?
2. What evidence can establish the operation state?
3. Why is blindly retrying dangerous?
4. How should idempotency be involved?

## 52. Coding / Debugging Exercises

### Exercise 1 — Broken Algorithm

Given a failing algorithm:

1. reproduce
2. find first incorrect state
3. identify invariant violation
4. fix
5. add regression tests

### Exercise 2 — Race Condition

Build a shared-state race and reproduce it under concurrency.

Document:

- interleaving
- invariant
- root cause
- fix

### Exercise 3 — Memory Leak

Create a controlled retention bug and use runtime diagnostics to identify the retained objects.

### Exercise 4 — Database Incident

Create an intentionally inefficient query, measure it, inspect its execution plan, and optimize it.

### Exercise 5 — Distributed Timeout

Simulate:

    Service A → Service B → database

Introduce a timeout and determine whether the operation may have succeeded.

### Exercise 6 — AI Pipeline

Create a small RAG pipeline and intentionally introduce:

- bad retrieval
- incorrect context construction
- malformed output

Trace the failure to the correct stage.
