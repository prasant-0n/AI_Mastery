# 00.08 — Data Structures & Algorithmic Thinking

## 1. Why This Exists

Data structures determine how information is organized. Algorithms determine how that information is processed.

Backend, AI, and distributed systems repeatedly depend on these decisions:

- hash maps for fast lookup
- queues for asynchronous work
- heaps for priority scheduling
- trees for hierarchical data
- graphs for relationships and workflows
- sets for uniqueness
- indexes for database access
- tries for prefix search
- matrices and tensors for AI computation

The goal is not to memorize a list of structures.

The goal is to develop the reasoning pattern:

> What operations does the system need, what constraints exist, and which representation makes those operations efficient and correct?

---

## 2. Problem It Solves

Weak data-structure reasoning leads to:

- slow lookups
- unnecessary scans
- excessive memory use
- incorrect ordering
- duplicate data
- poor cache behavior
- inefficient algorithms
- weak interview performance
- poor system-design decisions

A strong engineer chooses structures based on required operations rather than familiarity.

---

## 3. Core Concept

Every data structure provides a set of operations with different costs.

For example:

    Array
      |
      +-- index access
      +-- append
      +-- search
      +-- insert
      +-- delete

The correct structure depends on which operations dominate the workload.

A useful decision process is:

    Requirements
        |
        v
    Required operations
        |
        v
    Constraints
        |
        v
    Data structure
        |
        v
    Algorithm
        |
        v
    Measure

---

## 4. Arrays

Arrays store elements in an ordered sequence.

Common operations:

- index access
- iteration
- append
- insertion
- deletion
- search

Conceptually:

    [ A ][ B ][ C ][ D ]
      0    1    2    3

Strengths:

- simple
- cache-friendly in many implementations
- direct index access
- excellent for sequential processing

Weaknesses:

- middle insertion/deletion can require shifting
- searching an unsorted array is linear

Use arrays when ordered iteration and indexed access are important.

---

## 5. Linked Lists

A linked list represents elements as nodes connected by references.

Conceptually:

    [A] → [B] → [C] → [D]

Advantages:

- local insertion/removal can be efficient when the node is known
- flexible node structure

Costs:

- no constant-time random access
- extra references
- poorer locality in many implementations
- more allocation overhead

In modern application code, arrays are often more practical than linked lists unless linked-list semantics specifically solve a problem.

---

## 6. Stacks

A stack follows:

    Last In → First Out

Conceptually:

    push A
    push B
    push C

    TOP
     C
     B
     A

    pop → C

Applications:

- call stacks
- undo operations
- DFS
- expression evaluation
- parsing

Core operations:

- push
- pop
- peek

---

## 7. Queues

A queue follows:

    First In → First Out

Conceptually:

    Front
      ↓
    [A][B][C][D]
                ↑
               Back

Applications:

- job processing
- message queues
- BFS
- request buffering
- event processing

Core operations:

- enqueue
- dequeue
- peek

Queues are foundational to backend and distributed systems.

---

## 8. Deques

A deque supports insertion/removal from both ends.

    Front ⇄ [A][B][C][D] ⇄ Back

Useful for:

- sliding-window algorithms
- work queues
- caches
- monotonic queue techniques

The data structure is especially useful when both ends matter.

---

## 9. Hash Maps

A hash map stores key-value associations.

    key
     |
     v
    hash
     |
     v
    bucket
     |
     v
    value

Typical average-case lookup is O(1), subject to implementation and hash-distribution assumptions.

Applications:

- user lookup by ID
- memoization
- frequency counting
- indexes
- caches
- deduplication

Worst-case behavior depends on the implementation and collision handling.

---

## 10. Sets

A set stores unique values.

Example:

    { A, B, C }

Useful for:

- membership tests
- deduplication
- visited-node tracking
- permissions
- feature flags

Example:

    const seen = new Set();

    if (seen.has(id)) {
      // already processed
    }

Choosing a set communicates that uniqueness and membership are the primary concerns.

---

## 11. Trees

Trees represent hierarchical relationships.

Example:

    Root
     |
     +-- A
     |   +-- A1
     |   +-- A2
     |
     +-- B
         +-- B1

Applications:

- file systems
- syntax trees
- organizational structures
- indexes
- UI hierarchies
- decision structures

Important concepts include:

- root
- parent
- child
- leaf
- depth
- height

---

## 12. Binary Search Trees

A binary search tree organizes values according to an ordering rule.

Conceptually:

        8
       /       4   12
     /   /     2  6 10 14

When balanced, search can approach O(log n).

When badly skewed:

    1
           2
               3
                   4

it can degrade toward O(n).

Tree performance therefore depends on structure.

---

## 13. Heaps

A heap supports efficient access to an extreme-priority element.

Min-heap:

    smallest element at top

Max-heap:

    largest element at top

Applications:

- priority queues
- scheduling
- top-K problems
- shortest-path algorithms
- rate/event scheduling

A heap is usually not chosen for arbitrary lookup.

Its strength is priority management.

---

## 14. Priority Queues

A priority queue processes elements according to priority rather than arrival order.

Example:

    normal job → priority 1
    urgent job → priority 10

The urgent job should be processed first.

Applications:

- task scheduling
- job systems
- networking
- operating systems
- AI agent scheduling

This connects directly to production worker systems.

---

## 15. Graphs

Graphs model relationships between entities.

Conceptually:

    A ---- B
    |      |
    |      |
    C ---- D

A graph consists of:

- vertices/nodes
- edges
- optional weights
- optional direction

Applications:

- social networks
- dependency graphs
- service topology
- workflows
- knowledge graphs
- routing
- agent task dependencies

---

## 16. Directed vs Undirected Graphs

### Directed

    A → B

The relationship has direction.

Examples:

- dependency
- workflow transition
- following relationship

### Undirected

    A — B

The relationship is symmetric.

Examples:

- physical connection
- friendship model
- bidirectional relationship

Choose the representation that matches the domain.

---

## 17. Weighted Graphs

Edges can have weights.

    A --5--> B
    A --2--> C
    C --1--> B

Weights may represent:

- distance
- latency
- cost
- risk
- capacity

This enables algorithms such as shortest-path analysis.

---

## 18. Graph Traversal

Two foundational traversal strategies are:

### Breadth-First Search

Uses queue-like exploration:

    Start
     |
     +-- neighbors
          |
          +-- next level

Useful for:

- shortest unweighted paths
- level-order traversal
- relationship distance

### Depth-First Search

Explores deeply before backtracking.

Useful for:

- dependency traversal
- cycle detection
- backtracking
- connected components

---

## 19. Graph Representation

Common representations:

### Adjacency list

    A → [B, C]
    B → [A, D]

Efficient for sparse graphs.

### Adjacency matrix

    matrix[A][B] = 1

Useful when dense connectivity or constant-time edge lookup is important.

Representation should follow workload characteristics.

---

## 20. Tries

A trie stores strings by shared prefixes.

Example:

    c
    |
    a
    |
    t
   /   s   h

Useful for:

- autocomplete
- prefix search
- dictionaries
- routing patterns

Tries can trade memory for fast prefix operations.

---

## 21. Disjoint Set Union

Disjoint Set Union, also called Union-Find, tracks connected components.

Core operations:

- find
- union

Useful for:

- connectivity
- clustering
- cycle detection
- network grouping

With path compression and union by rank/size, operations are extremely efficient in practice.

---

## 22. Choosing a Data Structure

Use a requirement-first approach.

Ask:

1. Do I need indexed access?
2. Do I need fast key lookup?
3. Do I need uniqueness?
4. Do I need FIFO behavior?
5. Do I need LIFO behavior?
6. Do I need priority ordering?
7. Do I need hierarchical relationships?
8. Do I need arbitrary graph relationships?
9. Do I need prefix queries?
10. What are the memory constraints?

Then choose.

Do not start with:

> "Which data structure do I remember?"

Start with:

> "Which operations dominate?"

---

## 23. Algorithmic Thinking

An algorithm is a procedure for solving a problem.

A strong algorithmic process is:

    Understand problem
         |
         v
    Define inputs/outputs
         |
         v
    Identify constraints
         |
         v
    Choose representation
         |
         v
    Choose algorithm
         |
         v
    Prove correctness
         |
         v
    Analyze complexity
         |
         v
    Test edge cases
         |
         v
    Optimize if necessary

---

## 24. Brute Force First

A brute-force solution can be valuable as a baseline.

Why?

Because it provides:

- a correctness reference
- a simple implementation
- a way to discover constraints
- a comparison point for optimization

The process is:

    Correct simple solution
          |
          v
    Identify bottleneck
          |
          v
    Improve representation/algorithm
          |
          v
    Compare results

Do not optimize before understanding the problem.

---

## 25. Invariants

An invariant is a condition that remains true during algorithm execution.

Example:

For a sliding window:

    left <= right

and the current window satisfies the required condition.

Invariants help prove correctness and debug algorithms.

Ask:

> What must always remain true after each step?

---

## 26. Two Pointers

Two pointers maintain two positions while processing a sequence.

Example:

    left → [ ... ]
                [ ... ] ← right

Useful for:

- sorted arrays
- pair problems
- partitioning
- sliding windows

The technique often reduces nested loops to linear scans.

---

## 27. Sliding Window

A sliding window maintains a contiguous region.

Conceptually:

    [ A B C D E F G ]
      ← window →

Expand and shrink the window according to constraints.

Useful for:

- substring problems
- rate windows
- streaming analytics
- moving aggregates

This pattern also appears in production systems such as rolling metrics.

---

## 28. Binary Search

Binary search repeatedly halves the search space.

Requirements usually include a monotonic or sorted search condition.

Conceptually:

    low -------- high
          |
        middle

After each decision:

    low --- high
        ↓
    half removed

Complexity:

    O(log n)

Binary search is also useful beyond arrays when a predicate is monotonic.

---

## 29. Sorting

Sorting is a foundational algorithmic operation.

Common classes include:

- comparison sorting
- counting/radix approaches
- external sorting

Efficient comparison sorting is commonly O(n log n).

Sorting can enable later algorithms such as:

- binary search
- two pointers
- interval merging
- deduplication

The cost of sorting must be justified by subsequent benefits.

---

## 30. Hashing as an Algorithmic Tool

Hashing can convert repeated searches into membership or lookup operations.

Example:

    naive:
      for each item
        scan all previous items

    optimized:
      set.has(item)

This often changes:

    O(n²)

into approximately:

    O(n)

at the cost of additional memory.

This is one of the most important interview optimization patterns.

---

## 31. Recursion and Backtracking

Backtracking explores possible choices and reverses decisions when a branch fails.

Conceptually:

    choose
      |
      v
    explore
      |
      +--> success
      |
      +--> failure → undo → try next

Applications:

- permutations
- combinations
- constraint problems
- parsers
- search spaces

Backtracking can have exponential complexity.

Use pruning to eliminate impossible branches early.

---

## 32. Dynamic Programming

Dynamic programming solves problems with overlapping subproblems and useful optimal-substructure properties.

Two common styles:

### Top-down

    recursive solution
          +
    memoization

### Bottom-up

    build smaller solutions
          ↓
    build larger solutions

The core idea:

> Do not recompute the same expensive subproblem unnecessarily.

---

## 33. Greedy Algorithms

A greedy algorithm makes a locally optimal choice at each step.

Greedy solutions are correct only when the problem has the necessary structural properties.

Do not assume:

    locally best = globally best

You need a correctness argument.

Applications include:

- interval scheduling
- some routing/optimization problems
- minimum spanning tree algorithms
- resource allocation under appropriate assumptions

---

## 34. Graph Algorithms

Important foundational algorithms include:

- BFS
- DFS
- topological sorting
- shortest paths
- minimum spanning tree
- connected components
- cycle detection

These become directly relevant to:

- dependency systems
- workflow engines
- service graphs
- knowledge graphs
- agent planning

---

## 35. Algorithm Correctness

Correctness should be reasoned about, not assumed.

Useful techniques:

- invariants
- induction
- counterexamples
- boundary-case analysis
- exhaustive testing for small inputs

Ask:

1. Does it terminate?
2. Does it produce the required output?
3. Does it handle empty input?
4. Does it handle maximum input?
5. Does it preserve required invariants?
6. Does it avoid invalid states?

---

## 36. Production Considerations

Real systems add constraints beyond textbook algorithms:

- data arrives continuously
- input may be malformed
- memory is limited
- dependencies are remote
- workloads are concurrent
- data may be too large for memory
- operations may fail
- results may need to be observable

Therefore an algorithm that is theoretically efficient may still be operationally inappropriate.

---

## 37. Trade-offs

| Choice | Benefit | Cost |
|---|---|---|
| Array | Simplicity/locality | Slow arbitrary insertion |
| Hash map | Fast lookup | Extra memory |
| Set | Fast membership | No ordered semantics by default |
| Heap | Efficient priority access | Limited arbitrary lookup |
| Tree | Ordered/hierarchical data | More structural complexity |
| Graph | Flexible relationships | Higher memory/algorithm complexity |
| Recursion | Natural for recursive structures | Stack depth |
| Iteration | Explicit resource control | Sometimes more verbose |
| Memoization | Avoid repeated work | Memory |
| Greedy | Often fast/simple | Requires correctness proof |

---

## 38. When to Use

Use a hash map when:

- key-based lookup dominates

Use a set when:

- uniqueness/membership dominates

Use a queue when:

- FIFO processing matters

Use a heap when:

- priority selection dominates

Use a tree when:

- hierarchy or ordered structure matters

Use a graph when:

- arbitrary relationships matter

Use dynamic programming when:

- subproblems overlap

Use BFS/DFS when:

- graph/tree traversal is required

---

## 39. When NOT to Use

Do not:

- choose a complex structure when an array is sufficient
- use hash maps when ordering semantics are primary
- use recursion for unbounded depth
- use dynamic programming without identifying overlapping subproblems
- use greedy algorithms without a correctness argument
- optimize algorithmic complexity while ignoring database/network costs

---

## 40. Common Mistakes

### Mistake 1 — Memorizing patterns

Recognizing "sliding window" is not enough. Understand why it works.

### Mistake 2 — Ignoring constraints

A solution may work for n=100 but fail at n=10 million.

### Mistake 3 — Forgetting memory

An O(n) optimization may be impossible under strict memory limits.

### Mistake 4 — Incorrect invariants

A broken invariant usually means the algorithm is incorrect.

### Mistake 5 — Optimizing the wrong layer

A faster local algorithm does not help if the database dominates latency.

### Mistake 6 — Ignoring real-world input

Production data can be malformed, adversarial, or much larger than test data.

---

## 41. Failure Modes

| Failure | Root cause |
|---|---|
| Timeout | Poor complexity |
| Out-of-memory | Excessive auxiliary storage |
| Wrong result | Broken invariant |
| Infinite loop | Incorrect termination condition |
| Stack overflow | Excessive recursion |
| Duplicate work | Missing memoization/deduplication |
| Slow lookup | Wrong data structure |
| Queue overload | Wrong scheduling structure |
| Graph explosion | Unbounded traversal |
| Production mismatch | Ignored workload constraints |

## 42. Security

Algorithm choice can affect security.

Potential risks include:

- algorithmic complexity attacks
- hash collision abuse
- regex denial of service
- graph traversal explosions
- unbounded parsing
- adversarial input sizes

Security-sensitive algorithms should have:

- input limits
- time budgets
- memory limits
- depth limits
- concurrency limits

Treat worst-case input as a production concern.

---

## 43. Performance

When evaluating an algorithm, consider:

    Time complexity
    Space complexity
    Constant factors
    Allocation
    Cache behavior
    I/O
    Network
    Concurrency
    Input distribution

Then benchmark realistic workloads.

The best algorithm on paper is not always the best implementation for a particular system.

---

## 44. Scalability

As data grows:

    O(log n)
    O(n)
    O(n log n)
    O(n²)

can behave dramatically differently.

But distributed systems add another dimension:

    local computation
        +
    data movement
        +
    coordination

An algorithm that requires many network round trips may be worse than a slightly more expensive local algorithm.

---

## 45. Cost

Algorithmic efficiency affects infrastructure cost.

Examples:

- fewer database queries
- fewer CPU cycles
- lower memory requirements
- fewer network calls
- fewer model calls
- less data movement

In AI systems, algorithmic improvements can also reduce:

- retrieval count
- reranking work
- token generation
- tool invocations

---

## 46. Debugging

When an algorithm produces incorrect output:

1. Reproduce with the smallest failing input.
2. Identify the first incorrect state.
3. Check the invariant.
4. Trace one iteration at a time.
5. Compare against a brute-force reference.
6. Test boundaries.
7. Test duplicates and empty inputs.
8. Test maximum realistic sizes.

For performance problems:

1. measure input size
2. measure operation count
3. profile
4. identify dominant complexity
5. optimize representation or algorithm
6. benchmark again

## 47. Scenario-Based Questions

### Scenario 1 — Duplicate Detection

You need to determine whether a list contains duplicates.

Options:

- nested loops
- sorting
- set

Questions:

1. What are the time and space trade-offs?
2. Which choice changes the asymptotic complexity?
3. When might sorting still be preferable?

### Scenario 2 — Top K

A service receives millions of values but only needs the top 100.

Questions:

1. Should you sort everything?
2. Could a heap reduce work?
3. What is the memory requirement?
4. How does streaming change the design?

### Scenario 3 — Dependency Graph

A build system contains thousands of dependencies.

Questions:

1. What graph representation is appropriate?
2. How do you detect cycles?
3. How do you determine build order?
4. What happens when the graph is extremely large?

### Scenario 4 — AI Retrieval

A retrieval system returns 10,000 candidate documents but only needs the best 20.

Questions:

1. Where should filtering happen?
2. Can top-K structures help?
3. What is the cost of reranking all 10,000?
4. Can candidate generation be reduced earlier?

### Scenario 5 — Large Input Attack

An endpoint accepts an arbitrary graph and traverses it recursively.

Questions:

1. What resource-exhaustion risks exist?
2. What depth/size limits should exist?
3. Could iterative traversal be safer?
4. How should cycles be handled?
