# 00.05 — Errors & Failure Boundaries

## 1. Why This Exists

Production software fails.

Databases become unavailable. Network requests time out. Input is malformed. Credentials expire. Processes run out of memory. Queues deliver duplicate messages. External APIs return unexpected responses. AI models produce invalid or unsafe output.

A professional engineer therefore does not design only for the successful path.

The system must define:

- what can fail
- where failure is detected
- how failure is represented
- who handles it
- whether the operation can be retried
- what state remains after failure
- what the user should observe
- what operators should observe

The central mental model is:

> Failure is part of normal system behavior, not an exception to architecture.

---

## 2. Problem It Solves

Poor failure design creates:

- swallowed errors
- misleading error messages
- duplicate side effects
- corrupted state
- unsafe retries
- cascading failures
- information leaks
- impossible debugging
- silent data loss
- unnecessary outages

A strong system makes failure behavior explicit.

---

## 3. Core Concept

Model an operation as:

    Input
      |
      v
    Validation
      |
      v
    Business operation
      |
      v
    External side effect
      |
      v
    Output

At every stage:

    Success → continue

    Failure → classify
                 |
                 +--> recover
                 +--> retry
                 +--> compensate
                 +--> reject
                 +--> escalate
                 +--> terminate

Not every failure should be handled the same way.

---

## 4. Error vs Failure

An **error** is a representation of something that went wrong.

A **failure** is the system behavior or condition resulting from an unsuccessful operation.

Examples:

    Database timeout
        ↓
    Error detected
        ↓
    Request fails
        ↓
    System records incident

The distinction is useful because throwing an error does not itself define the system's recovery behavior.

---

## 5. Failure Categories

Useful categories include:

### Validation failure

Input does not satisfy the contract.

Example:

    email = invalid

Usually:

    reject request

### Authentication failure

The caller cannot establish identity.

### Authorization failure

The caller is authenticated but lacks permission.

### Business failure

The requested operation violates domain rules.

Example:

    order already cancelled

### Dependency failure

An external system is unavailable or returns an unexpected response.

### Resource failure

CPU, memory, disk, connection pool, or another resource is exhausted.

### Programmer error

The software violates an internal assumption.

Example:

    undefined state that should be impossible

### Unknown failure

The system cannot safely classify the problem.

These categories should not automatically map to the same HTTP response, retry policy, or logging level.

---

## 6. Failure Boundaries

A failure boundary is a point where a failure can be:

- detected
- classified
- translated
- logged
- recovered
- propagated

Examples:

    HTTP Controller
        |
        v
    Service
        |
        v
    Repository
        |
        v
    Database

The repository may detect a database error.

The service decides whether that failure is meaningful to the business operation.

The controller decides how to expose the result through the API.

This prevents every layer from handling every error independently.

---

## 7. Error Propagation

Errors should travel until a component has enough context to handle them correctly.

Bad pattern:

    try {
      operation();
    } catch {
      return null;
    }

This may hide the actual failure.

Better:

    lower layer
        |
        v
    meaningful error
        |
        v
    boundary with context
        |
        v
    appropriate handling

A function should not catch an error merely because it can.

Catch it when the layer has a reason to recover, translate, add context, or perform cleanup.

---

## 8. Error Translation

Internal infrastructure details should not always leak to clients.

For example:

    PostgreSQL connection refused

is an infrastructure-level error.

The API may expose:

    "Service temporarily unavailable"

while logs and traces preserve the technical details.

Conceptually:

    Internal error
         |
         v
    Classification
         |
         +--> operator detail
         |
         +--> user-safe response

This is both a usability and security concern.

---

## 9. Error Taxonomy

A production error taxonomy should distinguish at least:

    CLIENT / INPUT
        ↓
    AUTHENTICATION
        ↓
    AUTHORIZATION
        ↓
    BUSINESS
        ↓
    DEPENDENCY
        ↓
    RESOURCE
        ↓
    PROGRAMMER / SYSTEM

The exact taxonomy can differ by application.

The important property is consistency.

---

## 10. Expected vs Unexpected Errors

### Expected

The application knows these can occur as part of normal operation.

Examples:

- invalid input
- insufficient permissions
- resource not found
- business rule violation
- expected dependency rejection

These should have deliberate responses.

### Unexpected

Examples:

- invariant violation
- impossible state
- programming bug
- corrupted internal state

These generally require:

- logging
- tracing
- alerting where appropriate
- investigation

Do not turn every unexpected error into a friendly "try again" response while hiding the root cause.

---

## 11. Exceptions

Exceptions provide one mechanism for propagating failures through call stacks.

Example:

    function loadUser(id) {
      if (!id) {
        throw new Error("User ID required");
      }

      return repository.findById(id);
    }

Exceptions are useful when callers need to handle failures at a higher boundary.

But exceptions do not automatically solve:

- retry policy
- idempotency
- distributed transactions
- recovery
- observability

Those are architectural concerns.

---

## 12. Result-Based Errors

Some systems represent success and failure explicitly.

Conceptually:

    Result<Success, Failure>

Example:

    {
      ok: true,
      value: user
    }

or:

    {
      ok: false,
      error: "NOT_FOUND"
    }

This can make expected business failures explicit.

It can also introduce verbosity.

The important engineering question is:

> Is this failure exceptional control flow or a normal domain outcome?

---

## 13. Cleanup and Finally

Resources often need cleanup even when an operation fails.

Example:

    const connection = acquire();

    try {
      await execute(connection);
    } finally {
      release(connection);
    }

Cleanup concerns include:

- database connections
- file handles
- locks
- temporary files
- timers
- subscriptions
- tracing spans

Failure handling must preserve resource lifecycle correctness.

---

## 14. Error Context

A useful error should preserve enough context to diagnose the problem.

Context can include:

- operation name
- request ID
- correlation ID
- user/tenant context where appropriate
- dependency
- error category
- retry state
- timing
- relevant identifiers

Avoid putting secrets or sensitive personal data into errors and logs.

Good context:

    payment.charge.failed
    request_id=abc
    dependency=payment-provider
    attempt=2
    timeout=true

Bad context:

    password=...
    authorization_token=...
    full_sensitive_payload=...

---

## 15. Error Codes

Stable machine-readable codes are often better than parsing human-readable messages.

Example:

    USER_NOT_FOUND
    ORDER_ALREADY_PAID
    PAYMENT_PROVIDER_TIMEOUT

Clients can handle codes while messages remain human-readable.

Avoid exposing raw database or infrastructure messages as public API contracts.

---

## 16. HTTP Error Semantics

HTTP APIs should use status codes consistently.

Examples:

- 400 — malformed request
- 401 — authentication required/failed
- 403 — authenticated but not permitted
- 404 — resource not found
- 409 — state/conflict condition
- 422 — semantically invalid input where appropriate
- 429 — rate limited
- 500 — unexpected server failure
- 502/503/504 — dependency/gateway/service availability failures where appropriate

The exact mapping depends on the API contract.

Do not use 500 for every possible problem.

---

## 17. Retryability

Not every error should be retried.

A useful classification is:

    Retryable?
       |
       +-- Yes → bounded retry policy
       |
       +-- No  → fail / compensate / report

Potentially retryable:

- transient network failure
- temporary service unavailable
- some rate limits
- connection reset

Usually not retryable without changing input/state:

- validation failure
- authorization failure
- malformed request
- permanent business rule violation

Retry decisions should be based on semantics, not simply the presence of an exception.

---

## 18. Exponential Backoff

Repeated retries can overload a struggling dependency.

A common approach is increasing the delay:

    attempt 1 → short delay
    attempt 2 → longer delay
    attempt 3 → longer delay

Often jitter is added so many clients do not retry simultaneously.

Conceptually:

    retry delay
         ^
         |          *
         |       *
         |    *
         | *
         +----------------> attempts

Retries should also have:

- maximum attempts
- maximum elapsed time
- cancellation
- observability

---

## 19. Retry Storms

Suppose:

    Service A
       |
       v
    Service B

Service B becomes slow.

If A immediately retries every failure:

    A → B
    A → B
    A → B
    A → B
       ↓
    B becomes even more overloaded

Retries can therefore amplify failures.

This is why production systems often combine:

- exponential backoff
- jitter
- timeouts
- circuit breakers
- rate limits
- concurrency limits

---

## 20. Timeout as a Failure Boundary

Without a timeout:

    Request
       |
       v
    External service
       |
       ...
       ...
       ↓
    Resources remain occupied

A timeout converts indefinite waiting into a bounded failure.

Every network boundary should have an intentional timeout policy.

Different operations may require different budgets.

---

## 21. Cancellation

Sometimes the caller no longer needs the result.

For example:

    User closes request
        ↓
    Work continues unnecessarily

Cancellation allows work to stop when appropriate.

Cancellation is especially valuable for:

- HTTP requests
- long-running jobs
- AI generation
- database operations
- streaming
- background workflows

Cancellation must be propagated through the operation graph where supported.

---

## 22. Partial Failure

Distributed operations can partially succeed.

Example:

    Create order       ✓
    Charge payment    ✓
    Send email        ✗

The system is now in a partially completed state.

The correct response is not always:

    "Retry everything."

Instead ask:

1. What succeeded?
2. What failed?
3. What state was persisted?
4. Can the failed step be retried safely?
5. Is compensation required?
6. Can the workflow resume from the failure point?

This is foundational distributed-systems reasoning.

---

## 23. Compensation

When an operation cannot be atomically rolled back, a compensating action may be needed.

Example:

    Reserve inventory ✓
    Charge payment    ✓
    Shipping creation ✗

A compensating workflow might release inventory or initiate a refund, depending on business semantics.

Compensation is not the same as database rollback.

It is a new operation that attempts to restore an acceptable business state.

---

## 24. Idempotency

An operation is idempotent when repeating it produces the same intended final effect.

This matters because retries can duplicate side effects.

Example:

    POST /payments

If a client times out after the payment provider accepts the request, the client may retry.

An idempotency key can allow the server/provider to recognize:

    same logical operation
        ≠
    new operation

Idempotency is a core reliability pattern.

---

## 25. Error Handling and Transactions

Transactions can protect multiple database changes from partial persistence.

Example:

    Begin transaction
       |
       +-- create order
       +-- create order items
       +-- update inventory
       |
       v
    Commit

If a transaction fails:

    Rollback

But transactions do not automatically cover external services.

For example:

    Database transaction
          |
          X
    External payment provider

This is why distributed workflows require additional patterns.

---

## 26. Circuit Breakers

A circuit breaker can stop repeatedly calling an unhealthy dependency.

Conceptually:

    CLOSED
      |
      | repeated failures
      v
    OPEN
      |
      | wait
      v
    HALF-OPEN
      |
      +--> success → CLOSED
      |
      +--> failure → OPEN

Circuit breakers can protect both the caller and dependency.

They add state and operational complexity, so they should be introduced when the failure pattern justifies them.

---

## 27. Bulkheads

A bulkhead isolates resources so one workload cannot consume everything.

Example:

    Tenant A
       |
       +--> worker pool A

    Tenant B
       |
       +--> worker pool B

Or:

    critical jobs → reserved capacity
    background jobs → separate capacity

The goal is to limit blast radius.

---

## 28. Graceful Degradation

A system may provide reduced functionality instead of failing completely.

Example:

    Primary recommendation service
            |
            X
            |
            v
    Cached recommendations

Or:

    AI provider unavailable
          |
          v
    deterministic fallback response

Degradation should be explicit and safe.

Never silently return incorrect data merely to keep the system "working."

---

## 29. Failure Containment

A failure should ideally remain within the smallest practical boundary.

Example:

    One background job fails
          |
          X
          |
          v
    Other jobs continue

This is better than:

    One job fails
          |
          v
    entire worker crashes
          |
          v
    all jobs stop

Isolation improves reliability.

---

## 30. Production Considerations

Every important operation should have an explicit answer for:

- timeout
- retry
- cancellation
- error classification
- logging
- metrics
- tracing
- idempotency
- resource cleanup
- user-visible response
- recovery

For expensive or irreversible operations, add stronger controls.

Examples:

- payment
- deletion
- external tool execution
- infrastructure changes
- AI-generated actions

---

## 31. Trade-offs

| Pattern | Benefit | Cost |
|---|---|---|
| Retry | Recovers transient failures | Duplicate load/side effects |
| Timeout | Bounds resource usage | May terminate slow-but-valid work |
| Circuit breaker | Protects unhealthy dependencies | Additional state |
| Bulkhead | Limits blast radius | Lower resource sharing |
| Fallback | Maintains availability | Reduced functionality |
| Compensation | Handles partial workflows | Business complexity |
| Transaction | Strong database consistency | Lock/resource cost |
| Idempotency | Safe retries | Storage/state complexity |

Reliability mechanisms themselves create complexity.

Use them intentionally.

---

## 32. When to Use

Use retries when:

- failure is plausibly transient
- the operation is safe to retry
- the retry budget is bounded

Use idempotency when:

- operations can be retried
- side effects must not duplicate

Use timeouts when:

- waiting indefinitely is harmful

Use circuit breakers when:

- a dependency repeatedly fails
- continued calls create additional harm

Use compensation when:

- distributed steps can partially succeed
- atomic rollback is impossible

Use bulkheads when:

- workloads have different criticality
- resource exhaustion could spread

---

## 33. When NOT to Use

Do not:

- retry every error
- retry non-idempotent side effects blindly
- set enormous timeouts to hide dependency problems
- add circuit breakers without measuring the failure pattern
- swallow errors to make dashboards look healthy
- return fake success during dependency failure
- use distributed transactions where simpler workflow design is sufficient

---

## 34. Common Mistakes

### Mistake 1 — Catch and ignore

    try {
      await operation();
    } catch {}

This destroys diagnostic information.

### Mistake 2 — Retry everything

Some failures are permanent.

### Mistake 3 — Infinite retries

A retry loop can become an outage amplifier.

### Mistake 4 — No timeout

A stuck dependency can consume resources indefinitely.

### Mistake 5 — Retry without idempotency

The same side effect can happen multiple times.

### Mistake 6 — Log secrets

Error context must not become a data-leak channel.

### Mistake 7 — Treat all 500 errors equally

Different root causes require different operational responses.

---

## 35. Failure Modes

| Failure mode | Typical cause |
|---|---|
| Duplicate payment | Unsafe retry |
| Retry storm | Missing backoff/jitter |
| Cascading outage | Unbounded dependency failure |
| Resource exhaustion | Missing timeout/limits |
| Silent data loss | Swallowed error |
| Corrupted workflow state | Partial failure |
| Information leak | Raw internal error exposed |
| Stuck worker | Missing cancellation |
| Dependency overload | Aggressive retries |
| False success | Unsafe fallback |

---

## 36. Security

Error handling is part of the security boundary.

Do not expose:

- stack traces
- SQL statements
- internal hostnames
- credentials
- tokens
- secrets
- sensitive user data

to untrusted clients.

Use:

    External response
       |
       v
    safe error contract

while preserving detailed diagnostics internally.

Also consider denial-of-service through failure paths:

- oversized payloads
- expensive retries
- repeated expensive AI calls
- unbounded queues
- resource-exhausting inputs

---

## 37. Performance

Failure handling consumes resources.

For example:

    Original request
       +
    3 retries
       +
    logging
       +
    tracing
       +
    fallback

may cost much more than a single request.

Therefore reliability must be budgeted.

Measure:

- retry counts
- timeout rates
- dependency latency
- queue age
- failure rate
- recovery time
- fallback usage

---

## 38. Scalability

At scale, failure amplification becomes dangerous.

If:

    10,000 clients

each retry a failed dependency three times, the dependency may receive:

    40,000 requests

instead of 10,000.

This is why distributed systems use bounded retries, jitter, rate limits, concurrency controls, and load shedding.

Reliability design must account for aggregate behavior, not just one request.

---

## 39. Cost

Failures can directly increase cost.

Examples:

- duplicate model calls
- repeated database queries
- retry traffic
- additional compute
- emergency scaling
- duplicate external transactions

AI systems are especially sensitive to retry loops because each model call may consume meaningful compute and token budget.

Cost controls should therefore participate in failure handling.

---

## 40. Debugging

When an operation fails, reconstruct the timeline.

Example:

    t0 request received
    t1 validation passed
    t2 payment request sent
    t3 payment provider accepted
    t4 response timed out
    t5 client retried
    t6 second payment request sent

The critical discovery is:

> The timeout did not prove that the payment failed.

This is why distributed systems require:

- correlation IDs
- idempotency keys
- timestamps
- structured logs
- traces
- dependency metrics

Debugging should reconstruct state transitions, not merely inspect the final exception.

## 41. Scenario-Based Questions

### Scenario 1 — Payment Timeout

A payment API times out, but the provider may have processed the charge.

Questions:

1. Should the client retry?
2. How can the operation be made idempotent?
3. How can the final payment state be reconciled?
4. What evidence is needed to determine whether the charge succeeded?

### Scenario 2 — Retry Storm

A dependency begins returning 503.

Questions:

1. What happens if every client retries immediately?
2. How do backoff and jitter help?
3. Should there be a circuit breaker?
4. Should requests be shed?

### Scenario 3 — Partial Order Workflow

An order is created and inventory reserved, but shipping creation fails.

Questions:

1. What state should the order enter?
2. Can shipping creation be retried?
3. Should inventory be released?
4. Where should recovery logic live?

### Scenario 4 — AI Provider Failure

The primary LLM provider is unavailable.

Questions:

1. Should the request fail?
2. Is there a fallback model?
3. Are prompts and tool contracts compatible?
4. How do you prevent duplicate expensive generation?
5. What should be recorded for observability?

### Scenario 5 — Worker Failure

A background job fails halfway through processing.

Questions:

1. Can the job resume?
2. Is the operation idempotent?
3. What state was persisted?
4. Should the job retry?
5. When should it move to a dead-letter queue?
