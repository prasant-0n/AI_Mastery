# 00.18 — Phase 00 Project

## 1. Project Overview

Phase 00 ends with one integrated engineering project.

The purpose of this project is to demonstrate that the concepts from the Engineering Foundation can be combined into a working, testable, debuggable, observable, and defensible system.

This is not intended to be a feature-heavy application.

It is an engineering laboratory disguised as a real backend service.

The project must demonstrate:

- programming fundamentals
- data and type boundaries
- memory awareness
- asynchronous execution
- concurrency control
- complexity analysis
- data structures
- modular architecture
- testing
- Git workflow
- debugging
- observability
- failure handling
- security boundaries
- performance measurement
- scalability reasoning
- cost awareness
- architectural trade-offs
- AI-system engineering principles

## 2. Project Name

**Engineering Task Platform**

Suggested repository/project name:

`engineering-task-platform`

The exact implementation language may be TypeScript/Node.js, with PostgreSQL for persistence and Redis or an equivalent queue/cache component where appropriate.

The architecture should remain understandable enough to inspect during interviews.

## 3. Problem Statement

Build a backend platform where authenticated users can create tasks and submit long-running processing jobs.

The platform must:

1. accept validated task requests
2. persist task state
3. execute asynchronous jobs
4. expose task status
5. prevent duplicate job execution
6. handle failures safely
7. expose structured observability
8. enforce tenant/user boundaries
9. provide measurable performance
10. document architectural decisions

The system should support simulated external dependencies so reliability and debugging behavior can be tested without depending on real third-party services.

## 6. Functional Requirements

### 6.1 Authentication

Support:

- user registration
- login
- authenticated requests

Do not store plaintext passwords.

### 6.2 Tenant Context

Each user belongs to an organization.

Every task belongs to an organization.

Every protected operation must enforce tenant ownership.

### 6.3 Task Creation

Example:

`POST /v1/tasks`

Request:

~~~json
{
  "type": "process_document",
  "input": {
    "documentId": "..."
  }
}
~~~

Response should return a task identifier and initial state.

### 6.4 Task Status

Example:

`GET /v1/tasks/:taskId`

Return:

- task ID
- organization ID
- type
- status
- timestamps
- result metadata
- error information when safe

### 6.5 Task Processing

A background worker processes tasks.

Suggested state machine:

    PENDING
       ↓
    QUEUED
       ↓
    RUNNING
      /   \
 SUCCEEDED FAILED
            |
         RETRYABLE?
          /     \
        YES      NO
        ↓         ↓
     QUEUED     FAILED

Optional terminal state:

    CANCELLED

### 6.6 Idempotency

Task submission should support an idempotency key.

Repeated requests with the same logical key must not accidentally create duplicate work.

Define:

- key scope
- expiration
- request compatibility
- stored result behavior

### 6.7 Retry

Only retry failures that are classified as retryable.

Use:

- bounded attempts
- exponential backoff
- jitter

Never implement infinite retries.

### 6.8 Timeout

External processing must have bounded execution time.

The system must distinguish:

- successful completion
- timeout
- cancellation
- unknown outcome where applicable

### 6.9 Failure Handling

The system must survive:

- worker crash
- database error
- queue failure
- external provider timeout
- malformed provider response
- duplicate delivery

## 7. Non-Functional Requirements

Define measurable targets.

Suggested initial targets:

- API p95 latency under 300 ms for normal CRUD operations
- task submission returns without waiting for long-running processing
- worker processing has bounded execution time
- tenant isolation has automated regression tests
- all production-like failures are observable
- repeated task submission does not create unintended duplicate work

These are engineering targets, not universal guarantees.

## 11. State Machine

Task status transitions must be explicit.

Valid example:

    PENDING → QUEUED
    QUEUED → RUNNING
    RUNNING → SUCCEEDED
    RUNNING → FAILED
    RUNNING → QUEUED
    QUEUED → CANCELLED
    RUNNING → CANCELLED

Invalid transitions must be rejected.

For example:

    SUCCEEDED → RUNNING

must not silently succeed.

## 12. Invariants

Define invariants before implementation.

Examples:

1. A task belongs to exactly one organization.
2. A user can only access tasks belonging to their organization.
3. A terminal task cannot transition back to an active state.
4. A task cannot have a successful result and terminal failure simultaneously.
5. Idempotency keys cannot map one logical request to unrelated tasks.
6. Retry count cannot exceed the configured limit.
7. Worker processing must have a bounded execution time.

These invariants should be tested.

## 17. Queue Design

The queue decouples task submission from processing.

Flow:

    API
     |
     | create task
     v
    DB
     |
     | enqueue
     v
    Queue
     |
     v
    Worker

Important questions:

- What if DB commit succeeds but enqueue fails?
- What if enqueue succeeds but worker crashes?
- What if a job is delivered twice?
- What if the provider is unavailable?

Do not assume queues eliminate failure.

## 18. Database/Queue Consistency

Analyze the dual-write problem:

    DB transaction
        +
    queue publish

These operations may not succeed atomically.

For the initial project, document the chosen strategy.

Possible approaches:

- transactional outbox
- retryable enqueue
- reconciliation worker

The simplest safe design should be selected based on project scope.

## 19. Worker Design

Worker responsibilities:

1. receive job
2. validate payload
3. claim/transition task
4. execute processing
5. persist result
6. acknowledge job
7. handle failure

Worker code must be safe against duplicate delivery.

## 20. Idempotent Processing

The worker should assume:

> The same job may be delivered more than once.

Possible protections:

- task state checks
- database constraints
- idempotency keys
- atomic state transitions

Avoid relying only on an in-memory flag.

## 21. Retry Policy

Classify failures.

### Retryable

Examples:

- temporary network failure
- dependency timeout
- transient database connectivity

### Non-Retryable

Examples:

- invalid input
- authorization failure
- permanently invalid provider response

Use:

    delay = base × 2^attempt + jitter

with a maximum delay and attempt limit.

## 31. Debugging Runbook

When a task is stuck:

1. identify task ID
2. identify organization
3. inspect task state
4. inspect queue state
5. inspect worker logs
6. inspect attempt count
7. inspect provider calls
8. inspect database state
9. reconstruct timeline
10. determine root cause

Do not manually modify production state without understanding the invariant being preserved.

## 32. Incident Example

### Symptom

Tasks remain in `QUEUED`.

### Investigation

Check:

- queue depth
- worker health
- worker logs
- queue connectivity
- task timestamps

### Possible causes

- worker stopped
- queue unavailable
- malformed job
- worker unable to claim tasks

### Verification

Identify the earliest point where expected state stopped changing.

This is more useful than restarting everything immediately.

## 43. Example 30-Second Explanation

> I built a multi-tenant task-processing backend where API requests create durable task records and enqueue asynchronous work. A worker processes jobs using explicit state transitions, idempotency, bounded retries, and timeouts. PostgreSQL stores authoritative task state, while structured logs and metrics make each task traceable. I intentionally tested duplicate delivery, dependency failure, worker crashes, and cross-tenant access to validate the reliability and security boundaries.

This explanation must be adapted to the actual implementation rather than memorized as a claim.
