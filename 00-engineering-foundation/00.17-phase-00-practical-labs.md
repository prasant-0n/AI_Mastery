# 00.17 — Phase 00 Practical Labs

## 1. Purpose

This chapter turns Phase 00 knowledge into executable engineering practice.

Reading establishes understanding.

Practical labs establish evidence.

Each lab is designed to force the complete engineering loop:

    Understand
      ↓
    Implement
      ↓
    Test
      ↓
    Break
      ↓
    Observe
      ↓
    Debug
      ↓
    Improve
      ↓
    Explain
      ↓
    Document

The goal is not to complete random coding exercises.

The goal is to build engineering instincts that transfer to backend, distributed systems, DevOps, and AI systems.

## 2. Lab Philosophy

Every serious lab should answer:

1. What problem are we solving?
2. What constraints exist?
3. What behavior is expected?
4. What can fail?
5. How do we observe failure?
6. How do we verify correctness?
7. What trade-offs exist?
8. What evidence proves completion?

A lab is incomplete if the implementation works but cannot be tested, debugged, or explained.

## 3. Lab Evidence Standard

Each lab should produce, where applicable:

- source code
- tests
- benchmark results
- logs
- metrics
- diagrams
- debugging notes
- failure reproduction
- ADR
- README
- interview explanation

Recommended evidence structure:

~~~text
lab/
├── README.md
├── src/
├── tests/
├── benchmarks/
├── docs/
│   ├── design.md
│   ├── debugging.md
│   └── decisions.md
└── evidence/
~~~

## 4. Lab Levels

### Level 1 — Implement

Build the basic behavior.

### Level 2 — Verify

Add tests and invariants.

### Level 3 — Break

Intentionally introduce failures.

### Level 4 — Debug

Diagnose failures using evidence.

### Level 5 — Improve

Optimize or redesign.

### Level 6 — Defend

Explain the solution and trade-offs.

### Objective

Build a small program that demonstrates:

- variables

- deterministic behavior

### Requirements

Implement:

- initial state

# 9. Lab 05 — Event Loop Blocking

## Objective

Demonstrate why CPU-bound work can block Node.js request processing.

## Architecture

Create an HTTP server with:

- fast endpoint
- CPU-heavy endpoint

Example:

    GET /health
    GET /compute

## Experiment

Generate concurrent requests to `/health` while repeatedly calling `/compute`.

Measure:

- latency
- throughput
- p50
- p95
- p99

## Break It

Increase computation until health requests become slow.

## Improve It

Move CPU-heavy work to:

- worker threads
- background jobs

Compare results.

## Interview Question

Why does making the function async not automatically make CPU work non-blocking?

# 28. Lab 24 — Safe Refactoring Lab

## Objective

Refactor an intentionally messy module without changing behavior.

Starting point:

- giant function
- duplicated logic
- hidden dependencies
- poor error handling

## Process

1. Add characterization tests.
2. Identify boundaries.
3. Refactor one responsibility at a time.
4. Run tests after each change.
5. Compare behavior.
6. Document the final design.

## Success Criterion

Behavior remains unchanged while maintainability improves.
