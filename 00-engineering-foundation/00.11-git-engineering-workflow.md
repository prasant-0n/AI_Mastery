# 00.11 — Git & Engineering Workflow

## 1. Why This Exists

Git is more than a command-line tool for saving code.

Professional engineering requires a reliable workflow for tracking change, collaborating, reviewing code, recovering from mistakes, releasing safely, investigating regressions, and connecting implementation to engineering work.

The goal is not to memorize Git commands.

The goal is to understand:

> How does a change move safely from an engineer's working tree to a reviewed, tested, traceable production artifact?

## 2. Problem It Solves

Without disciplined version control, teams encounter:

- lost work
- unclear ownership
- accidental overwrites
- unreviewed changes
- difficult rollback
- polluted history
- merge conflicts
- impossible-to-reproduce releases
- unclear incident timelines

Git provides the primitives. Engineering workflow provides the discipline.

## 3. Core Concept

Git records snapshots and relationships between commits.

A simplified workflow:

    Working Tree
         |
       stage
         |
       Index
         |
      commit
         |
    Repository
         |
       push
         |
      Remote

A professional workflow adds:

    change
      ↓
    review
      ↓
    verification
      ↓
    merge
      ↓
    release
      ↓
    observe

## 4. Git's Core Data Model

Important objects include:

- blobs — file contents
- trees — directory snapshots
- commits — snapshots plus metadata and parents
- references — names pointing to commits

Conceptually:

    branch
      |
      v
    commit
      |
      v
    tree
     /   file file

A commit represents a repository state, not merely a changed file.

## 5. Working Tree, Index and Repository

### Working tree

Your current files.

### Index

The staged snapshot prepared for the next commit.

### Repository

The stored history.

This explains commands such as:

- git add
- git commit
- git restore
- git reset

Understanding the model is more useful than memorizing commands.

## 6. Commits

A commit should represent a coherent change.

Good:

    fix: reject expired refresh tokens

Poor:

    update stuff

A useful commit answers:

- what changed?
- why?
- what behavior is affected?

Small coherent commits improve review, debugging, cherry-picking, rollback, and historical understanding.

## 7. Commit Quality

A strong commit usually has:

- one logical purpose
- minimal unrelated changes
- meaningful message
- passing relevant checks
- reviewable diff

Avoid mixing a feature, formatting, dependency upgrades, and unrelated refactoring into one unexplained commit.

## 8. Git Diff as an Engineering Tool

Before committing, inspect:

    git diff

Inspect staged changes:

    git diff --staged

Ask:

1. Did I change what I intended?
2. Did I accidentally include unrelated files?
3. Did credentials appear?
4. Did generated files change?
5. Is the diff understandable?

The diff is one of the most important pre-commit reviews.

## 9. Branches

A branch is a movable reference to a commit.

Conceptually:

    main
      A---B---C
                       D---E
             feature

Branches allow isolated development.

Typical workflow:

    main
      |
    feature branch
      |
    commits
      |
    review
      |
    merge

Branch strategy should match team needs rather than ideology.

## 10. Feature Branches

A feature branch can isolate a change until it is ready.

Example:

    feature/auth-refresh-tokens

Advantages:

- focused review
- isolated work
- safer integration

Risks:

- long-lived branches drift
- conflicts increase
- integration happens late

Prefer short-lived branches when practical.

## 11. Main Branch

The main branch should represent an intentionally maintained state.

Depending on team workflow, it may be:

- always releasable
- continuously deployed
- protected by required checks

Do not assume main automatically means production-ready. Repository policy defines that guarantee.

## 12. Pull Requests

A pull request is a review and integration boundary.

A useful PR communicates:

### Problem

What needs to change?

### Solution

What was implemented?

### Evidence

What tests and checks passed?

### Risk

What could break?

### Rollout

How will it be deployed safely?

### Rollback

How can the change be reversed?

## 13. Code Review

Review should evaluate:

- correctness
- requirements
- security
- maintainability
- performance
- tests
- observability
- failure handling

Review should focus on behavior and risk rather than personal style preferences.

Automate formatting and linting where possible.

## 14. Reviewable Diffs

Large diffs increase cognitive load.

Improve reviewability by:

- keeping changes focused
- separating refactors from features
- avoiding unrelated formatting
- explaining non-obvious decisions
- including tests
- linking relevant design documentation

## 15. Merge Strategies

Common strategies include:

### Merge commit

Preserves branch topology.

### Squash merge

Combines branch work into a single commit.

### Rebase

Replays commits onto another base.

Each strategy affects history differently. The team should use a consistent policy.

## 16. Rebase

Rebase changes the commit ancestry of a branch.

Conceptually:

    A---B---C main
                   D---E feature

after rebase:

    A---B---C---D'---E'

Rebase can create a cleaner linear history.

Important rule:

> Do not casually rewrite shared history.

## 17. Reset vs Revert

### Reset

Moves a reference and can change local history.

Common modes include:

- soft
- mixed
- hard

### Revert

Creates a new commit that reverses an earlier change.

For shared history, revert is often safer.

Understand the difference before using destructive commands.

## 18. Recovering Lost Work

Git often allows recovery through the reflog.

Conceptually:

    branch moved
        |
      reflog
        |
    previous commit

Useful when:

- reset was accidental
- rebase went wrong
- a branch reference moved
- commits appear lost

Recovery depends on retained objects and repository state.

## 19. Merge Conflicts

A conflict means Git cannot automatically determine the intended result.

Workflow:

    update base
       ↓
    conflict
       ↓
    inspect both sides
       ↓
    understand intent
       ↓
    resolve
       ↓
    test
       ↓
    continue

Never resolve conflicts by blindly choosing ours or theirs.

Understand the intended behavior.

## 20. Conflict Prevention

Reduce conflicts through:

- small branches
- frequent integration
- focused files
- avoiding unnecessary formatting changes
- coordinated ownership
- clear module boundaries

Good architecture can reduce Git conflicts because fewer engineers need to edit the same code.

## 21. Tags and Releases

Tags can identify important repository states.

Example:

    v1.0.0

A release should ideally be traceable to:

    source commit
      +
    build artifact
      +
    configuration
      +
    deployment

This supports reproducibility.

## 22. Semantic Versioning

Semantic versioning commonly uses:

    MAJOR.MINOR.PATCH

Conceptually:

- MAJOR — breaking compatibility
- MINOR — backward-compatible functionality
- PATCH — backward-compatible fixes

Not every organization uses strict SemVer, but the compatibility principle remains useful.

## 23. Git and CI/CD

Git events can trigger automation:

    push
      ↓
    CI
      ↓
    lint
      ↓
    test
      ↓
    build
      ↓
    security checks
      ↓
    artifact
      ↓
    deployment

This turns source changes into repeatable delivery.

## 24. Commit Verification

Before pushing:

    git status
    git diff
    git diff --staged

Then run relevant checks:

    lint
    typecheck
    tests
    build

A successful commit does not prove a correct implementation.

## 25. Git Hooks

Hooks can enforce local checks.

Examples:

- formatting
- linting
- secret detection
- commit message validation

Hooks improve local feedback but should not replace CI because local hooks can be bypassed or absent.

## 26. Protected Branches

Protected branches can require:

- pull requests
- successful CI
- approvals
- signed commits where appropriate
- restricted force pushes

Protection reduces accidental destructive changes.

## 27. Secrets

Never commit:

- API keys
- passwords
- private keys
- database credentials
- production tokens

Use:

- environment variables
- secret managers
- CI secret stores
- secure configuration systems

If a secret is committed, removing it from Git history is not sufficient. Assume it may already be exposed and rotate it.

## 28. .gitignore

.gitignore prevents selected files from being tracked.

Typical examples:

    .env
    node_modules/
    dist/
    coverage/
    .venv/
    IDE metadata

Do not blindly ignore files. Generated artifacts required for reproducible builds may need deliberate treatment.

## 29. Git LFS and Large Files

Git is optimized for source history, not arbitrary large binary datasets.

Large files can cause:

- repository growth
- slow clones
- expensive history operations

Options include:

- Git LFS
- object storage
- release artifacts
- external artifact repositories

For AI projects, model weights and datasets generally require specialized storage strategies.

## 30. Monorepo Workflow

A monorepo may contain:

    apps/
    services/
    packages/

Changes can affect multiple components.

Useful practices:

- clear ownership
- package-level tests
- dependency-aware CI
- consistent tooling
- workspace conventions
- affected-project testing

A monorepo does not remove the need for module boundaries.

## 31. Commit Atomicity

A commit should ideally leave the repository in a coherent state.

Avoid committing half of a feature if the resulting state breaks normal development workflows.

For large features, use:

- feature flags
- backward-compatible migrations
- incremental commits
- branch-by-abstraction

## 32. Database Changes and Git

Database migrations should be version-controlled.

Example:

    migrations/
      001_initial.sql
      002_add_users.sql
      003_add_index.sql

Application code and schema changes must be coordinated.

For production systems, think about:

    expand
       ↓
    migrate
       ↓
    deploy
       ↓
    contract

Avoid migrations that require an unsafe all-at-once deployment unless the environment explicitly supports it.

## 33. Git for Incident Investigation

Git history can help answer:

- when did behavior change?
- which commit introduced it?
- who changed the relevant area?
- what tests existed?
- what deployment contained the change?

Useful commands include:

    git log
    git show
    git blame
    git bisect

Git is therefore part of debugging, not merely source storage.

## 34. Git Bisect

git bisect performs a binary search through history to identify the commit that introduced a regression.

Conceptually:

    good ---- bad
          |
        midpoint
        /           good      bad
        ...
          ↓
    suspect commit

This turns a potentially linear investigation into a logarithmic search over commits.

## 35. Git Blame

git blame identifies the commit associated with lines in a file.

Use it to understand history, not to assign personal blame.

A productive workflow is:

    suspicious line
        ↓
    commit
        ↓
    PR/context
        ↓
    design reasoning

History is context.

## 36. Git Worktrees

Worktrees allow multiple working directories connected to one repository.

Useful when:

- reviewing another branch
- investigating an incident
- working on parallel features
- comparing versions

They reduce the need to repeatedly switch the same working directory.

## 37. Reproducible Development

A repository should make it possible for another engineer to understand:

- required runtime
- dependencies
- commands
- environment configuration
- database setup
- tests
- build process

Useful files include:

    README.md
    CONTRIBUTING.md
    runtime configuration
    lockfile
    environment documentation
    CI configuration

Reproducibility is an engineering feature.

## 38. Engineering Journal and ADRs

Git records what changed. It does not always explain why.

Architecture Decision Records can document:

- context
- decision
- alternatives
- consequences

Engineering journals can capture:

- experiments
- failures
- debugging findings
- performance measurements

This is especially useful for complex AI systems.

## 39. Git in AI Engineering

AI repositories often contain:

- prompts
- evaluation datasets
- model configurations
- agent workflows
- tool schemas
- infrastructure
- experiments

Version these deliberately.

A model-output change may result from:

- prompt change
- model version
- retrieval configuration
- system instructions
- tool schema
- dataset change

Traceability matters.

## 40. Data and Model Versioning

Do not assume Git should store every AI artifact.

Consider separate versioning for:

- source code
- prompts
- datasets
- model weights
- evaluation results
- generated artifacts

Record identifiers and provenance so an experiment can be reproduced.

## 41. Branching Strategy Trade-offs

### Trunk-based development

Frequent integration into a shared main branch.

Benefits:

- low drift
- fast feedback
- smaller integration batches

Costs:

- requires strong CI
- incomplete features need safe rollout techniques

### Long-lived feature branches

Benefits:

- isolation

Costs:

- merge drift
- delayed integration
- larger conflicts

Choose based on team workflow and deployment model.

## 42. Trade-offs

| Practice | Benefit | Cost |
|---|---|---|
| Small commits | Review/recovery | More commit management |
| Feature branches | Isolation | Drift |
| Trunk-based workflow | Fast integration | Requires strong CI |
| Rebase | Linear history | History rewriting risk |
| Squash | Clean main history | Loses granular branch commits |
| Strict hooks | Early feedback | Local friction |
| Protected branches | Safety | Slower direct changes |
| Git LFS | Large-file handling | Additional tooling |
| ADRs | Decision context | Documentation effort |

## 43. When to Use

Use Git history actively when:

- debugging regressions
- reviewing changes
- preparing releases
- investigating incidents
- coordinating teams
- reproducing previous states

Use feature branches when changes require isolated review.

Use tags when releases need immutable references.

Use ADRs when a decision has meaningful long-term consequences.

## 44. When NOT to Use

Avoid:

- committing secrets
- force-pushing shared branches casually
- giant unrelated commits
- long-lived branches without integration
- using Git as a database for large mutable datasets
- storing generated dependency directories
- rewriting public history to hide mistakes
- treating commit count as a productivity metric

## 45. Common Mistakes

### Mistake 1 — Commit everything

A commit should contain intentional changes.

### Mistake 2 — Giant commits

Large changes are difficult to review and recover.

### Mistake 3 — Blind conflict resolution

The result may compile while behavior is wrong.

### Mistake 4 — Force push without understanding

History can be lost for collaborators.

### Mistake 5 — Secret removal without rotation

The credential may remain compromised.

### Mistake 6 — Ignoring CI

Local success does not prove repository-wide compatibility.

## 46. Failure Modes

| Failure | Root cause |
|---|---|
| Lost changes | Unsafe reset/rebase |
| Broken main | Missing CI protection |
| Merge conflict explosion | Long-lived branches |
| Secret exposure | Incorrect repository hygiene |
| Irreproducible release | Untracked build inputs |
| Difficult rollback | Unclear release references |
| Regression investigation failure | Poor commit history |
| AI experiment confusion | Missing artifact provenance |

## 47. Security

Git security includes:

- secret prevention
- access control
- protected branches
- signed artifacts where required
- dependency review
- commit provenance
- CI credential protection

Treat source repositories as security-sensitive infrastructure.

For compromised secrets:

1. revoke or rotate them
2. investigate exposure
3. remove unsafe references
4. update consumers
5. document the incident

## 48. Performance

Git performance can degrade with:

- huge repositories
- enormous binary files
- excessive generated artifacts
- deep histories in unsuitable workflows

For large repositories consider:

- sparse checkout
- partial clone
- shallow clone where appropriate
- Git LFS
- repository decomposition when justified

Do not optimize Git performance before identifying the actual bottleneck.

## 49. Scalability

A scalable engineering workflow requires:

    developer
       ↓
    branch/commit
       ↓
    automated checks
       ↓
    review
       ↓
    merge
       ↓
    artifact
       ↓
    deployment
       ↓
    observability

As teams grow, automation becomes increasingly important.

## 50. Cost

Poor Git workflow creates hidden costs:

- review time
- merge conflict time
- incident investigation
- CI usage
- storage
- developer context switching

Workflow discipline reduces repeated operational work.

## 51. Debugging

For a suspected regression:

1. Reproduce the failure.
2. Identify the last known good revision.
3. Identify the first known bad revision.
4. Inspect the diff.
5. Use git bisect if the range is large.
6. Read the relevant PR or commit context.
7. Confirm the causal change.
8. Add a regression test.
9. Fix the implementation.
10. Verify the fix at the current revision.

## 52. Scenario-Based Questions

### Scenario 1 — Broken Main

A developer pushes code that passes locally but breaks the build.

Questions:

1. What controls should have caught this?
2. How should the branch be restored?
3. How would you prevent recurrence?

### Scenario 2 — Accidental Reset

Several local commits disappeared after a reset.

Questions:

1. Where might the commits still be referenced?
2. How can reflog help?
3. What should be avoided before recovery?

### Scenario 3 — Secret Commit

An API key was committed and pushed.

Questions:

1. Is deleting the file sufficient?
2. What should happen to the credential?
3. What repository and CI changes are needed?

### Scenario 4 — Regression

A production endpoint became slow after a recent release.

Questions:

1. How would Git history help?
2. When would you use git bisect?
3. What evidence should be combined with repository history?

### Scenario 5 — AI Experiment

An LLM application's quality dropped after several changes.

Questions:

1. How should prompts and configurations be versioned?
2. How would you identify the causal change?
3. What evaluation artifact should accompany the change?

## 54. Coding / Workflow Exercises

### Exercise 1 — Commit Hygiene

Take an intentionally messy change and split it into coherent commits.

### Exercise 2 — Conflict Resolution

Create two branches modifying overlapping code, merge them, and resolve the conflict correctly.

### Exercise 3 — Regression Investigation

Introduce a known bug across several commits and use git bisect to locate it.

### Exercise 4 — Release Workflow

Create:

    tag
    changelog
    build artifact
    verification record

and document how the release maps back to a commit.

### Exercise 5 — Monorepo CI

Design CI that runs only the relevant checks for changed packages while preserving repository-wide safety checks.

### Exercise 6 — AI Provenance

Create an experiment record containing:

- source commit
- prompt version
- model identifier
- configuration
- evaluation dataset
- result
- conclusion
