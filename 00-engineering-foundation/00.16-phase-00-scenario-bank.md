# 00.16 — Phase 00 Scenario Bank

## 1. Purpose

This scenario bank converts Phase 00 concepts into realistic engineering situations.

The objective is not to memorize solutions.

The objective is to practice:

- identifying the real problem
- separating symptoms from causes
- stating assumptions
- choosing evidence
- reasoning across boundaries
- identifying failure modes
- evaluating trade-offs
- proposing safe changes
- communicating decisions
- defending alternatives

Use each scenario with the Phase 00 learning loop:

    Understand
      ↓
    Investigate
      ↓
    Hypothesize
      ↓
    Implement / Design
      ↓
    Break
      ↓
    Debug
      ↓
    Explain
      ↓
    Defend

## 2. Scenario Response Framework

For every scenario, answer:

1. What do we know?
2. What do we not know?
3. What assumptions are reasonable?
4. What is the failure boundary?
5. What evidence would you collect?
6. What hypotheses are possible?
7. Which hypothesis should be tested first?
8. What is the safest intervention?
9. What trade-offs exist?
10. How would you verify the fix?
11. How would you prevent recurrence?

## 3. Scenario Difficulty Levels

### Level 1 — Concept

Test understanding of one concept.

### Level 2 — Application

Apply a concept to a practical problem.

### Level 3 — Debugging

Find the cause of a failure.

### Level 4 — Design

Construct a solution under constraints.

### Level 5 — Production

Reason about reliability, security, scale, and operations.

### Level 6 — Interview Defense

Defend the decision when requirements change.

# 4. Programming Mental Models

## Scenario 4.1 — Unexpected State Change

A function receives a user object and updates one field. Another part of the application unexpectedly observes the changed value.

Questions:

1. How could shared state cause this?
2. How would you prove object identity is involved?
3. Would you clone the object?
4. What are the costs of deep cloning?
5. Where should ownership of mutation live?

Concepts:

- references
- identity
- mutation
- ownership
- boundaries

## Scenario 4.2 — Non-Deterministic Output

The same input sometimes produces different output.

Questions:

1. What sources of nondeterminism could exist?
2. Could timing, randomness, external state, or concurrency be responsible?
3. How would you reproduce the issue?
4. How would you isolate the source?

## Scenario 4.3 — Hidden Side Effect

A helper named `calculateTotal()` writes to a database.

Questions:

1. Why is this surprising?
2. How does it affect testing?
3. How would you redesign the boundary?
4. When can a side effect inside a function be acceptable?

# 5. Data, Values, Types and References

## Scenario 5.1 — Shared Configuration Mutation

Two modules share a configuration object. One modifies a nested property and another module changes behavior.

Questions:

- How would you diagnose it?
- Would shallow copying solve it?
- When would immutable updates be preferable?
- Where should ownership be defined?

## Scenario 5.2 — Untrusted API Response

A TypeScript API client declares a response as `User`, but the external service sometimes omits fields.

Questions:

1. Why does TypeScript not protect the runtime boundary?
2. Where should validation occur?
3. What should happen when validation fails?
4. Should internal domain objects use the same type as transport data?

## Scenario 5.3 — Queue Schema Change

A producer starts sending:

`{ userId, priority }`

while older workers expect:

`{ userId }`.

Questions:

- What compatibility problems can occur?
- How would you evolve the schema?
- Should the consumer ignore unknown fields?
- When is a breaking change acceptable?

# 6. Memory and Execution

## Scenario 6.1 — Growing API Memory

An API's RSS grows continuously over several hours.

Questions:

1. Is this automatically a memory leak?
2. What memory categories should be investigated?
3. How would you compare heap and RSS?
4. How would you capture evidence?
5. What retention patterns could cause growth?

## Scenario 6.2 — CPU Spike

An endpoint occasionally consumes an entire CPU core.

Questions:

- Is this likely I/O-bound or CPU-bound?
- How would you profile it?
- Could a synchronous loop block Node.js?
- When would worker threads help?

## Scenario 6.3 — Large File Upload

Users upload 2 GB files and the API process crashes.

Questions:

- Is the application buffering the entire file?
- How would streaming change memory behavior?
- Where should size limits be enforced?
- What should happen if the client disconnects?

# 8. Errors and Failure Boundaries

## Scenario 8.1 — Payment Timeout

The API sends a payment request. The provider times out. The client retries.

Questions:

1. Did the payment fail or is the outcome unknown?
2. How could duplicate charging happen?
3. How would idempotency help?
4. Should the API retry automatically?
5. How would reconciliation work?

## Scenario 8.2 — Retry Storm

A dependency becomes slow. Hundreds of requests retry simultaneously.

Questions:

- What feedback loop is occurring?
- How do exponential backoff and jitter help?
- When should retries stop?
- Would a circuit breaker help?

## Scenario 8.3 — Partial Workflow Failure

An order workflow:

    reserve inventory
    → charge payment
    → create shipment

Payment succeeds but shipment creation fails.

Questions:

- What state should the order enter?
- How can compensation work?
- Which operations must be idempotent?
- Where should reconciliation happen?

# 9. Asynchrony, Concurrency and Parallelism

## Scenario 9.1 — Promise.all Failure

Five independent operations run through `Promise.all`. One rejects.

Questions:

- What happens to the returned promise?
- Are other operations necessarily cancelled?
- When would `Promise.allSettled()` be more appropriate?

## Scenario 9.2 — Lost Update

Two requests read the same account balance and both write a new value.

Questions:

- What race condition exists?
- How could a transaction solve it?
- Could optimistic locking help?
- What database invariant must remain true?

## Scenario 9.3 — Queue Growth

A worker processes 50 jobs/minute while producers generate 100 jobs/minute.

Questions:

1. What happens to queue depth?
2. Can adding workers solve the problem?
3. What limits scaling?
4. How should backpressure work?
5. What happens when downstream capacity is reached?

## Scenario 9.4 — CPU-Bound Node Endpoint

A Node.js endpoint performs expensive image processing synchronously.

Questions:

- Why can unrelated requests become slow?
- Would increasing async usage solve CPU saturation?
- Would worker threads help?
- What should happen under overload?

# 10. Complexity and Performance

## Scenario 10.1 — O(n²) Endpoint

An endpoint compares every item with every other item.

Input size increased from 1,000 to 100,000.

Questions:

- What happened to work growth?
- What alternative data structure could reduce repeated work?
- How would you prove the optimization?

## Scenario 10.2 — N+1 Queries

An endpoint loads 1,000 users and executes one database query per user.

Questions:

- What is the query complexity?
- How would you confirm the problem?
- Would a join always be correct?
- Could batching or eager loading help?

## Scenario 10.3 — High p99 Latency

Average latency is 80 ms, but p99 is 4 seconds.

Questions:

- Why can average latency hide the problem?
- What dependencies should be investigated?
- Could queueing or connection pool exhaustion explain the tail?
- Which traces would you inspect?

## Scenario 10.4 — AI Cost Growth

An AI application has stable traffic but token usage grows by 5x.

Questions:

- Could context size be increasing?
- Could retrieval return too many chunks?
- Could agent loops be expanding?
- How would you measure cost per successful task?

# 13. Testing and Verification

## Scenario 13.1 — Flaky Test

A test passes locally but fails randomly in CI.

Questions:

- What nondeterministic dependencies might exist?
- Could timing or shared state be involved?
- How would you reproduce it?
- Should the test simply be retried?

## Scenario 13.2 — Tenant Isolation

A multi-tenant API must never return another tenant's data.

Questions:

- Which tests should verify this?
- Where should tenant identity be enforced?
- Can a single missing filter cause a security incident?
- Should the database provide additional protection?

## Scenario 13.3 — AI Regression

A prompt change improves one benchmark but degrades real user tasks.

Questions:

- What evaluation gap exists?
- How should the test set be expanded?
- How would you separate retrieval, prompting, and model regressions?

Questions:

- Did retrieval change?
- Did chunking change?
- Did embeddings change?
- Did the prompt change?
- Did the model change?
- How would you compare before and after behavior?

- Is independent deployment enough justification?

      ↓

# 23. Architecture Defense Scenarios

## Scenario 23.1 — Interview Challenge

You proposed Redis caching.

Interviewer says:

> What if Redis goes down?

Respond by explaining:

- source of truth
- cache miss behavior
- fallback
- timeout
- stampede protection
- degraded performance

## Scenario 23.2 — Interview Challenge

You proposed a queue.

Interviewer asks:

> Why not call the service directly?

Explain:

- latency
- decoupling
- buffering
- retry behavior
- failure isolation
- delivery semantics

## Scenario 23.3 — Interview Challenge

You proposed microservices.

Interviewer says:

> Why not keep the monolith?

Re-evaluate:

- deployment independence
- scaling boundaries
- team ownership
- operational cost
- network failures
- transaction boundaries

The answer should depend on requirements, not ideology.
