# 00.02 — Data, Values, Types & References

## 1. Why This Exists

Most software bugs eventually involve data.

A variable contains the wrong value. A function receives an unexpected type. Two parts of a program unexpectedly share mutable state. A copy was assumed to be independent but was actually an alias. A database value crossed a boundary without validation.

Understanding data at this level is foundational for JavaScript, TypeScript, Node.js, databases, APIs, distributed systems, caching, serialization, AI pipelines, security, and performance.

The goal is not to memorize language-specific rules. The goal is to understand what information exists, how it is represented, how it moves, and who can change it.

---

## 2. Problem It Solves

Without a strong model of values and references, developers commonly:

- confuse variables with values
- confuse objects with references to objects
- misunderstand mutation
- make incorrect assumptions about copying
- trust TypeScript types at runtime
- pass unsafe data across boundaries
- accidentally share state
- create subtle cache bugs
- misunderstand serialization
- introduce security vulnerabilities through unvalidated data

A useful question is:

> What value exists, where is it stored, who can access it, and can someone else change it?

---

## 3. Core Concept

A useful conceptual model is:

    Variable
       |
       v
     Value

For primitive values:

    x ---> 42

For objects:

    user ---> [object]
                 |
                 +-- name: "Prasanta"
                 +-- role: "developer"

Two variables may refer to the same object:

    a --+
        |
        +---> [shared object]
        |
    b --+

Changing the object through one reference can therefore affect what the other reference observes.

---

## 4. Values

A value is information that a program can operate on.

Examples include numbers, strings, booleans, null, undefined, objects, and arrays.

In JavaScript, common primitive values include:

- string
- number
- bigint
- boolean
- undefined
- symbol
- null

Objects include:

- plain objects
- arrays
- functions
- dates
- maps
- sets
- class instances

The distinction matters because object identity and mutation behave differently from primitive value operations.

---

## 5. Types

A type describes what kind of value an operation expects or produces.

Conceptually:

    Type
      |
      v
    Allowed values
      |
      v
    Allowed operations

A type system makes assumptions explicit and can prevent many invalid operations before execution.

---

## 6. Static Types vs Runtime Reality

TypeScript can express contracts:

    function add(a: number, b: number): number {
      return a + b;
    }

But TypeScript types do not automatically validate external data at runtime.

An HTTP request can still contain:

    { "email": 123 }

even when the application expects:

    { email: string }

A production boundary therefore looks like:

    Untrusted input
          |
          v
       unknown
          |
          v
    Runtime validation
          |
          v
     Trusted data
          |
          v
     Business logic

This distinction is fundamental to backend engineering.

---

## 7. Unknown vs Any

Prefer unknown when data has not yet been validated.

Example:

    function processInput(value: unknown) {
      // Validate before using value.
    }

Using any effectively tells the compiler to stop checking that value.

That may be appropriate at a deliberately isolated boundary, but excessive any usage removes much of TypeScript's value.

A useful production rule is:

> Unknown first, validate second, domain type third.

---

## 8. References and Identity

Consider:

    const a = { count: 1 };
    const b = a;

    b.count = 2;

    console.log(a.count);

The result is 2.

Why?

Because a and b refer to the same object.

Conceptually:

    a --+
        |
        +---> { count: 2 }
        |
    b --+

The important question is not only:

> Do these objects contain the same data?

It is also:

> Are these two references pointing to the same object?

That distinction is called object identity.

---

## 9. Equality

JavaScript has multiple equality behaviors, but strict equality is the normal starting point for application code.

Primitive comparison:

    1 === 1

Object comparison:

    {} === {}

is false because the two object literals create different objects.

With a shared reference:

    const a = {};
    const b = a;

    a === b

is true because both variables refer to the same object.

Object identity matters for caching, memoization, state management, data structures, and change detection.

---

## 10. Mutation

Mutation means changing an existing value or object.

Example:

    const user = {
      name: "A"
    };

    user.name = "B";

The object was mutated.

Mutation is not automatically bad. It becomes dangerous when:

- ownership is unclear
- multiple components share the object
- mutations happen far from the source
- asynchronous operations observe the object at different times
- caches depend on object state
- state changes are not tracked

The correct principle is:

> Make ownership and mutation boundaries explicit.

---

## 11. Immutability

Immutability means an existing value is not changed after creation.

Instead of mutating:

    user.name = "B";

create updated state:

    const updatedUser = {
      ...user,
      name: "B"
    };

Immutability can simplify reasoning, especially when state is shared.

However, blindly copying large structures can increase memory usage and CPU cost.

Immutability is a tool, not a religion.

---

## 12. Shallow Copy vs Deep Copy

A shallow copy copies the outer structure:

    const copy = { ...original };

Nested objects can remain shared.

Conceptually:

    copy ---> new outer object
                  |
                  +---> same nested object

A deep copy recursively creates independent nested structures.

Modern JavaScript provides structuredClone for many data structures:

    const copy = structuredClone(original);

Deep cloning is not universally appropriate. It can consume memory, consume CPU, remove identity, and fail for unsupported values.

Prefer designing clear ownership before reaching for deep cloning.

---

## 13. Ownership

Ownership answers:

> Which component is responsible for changing this data?

For example:

    Request Handler
          |
          v
    Service owns domain transition
          |
          v
    Repository owns persistence interaction

If every component can mutate the same object, reasoning becomes difficult.

Explicit ownership reduces accidental coupling.

---

## 14. Pass-by-Value and Object References

JavaScript is commonly described as pass-by-value.

When an object is passed to a function, the value being passed is a reference to the object.

Example:

    function update(user) {
      user.name = "Changed";
    }

    const user = { name: "Original" };
    update(user);

    console.log(user.name);

The original object changes because the function received a copied reference value that still points to the same object.

Useful mental model:

    Caller
      |
      +-- reference value ---> Object
                               ^
                               |
                    Function parameter

The parameter is not an independent copy of the object.

---

## 15. Serialization

Objects in memory cannot simply be transmitted across every system boundary.

They must often be serialized.

Common formats include:

- JSON
- MessagePack
- Protocol Buffers
- Avro
- custom binary formats

Conceptually:

    In-memory object
          |
          v
      Serialization
          |
          v
       Bytes/text
          |
          v
        Network
          |
          v
     Deserialization
          |
          v
    New in-memory value

Important consequence:

> Serialization normally breaks object identity.

The object on the other side is not the same in-memory object.

---

## 16. JSON Boundaries

JSON is common in APIs because it is simple and widely supported.

But JSON has limitations:

- no native undefined
- no native BigInt
- dates require representation conventions
- functions are not represented
- object identity is not preserved

Therefore an API contract should define representations explicitly.

For example, timestamps should use a documented representation such as an ISO-8601 string.

The receiving application must interpret that representation according to the contract.

---

## 17. Data Across Boundaries

Every boundary changes the trust model.

Examples:

- HTTP
- queues
- databases
- caches
- files
- AI models
- third-party APIs

For each boundary ask:

1. What type arrives?
2. Can it be malformed?
3. Who validates it?
4. Who owns it?
5. Can it be mutated?
6. How is it serialized?
7. What happens when decoding fails?

This is a foundational backend engineering habit.

---

## 18. Type Narrowing

TypeScript can narrow an unknown value using runtime checks.

Example:

    function format(value: unknown): string {
      if (typeof value === "string") {
        return value.trim();
      }

      return String(value);
    }

The runtime check establishes a fact that TypeScript can use.

For complex external data, schema validation is usually preferable.

Conceptually:

    unknown input
        |
        v
    schema validation
        |
        v
    trusted domain object

---

## 19. Domain Types vs Transport Types

Do not automatically treat API payloads as domain objects.

A safer flow is:

    HTTP DTO
       |
       v
    Validation
       |
       v
      Mapping
       |
       v
    Domain Model
       |
       v
    Business Logic

This keeps transport-specific details away from business logic.

For example, an HTTP request might use snake_case while the domain model uses camelCase. The mapping should be explicit rather than allowing transport conventions to leak throughout the system.

---

## 20. Production Considerations

### Input validation

Validate external data before business logic.

### Ownership

Know which component is allowed to modify state.

### Serialization

Define stable representations across boundaries.

### Compatibility

Changing a type can break APIs, queues, database readers, old clients, and background workers.

### Backward compatibility

Distributed systems often contain multiple versions simultaneously. Schema evolution must therefore be deliberate.

---

## 21. Trade-offs

| Choice | Benefit | Cost |
|---|---|---|
| Mutable objects | Fast/simple updates | Hidden shared-state risk |
| Immutable updates | Easier reasoning | More allocations |
| Shallow copy | Cheap | Nested sharing remains |
| Deep copy | Isolation | CPU/memory cost |
| Static typing | Earlier error detection | Type-system complexity |
| Runtime validation | Boundary safety | Runtime overhead |
| JSON | Simple/interoperable | Limited type system |
| Binary formats | Efficiency/schema control | More complexity |

There is no universal winner.

Choose based on the boundary and operational requirements.

---

## 22. When to Use

Use explicit immutable transformations when:

- state is shared
- change tracking matters
- predictable state transitions are valuable
- debugging benefits from historical values

Use mutation when:

- ownership is local and obvious
- performance matters
- the object lifecycle is tightly controlled
- mutation does not leak across boundaries

Use runtime validation when data comes from:

- users
- HTTP
- queues
- files
- databases
- third-party APIs
- AI/model outputs

---

## 23. When NOT to Use

Do not:

- deep-clone everything
- use any for every external payload
- assume TypeScript protects runtime inputs
- create domain models for trivial internal values without a reason
- copy huge objects merely to avoid every mutation
- treat serialization as a transparent operation

The objective is controlled complexity, not maximal ceremony.

---

## 24. Common Mistakes

### Mistake 1 — const means immutable

A const binding can still reference a mutable object.

### Mistake 2 — Confusing shallow and deep copies

Nested references may remain shared.

### Mistake 3 — Trusting TypeScript at runtime

External data does not automatically satisfy compile-time types.

### Mistake 4 — Passing mutable state everywhere

This creates hidden coupling.

### Mistake 5 — Ignoring serialization

A value may change representation at a boundary.

### Mistake 6 — Treating API DTOs as domain models

Transport concerns can leak into business logic.

---

## 25. Failure Modes

| Failure | Root cause |
|---|---|
| Unexpected object mutation | Shared reference |
| Stale state | Incorrect ownership |
| Runtime type error | Missing validation |
| Data corruption | Invalid transformation |
| Queue consumer crash | Invalid serialized payload |
| API compatibility break | Unsafe schema change |
| Memory spike | Excessive copying |
| Security bypass | Trusting unvalidated data |
| Cache inconsistency | Multiple mutable representations |
| Agent/tool error | Unvalidated model-generated arguments |

---

## 26. Security

Data handling is a security boundary.

Never assume:

    typed = trusted

Security-sensitive data should be validated and authorized.

Examples include:

- user IDs
- tenant IDs
- permissions
- file paths
- URLs
- database query parameters
- tool arguments
- model-generated commands

For AI systems:

    Model output
        |
        v
    Treat as untrusted data
        |
        v
       Validate
        |
        v
      Authorize
        |
        v
      Execute

A model generating a valid-looking argument does not make that argument authorized.

---

## 27. Performance

Data representation affects performance.

Potential costs include:

- object allocation
- copying
- serialization
- deserialization
- garbage collection
- network transfer
- parsing

A useful mental model is:

    Data volume × Copy count × Boundary count

As data grows, unnecessary copying becomes increasingly expensive.

Measure before optimizing.

---

## 28. Scalability

At scale, data may move through:

    Client
      |
      v
    API
      |
      v
    Queue
      |
      v
    Worker
      |
      v
    Database
      |
      v
    Cache
      |
      v
    Search / Vector Store
      |
      v
    AI Model

Every hop can transform or serialize data.

Schema contracts therefore become part of system architecture.

Questions to ask:

- Can old consumers read new messages?
- Can new consumers read old messages?
- How large can payloads become?
- Is data duplicated unnecessarily?
- Where is the source of truth?

---

## 29. Cost

Data movement has cost.

Examples:

- CPU for serialization
- memory for copies
- network bandwidth
- database storage
- cache storage
- vector storage
- model input tokens

For AI systems, unnecessary context duplication can directly increase inference cost.

A strong engineer treats data movement as an architectural concern.

---

## 30. Debugging

When unexpected data appears, inspect the lifecycle:

    Source
      |
      v
    Validation
      |
      v
    Transformation
      |
      v
    Storage
      |
      v
    Retrieval
      |
      v
    Transformation
      |
      v
    Output

At each stage ask:

1. What was the value?
2. What type was it?
3. Who owned it?
4. Was it mutated?
5. Was it copied?
6. Was it serialized?
7. Was it validated?
8. Did another component change it?

This often identifies the first point where reality diverged from expectation.

---

## 31. Scenario-Based Questions

### Scenario 1 — Shared Object

Two modules in the same process appear to modify the same configuration object.

Questions:

1. Are they holding the same reference?
2. Who owns the configuration?
3. Should it be immutable?
4. Should each component receive a copy?
5. What is the performance impact?

### Scenario 2 — TypeScript Boundary

An endpoint expects a user object with an email string, but a client sends a numeric email.

Questions:

1. Will TypeScript prevent this?
2. Where should runtime validation happen?
3. What response should the API return?
4. What should reach the business layer?

### Scenario 3 — Queue Schema Evolution

Version 1 publishes a message containing userId and name. Version 2 adds a required field.

Questions:

1. Can old consumers still process messages?
2. Should the field be optional initially?
3. How should message versions be handled?
4. How would you roll out the change safely?

### Scenario 4 — AI Tool Arguments

An LLM generates a user ID and a large monetary amount for a tool call.

Questions:

1. Is valid JSON enough?
2. Is the type enough?
3. Is authorization required?
4. Should the model be allowed to choose the user ID?
5. What validation belongs immediately before execution?
