# 00.13 — Reading Existing Systems

## 1. Why This Exists

Most professional engineering work does not begin with an empty repository.

You inherit:

- existing services
- unfamiliar code
- undocumented behavior
- production constraints
- historical decisions
- technical debt
- tests of varying quality
- dependencies you did not choose

The ability to read an unfamiliar system efficiently is therefore a core engineering skill.

The objective is:

> Build an accurate mental model before making changes.

---

## 2. Problem It Solves

Weak codebase-reading habits lead to:

- changing the wrong layer
- duplicating existing functionality
- breaking hidden assumptions
- introducing incompatible behavior
- missing security controls
- misunderstanding data flow
- wasting time reading irrelevant files

Strong engineers reduce the search space before editing.

---

## 3. Core Concept

Read a system from outside inward.

A useful sequence is:

    Repository
        ↓
    Runtime / deployment
        ↓
    Entry points
        ↓
    Request / event flow
        ↓
    Modules
        ↓
    Data flow
        ↓
    Dependencies
        ↓
    Tests
        ↓
    Failure / observability paths

Do not begin by reading every file.

Start by discovering architecture and execution paths.

---

## 4. Repository Reconnaissance

First identify:

- repository structure
- README
- package manifests
- lockfiles
- runtime versions
- build scripts
- test scripts
- CI configuration
- deployment files
- environment documentation
- database migrations

Typical commands:

    ls
    find
    git status
    git log
    cat package.json

The exact tools vary by language and platform.

---

## 5. Identify the Technology Stack

Determine:

### Runtime

- Node.js
- Python
- JVM
- Go
- etc.

### Framework

- Express
- FastAPI
- Spring
- Django
- etc.

### Data

- PostgreSQL
- MongoDB
- Redis
- object storage

### Infrastructure

- Docker
- Kubernetes
- cloud services
- CI/CD

### AI components

- model providers
- vector database
- embedding service
- agent runtime

Knowing the stack tells you where to look next.

---

## 6. Find Entry Points

Every system has places where execution begins.

Examples:

### HTTP

    server.ts
    app.ts
    routes/

### Worker

    worker.ts
    queue consumer

### CLI

    main()
    command handlers

### Event-driven

    event consumer
    message handler

### AI agent

    runtime
    orchestrator
    workflow entry point

Identify entry points before reading implementation details.

---

## 7. Trace One Real Request

Choose one concrete use case.

Example:

    POST /orders

Trace:

    route
      ↓
    controller
      ↓
    validation
      ↓
    service
      ↓
    repository
      ↓
    database
      ↓
    response

Write the flow down.

This becomes your first mental model.

---

## 8. Trace an Async Workflow

For asynchronous systems:

    API
      ↓
    enqueue
      ↓
    queue
      ↓
    worker
      ↓
    database
      ↓
    event
      ↓
    notification

Identify:

- producer
- queue
- consumer
- retry policy
- acknowledgment
- failure path

---

## 9. Trace an AI Workflow

For an AI application:

    Request
      ↓
    validation
      ↓
    context construction
      ↓
    retrieval
      ↓
    model gateway
      ↓
    tool call
      ↓
    tool result
      ↓
    final response
      ↓
    persistence

Determine which components are deterministic and which are probabilistic.

---

## 10. Read Configuration Early

Configuration often reveals architecture faster than source code.

Look for:

- environment variables
- service URLs
- database connections
- queue names
- feature flags
- model identifiers
- timeouts
- concurrency settings

For example:

    DATABASE_URL
    REDIS_URL
    AI_SERVICE_URL

can immediately reveal system dependencies.

Never expose actual secrets while inspecting configuration.

---

## 11. Read Dependency Manifests

Package manifests reveal:

- framework
- database client
- testing tools
- observability
- authentication
- build tools
- AI SDKs

Look for both runtime and development dependencies.

Dependency names are architectural clues.

---

## 12. Read Tests as Documentation

Tests often describe intended behavior better than comments.

Search for:

- endpoint tests
- service tests
- integration tests
- fixtures
- regression tests

Ask:

> What behavior does this test consider important?

Tests can reveal hidden contracts.

---

## 13. Read Migrations and Schemas

Database schema often reveals domain structure.

Inspect:

- tables
- relationships
- constraints
- indexes
- enums
- audit columns
- tenant identifiers
- migration history

A schema may tell you more about the business model than class names do.

---

## 14. Read the Data Flow

Track important data:

    Input
      ↓
    Validation
      ↓
    Transformation
      ↓
    Storage
      ↓
    Processing
      ↓
    Output

For each boundary ask:

- Is the data validated?
- Is it transformed?
- Is it serialized?
- Is it persisted?
- Is it trusted?
- Is sensitive data exposed?

---

## 15. Identify Ownership

For each important responsibility determine:

- which module owns it
- which module calls it
- which data it owns
- which dependencies it controls

Example:

    Auth
      owns:
        sessions
        credentials
        tokens

    Orders
      owns:
        order lifecycle
        order state

Ownership prevents duplicate business rules.

---

## 16. Identify Public Interfaces

Find:

- HTTP routes
- exported functions
- classes
- service interfaces
- events
- queue messages
- database APIs
- tool schemas

These are the system's meaningful boundaries.

Read boundaries before internal helpers.

---

## 17. Identify External Dependencies

Build a dependency map:

    API
     |
     +--> PostgreSQL
     +--> Redis
     +--> object storage
     +--> payment provider
     +--> AI provider

Then ask:

- Is the dependency synchronous?
- Can it fail?
- Is it retryable?
- Is it idempotent?
- Is it rate-limited?
- Is it observable?

---

## 18. Identify Trust Boundaries

Important boundaries include:

    Browser → API
    API → database
    Service → service
    Application → provider
    Agent → tool

At each boundary inspect:

- authentication
- authorization
- validation
- serialization
- rate limits
- tenant context

Reading a codebase without identifying trust boundaries is dangerous.

---

## 19. Identify State

Determine where state lives.

Possible locations:

- local memory
- process state
- Redis
- database
- object storage
- browser
- queue
- external provider

Ask:

> What happens if this process restarts?

This often reveals hidden state dependencies.

---

## 20. Identify Concurrency

Look for:

- async functions
- workers
- queues
- scheduled jobs
- locks
- transactions
- shared mutable state
- retries

Ask:

> Can two operations affect the same state simultaneously?

If yes, investigate the consistency mechanism.

---

## 21. Identify Failure Paths

For every important dependency ask:

    What happens if it fails?

Examples:

- database unavailable
- Redis unavailable
- provider timeout
- queue publish failure
- malformed event
- worker crash

Trace:

    failure
      ↓
    propagation
      ↓
    recovery
      ↓
    retry
      ↓
    final outcome

---

## 22. Read Error Handling

Search for:

- try/catch
- error middleware
- error classes
- error codes
- retry logic
- circuit breakers
- fallback behavior

Determine whether errors are:

- translated
- swallowed
- logged
- retried
- exposed to callers

Error handling reveals system assumptions.

---

## 23. Read Observability

Look for:

- logs
- metrics
- traces
- health checks
- dashboards
- alerts

Determine:

- what is observable
- what is missing
- which identifiers connect events
- whether failures can be reconstructed

A system that cannot explain its own failures is difficult to operate.

---

## 24. Build a Dependency Graph

Represent major components:

    API
     |
     +--> Auth
     +--> Orders
     |      |
     |      +--> PostgreSQL
     |
     +--> Redis
     |
     +--> Queue
            |
          Worker
            |
          AI Service

Then identify:

- cycles
- high fan-out components
- central dependencies
- likely failure hotspots

---

## 25. Build a Data Ownership Map

Example:

| Data | Owner | Storage | Consumers |
|---|---|---|---|
| User | Auth/Users | PostgreSQL | Orders, Billing |
| Session | Auth | Redis/DB | API |
| Order | Orders | PostgreSQL | Billing |
| Job | Worker system | Queue | Workers |
| Document | Documents | Object store/DB | RAG |

Ownership helps prevent accidental coupling.

---

## 26. Read History

Use Git history to understand why code looks unusual.

Useful tools:

    git log
    git show
    git blame

Questions:

- Why was this abstraction introduced?
- Was this a bug fix?
- Is this compatibility code?
- Is this temporary?
- Which incident caused this behavior?

Do not remove unfamiliar code simply because it looks unnecessary.

---

## 27. Find Recent Changes

When debugging or extending a system, inspect recent history.

Recent changes may explain:

- regressions
- new dependencies
- altered behavior
- schema changes
- configuration changes

Combine history with runtime evidence.

---

## 28. Search Before Reading

Search is often more efficient than browsing directories manually.

Search for:

- function names
- route paths
- environment variables
- database tables
- event names
- error codes
- feature flags

Example:

    search "createOrder"

Then trace callers and callees.

---

## 29. Read Vertical Slices

Instead of reading one entire layer:

    all controllers
    all services
    all repositories

read one complete feature:

    route
      ↓
    controller
      ↓
    service
      ↓
    repository
      ↓
    schema
      ↓
    tests

Vertical reading builds a usable end-to-end mental model faster.

---

## 30. Read Horizontal Concerns Later

After understanding one vertical slice, inspect cross-cutting concerns:

- authentication
- authorization
- logging
- validation
- error handling
- transactions
- caching
- observability

This reveals shared infrastructure without overwhelming the initial mental model.

---

## 31. Architecture Inference

Sometimes documentation is incomplete.

Infer architecture from evidence:

- imports
- dependency graph
- runtime entry points
- deployment configuration
- database schema
- network calls
- queues
- tests

Clearly distinguish:

    documented fact
        vs
    observed behavior
        vs
    inferred architecture

Do not present an inference as documented truth.

---

## 32. Identify Architectural Invariants

Examples:

- every request requires tenant context
- orders must belong to an organization
- events are immutable
- only workers consume a queue
- database writes occur inside transactions
- model calls pass through a gateway

These invariants are critical when modifying the system.

---

## 33. Change Safely

Before changing code:

1. identify the owning module
2. trace consumers
3. identify tests
4. identify external contracts
5. identify migration requirements
6. identify observability
7. identify rollback strategy

Then make the smallest coherent change.

---

## 34. Working in Unfamiliar Code

A practical sequence:

### Pass 1 — Orientation

Understand repository and runtime.

### Pass 2 — Execution

Trace one real workflow.

### Pass 3 — Dependencies

Map external systems.

### Pass 4 — State

Find persistence and mutable state.

### Pass 5 — Failure

Trace error paths.

### Pass 6 — Tests

Identify behavioral guarantees.

### Pass 7 — History

Understand unusual decisions.

### Pass 8 — Change

Modify only after the model is sufficient.

---

## 35. Production Considerations

Reading production code requires additional attention to:

- backward compatibility
- migrations
- traffic patterns
- feature flags
- deployment strategy
- observability
- security
- tenant isolation
- failure handling
- operational ownership

The code is only one part of the system.

---

## 36. Trade-offs

| Reading strategy | Benefit | Cost |
|---|---|---|
| Read everything | Broad context | Extremely slow |
| Read entry points | Fast orientation | May miss hidden behavior |
| Vertical slice | Fast mental model | Requires later broader review |
| Tests first | Behavioral context | Tests may be incomplete |
| History first | Historical context | Can overwhelm early investigation |
| Dependency graph | Architecture clarity | Requires initial mapping |

---

## 37. When to Use

Use vertical-slice reading when:

- joining an unfamiliar project
- fixing one feature
- implementing a targeted change

Use dependency mapping when:

- debugging distributed behavior
- planning architecture changes

Use history when:

- code seems unusual
- behavior changed recently
- removing an abstraction

Use tests as documentation when:

- requirements are unclear
- implementation and docs disagree

---

## 38. When NOT to Use

Avoid:

- reading every file sequentially
- changing code before understanding callers
- trusting comments over executable behavior without verification
- deleting unfamiliar code without history/context
- assuming module names accurately describe ownership
- treating inferred architecture as documented fact

---

## 39. Common Mistakes

### Mistake 1 — Starting with implementation details

You lose the architectural context.

### Mistake 2 — Reading only the file to be changed

Hidden consumers may break.

### Mistake 3 — Ignoring configuration

Runtime behavior may differ from source assumptions.

### Mistake 4 — Ignoring tests

You miss explicit behavioral contracts.

### Mistake 5 — Ignoring history

You may remove compatibility or incident-driven logic.

### Mistake 6 — Ignoring data ownership

You can introduce cross-module coupling.

---

## 40. Failure Modes

| Failure | Cause |
|---|---|
| Wrong layer changed | Poor architecture understanding |
| Regression | Missed consumer |
| Security bug | Missed trust boundary |
| Data corruption | Missed ownership/invariant |
| Duplicate logic | Existing functionality overlooked |
| Migration failure | Schema not inspected |
| Runtime failure | Configuration ignored |
| Incorrect refactor | Historical context ignored |

---

## 41. Security

When reading an unfamiliar system, identify:

- authentication entry points
- authorization checks
- tenant boundaries
- secret handling
- input validation
- external integrations
- privileged operations

Never assume a missing visible check means no security exists; trace middleware, framework configuration, and shared policies.

---

## 42. Performance

Identify likely performance-sensitive paths:

- hot endpoints
- database queries
- loops over large collections
- serialization
- network calls
- model invocations
- queue processing

Do not optimize solely from code appearance.

Trace real workload and measurements.

---

## 43. Scalability

Ask:

- What happens when traffic doubles?
- What happens when data grows 100x?
- Which component scales independently?
- Which component is a bottleneck?
- Which state is shared?
- Which operations require coordination?

Code structure alone does not reveal scalability.

Combine architecture with workload assumptions.

---

## 44. Cost

When understanding a production system, identify expensive operations:

- database queries
- network calls
- storage
- compute
- model calls
- token usage
- queue processing

A good mental model includes:

    correctness
    performance
    reliability
    security
    cost

---

## 45. Debugging

When a bug appears in an unfamiliar codebase:

1. Reproduce it.
2. Trace the failing entry point.
3. Follow data and control flow.
4. Identify the first incorrect state.
5. Inspect relevant dependencies.
6. Read tests.
7. Read recent history.
8. Form a hypothesis.
9. Make the smallest fix.
10. Add regression coverage.

---

## 46. Scenario-Based Questions

### Scenario 1 — New Repository

You join a 300,000-line backend repository.

Questions:

1. What do you inspect first?
2. How do you find entry points?
3. How do you avoid reading everything?
4. How do you build the first architecture map?

### Scenario 2 — Unknown Endpoint

You receive a bug report for:

    POST /api/orders

Questions:

1. How do you trace the endpoint?
2. Which dependencies do you inspect?
3. Which tests do you search for?
4. How do you identify ownership?

### Scenario 3 — Strange Compatibility Code

You find an unusual adapter that appears unnecessary.

Questions:

1. Should you remove it?
2. What history should you inspect?
3. What consumers could depend on it?
4. What tests would give confidence?

### Scenario 4 — AI Service

A repository contains API, retrieval, agent, and model-provider modules.

Questions:

1. How do you trace one user request?
2. Where should provider-specific behavior live?
3. How do you distinguish deterministic and probabilistic stages?
4. What observability would you expect?

### Scenario 5 — Multi-Tenant Bug

A query returns another organization's record.

Questions:

1. Where would you trace tenant context?
2. Which layers must enforce isolation?
3. Which schema constraints should you inspect?
4. What regression test should exist?
