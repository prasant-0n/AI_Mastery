# 00.01 — Programming Mental Models

## 1. Why This Exists

Before learning frameworks, databases, AI systems, or distributed architecture, an engineer needs a correct mental model of what a program actually does.

Weak engineering reasoning usually starts with syntax:

> "Which API should I call?"

Strong engineering reasoning starts with:

> "What state exists, what transformation occurs, what boundary is crossed, and what can fail?"

This chapter establishes that foundation.

---

## 2. Problem It Solves

Without a mental model of execution, developers tend to:

- memorize syntax without understanding behavior
- confuse state with data
- misunderstand side effects
- debug symptoms instead of causes
- couple unrelated responsibilities
- struggle to reason about asynchronous systems
- make incorrect assumptions about performance
- give weak system-design answers

The goal is to move from **code-first thinking** to **behavior-first thinking**.

---

## 3. Core Concepts

### 3.1 Program

A program is a set of instructions and data that describes how a computer should perform a task.

At a high level:

```text
Input
  ↓
Processing
  ↓
State changes
  ↓
Output
```

A real application adds external boundaries:

```text
User
 ↓
Application
 ↓
Business Logic
 ↓
Database / Network / Files / External Services
 ↓
Result
```

---

### 3.2 State

State is information about the current condition of a system.

Examples:

- authenticated user
- shopping cart
- database row
- active job
- cache entry
- agent conversation state
- queue position

A useful model is:

```text
Current State + Input
        ↓
    Computation
        ↓
    New State + Output
```

This model becomes extremely important later for databases, distributed systems, agents, and stateful workflows.

---

### 3.3 Input

Input is information entering a computation.

Examples:

- HTTP request
- function argument
- CLI argument
- message from a queue
- database record
- file
- environment variable
- model output

Never assume input is trustworthy merely because it came from another part of your application.

---

### 3.4 Output

Output is information produced by a computation.

Examples:

- function return value
- HTTP response
- database write
- event
- log
- generated file
- AI response

Output may itself become input to another component.

---

### 3.5 Transformation

Most software can be understood as transformations:

```text
Input → Transformation → Output
```

For example:

```text
HTTP request
    ↓
Validation
    ↓
Business logic
    ↓
Database operation
    ↓
Response
```

Breaking a system into transformations makes debugging and architecture easier.

---

## 4. Deterministic vs Non-Deterministic Behavior

### Deterministic

The same relevant input and state produce the same output.

```text
f(x) = y
```

Example:

```js
function add(a, b) {
  return a + b;
}
```

For the same values, the result is predictable.

### Non-deterministic

The result can vary because external state, timing, randomness, concurrency, or probabilistic behavior affects execution.

Examples:

- random number generation
- race conditions
- network responses
- current time
- distributed systems
- LLM output

This distinction becomes critical in AI engineering.

An LLM-based application is not simply:

```text
input → guaranteed output
```

It is closer to:

```text
input + context + model + parameters + external state
                  ↓
             probabilistic output
```

Therefore AI systems require evaluation and observability in addition to conventional testing.

---

## 5. Pure vs Impure Operations

A pure function:

- depends only on its inputs
- produces an output
- does not modify external state

Example:

```js
function multiply(a, b) {
  return a * b;
}
```

An impure operation interacts with external state.

Examples:

```js
await db.users.insertOne(user);
```

```js
await fetch("https://example.com");
```

```js
console.log("hello");
```

Pure operations are generally easier to:

- test
- reason about
- cache
- reuse
- parallelize

Impure operations are necessary in real systems, but should be placed behind clear boundaries.

---

## 6. Side Effects

A side effect is an observable change outside the local computation.

Examples:

- database writes
- network requests
- file writes
- logging
- modifying shared state
- sending an email
- publishing an event
- calling an AI model

A useful architecture separates:

```text
Pure business logic
        ↓
Explicit side-effect boundary
        ↓
External system
```

This improves testability and debugging.

---

## 7. Abstraction

Abstraction means hiding implementation details behind a useful interface.

Example:

```js
await userRepository.findById(userId);
```

The caller doesn't need to know whether the repository uses:

- PostgreSQL
- MongoDB
- Redis
- an HTTP service

The abstraction is valuable only when the boundary represents a meaningful responsibility.

### Bad abstraction

Creating layers simply because:

> "Production projects need many folders."

### Good abstraction

Creating a boundary because:

> "This responsibility changes independently and has a clear contract."

---

## 8. Decomposition

Complex systems become manageable when divided into smaller responsibilities.

Instead of:

```text
handleEverything()
```

prefer:

```text
Request
 ↓
Validate
 ↓
Authenticate
 ↓
Authorize
 ↓
Execute business operation
 ↓
Persist
 ↓
Respond
```

Each step should have a clear responsibility.

This principle scales from a function to a distributed system.

---

## 9. Boundaries

A boundary separates responsibilities or systems.

Important boundaries include:

### Function boundary

```text
Function A → Function B
```

### Module boundary

```text
Auth Module → User Module
```

### Process boundary

```text
API Process → Worker Process
```

### Network boundary

```text
Application → PostgreSQL
```

### Trust boundary

```text
Untrusted user input → Trusted internal system
```

### Tenant boundary

```text
Tenant A data ≠ Tenant B data
```

### AI boundary

```text
Application → Model
```

The farther apart two components are, the more explicitly their contract, failure behavior, and security model must be defined.

---

## 10. A General System Model

A useful general model is:

```text
                    ┌──────────────┐
Input ─────────────→│  Processing  │─────────────→ Output
                    └──────┬───────┘
                           │
                           ↓
                         State
                           │
                  ┌────────┴────────┐
                  ↓                 ↓
              Side Effects      External Systems
```

When debugging a system, ask:

1. What was the input?
2. What state existed?
3. What transformation occurred?
4. What side effects happened?
5. What output was produced?
6. Which boundary failed?

This becomes a reusable debugging framework.

---

## 11. Production Perspective

A production system is not just code that works on a happy path.

You must consider:

- invalid input
- missing dependencies
- timeouts
- partial failures
- concurrency
- retries
- duplicate operations
- security boundaries
- resource limits
- observability
- recovery

For example:

```text
Request
 ↓
Validation ✓
 ↓
Business logic ✓
 ↓
Database
 ↓
Timeout ✗
```

The correct question is not merely:

> "Why did the request fail?"

It is:

> "What state did the system reach before the failure, and can retrying safely repeat the operation?"

That question leads directly to idempotency and distributed-systems thinking.

---

## 12. Trade-offs

Every abstraction has a cost.

### More abstraction

Advantages:

- separation
- testability
- replaceability

Costs:

- more code
- more indirection
- harder debugging
- potentially slower development

### More state

Advantages:

- faster access
- persistence
- richer workflows

Costs:

- consistency problems
- synchronization
- recovery complexity

### More distributed components

Advantages:

- independent scaling
- isolation
- team ownership

Costs:

- network failures
- operational complexity
- observability requirements
- deployment complexity

A mature engineer asks:

> "What complexity am I introducing, and what problem does it solve?"

---

## 13. When to Use

Use decomposition and explicit boundaries when:

- responsibilities change independently
- different teams own components
- security boundaries matter
- scaling requirements differ
- failure isolation is required
- testing becomes difficult without separation

---

## 14. When NOT to Use

Do not introduce:

- microservices
- abstractions
- queues
- event buses
- frameworks
- repositories
- design patterns

merely because they sound professional.

For a small application, a modular monolith may be more appropriate than multiple services.

Complexity is a liability unless it buys something valuable.

---

## 15. Common Mistakes

### Mistake 1 — Confusing code with behavior

Reading code is not enough. Understand the state transitions.

### Mistake 2 — Treating external systems as reliable

Databases, APIs, queues, and AI providers can fail.

### Mistake 3 — Hiding side effects

A function that looks pure but secretly modifies shared state is difficult to reason about.

### Mistake 4 — Over-abstraction

Layers without meaningful responsibilities create indirection rather than architecture.

### Mistake 5 — Ignoring state

Many production bugs are state-management bugs.

### Mistake 6 — Assuming deterministic behavior

Timing, concurrency, randomness, network responses, and AI models can produce different results.

---

## 16. Failure Modes

| Failure | Root concept |
|---|---|
| Duplicate database write | State + retries |
| Race condition | Shared state + concurrency |
| Stale cache | Multiple state representations |
| Lost event | Boundary + delivery semantics |
| Infinite retry loop | Failure handling |
| AI hallucination | Probabilistic output |
| Cross-tenant data leak | Trust/data boundary |
| Memory leak | Resource lifetime |
| Hidden side effect | Poor abstraction |
| Slow request | Transformation bottleneck |

---

## 17. Security

Every boundary should be treated according to its trust level.

Never assume:

```text
Internal = Trusted
```

Internal services can be compromised or misconfigured.

Important questions:

- Who controls the input?
- What data is accessible?
- What permissions are required?
- What happens if the component is compromised?
- Can the operation cross a tenant boundary?
- Is the action auditable?

These questions become critical in AI agents and tool execution.

---

## 18. Performance

Performance reasoning starts with identifying the dominant cost.

Possible bottlenecks:

- CPU
- memory
- disk
- database
- network
- external API
- serialization
- synchronization
- model inference

Do not optimize based on intuition alone.

Use:

```text
Measure
 ↓
Identify bottleneck
 ↓
Change
 ↓
Measure again
```

## 19. Scenario-Based Questions

### Scenario 1 — Duplicate Payment

A payment API times out after the payment provider accepted the request. The client retries.

**Questions:**

1. What state transitions can occur?
2. How can duplicate payment be prevented?
3. Where should idempotency be enforced?
4. What should be persisted?
5. What happens if the idempotency record itself fails?

**Pattern:** Idempotency + external side-effect boundary.

---

### Scenario 2 — Cross-Tenant Data

An AI assistant returns information belonging to another organization.

**Questions:**

1. Which boundary failed?
2. Should tenant filtering happen before or after vector retrieval?
3. Where should authorization be enforced?
4. How would you test for recurrence?

**Pattern:** Tenant isolation + authorization + retrieval constraints.

---

### Scenario 3 — Slow API

An endpoint changed from 200 ms to 8 seconds.

**Questions:**

1. What do you measure first?
2. How do you separate application latency from database/network latency?
3. What evidence would distinguish CPU saturation from a slow query?
4. Would adding a cache be your first action?

**Pattern:** Observe before changing architecture.

---

### Scenario 4 — Agent Loop

An agent repeatedly calls the same tool.

**Questions:**

1. Is the problem the model, tool result, state, or orchestration?
2. How do you detect loops?
3. Should you use a maximum-step budget?
4. What should happen when the budget is exceeded?

**Pattern:** Runtime guardrails + bounded execution.

---

### Scenario 5 — Redis Failure

Redis becomes unavailable while serving as a cache.

**Questions:**

1. Should the application fail?
2. Can traffic fall through to PostgreSQL?
3. Could fallback create a database stampede?
4. How would you protect PostgreSQL?

**Pattern:** Graceful degradation + cache stampede protection + bulkhead/circuit breaker concepts.

### Exercise 1

### Exercise 2

### Exercise 3

- transformations
- side effects

## 22. Debugging Drill

Given:

```text
POST /orders
   ↓
validate
   ↓
create order
   ↓
charge payment
   ↓
send email
   ↓
response
```

The client reports:

> "The request failed, but I was charged."

Your investigation should identify:

1. Which operation succeeded?
2. Which operation failed?
3. What state was persisted?
4. Can the request be retried?
5. How should payment idempotency work?
6. Should email be part of the synchronous transaction?
7. What events should be emitted?
8. How would you prevent the same class of incident?

Do not immediately rewrite the code. First reconstruct the state transition.
