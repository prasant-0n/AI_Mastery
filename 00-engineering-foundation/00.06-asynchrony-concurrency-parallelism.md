# 00.06 — Asynchrony, Concurrency & Parallelism

## 1. Why This Exists

Modern software rarely executes as one simple sequence.

Backend applications wait for databases, APIs, files, queues, and users. Workers process many jobs. Servers handle many requests at the same time. AI systems stream model output while performing retrieval and tool calls.

To reason about these systems, you must distinguish three concepts:

- **Asynchrony** — work can continue without waiting for an operation to finish.
- **Concurrency** — multiple tasks make progress during overlapping periods.
- **Parallelism** — multiple computations execute at the same time on separate execution resources.

These concepts are related but not interchangeable.

---

## 2. Problem It Solves

Without a correct concurrency model, developers commonly:

- confuse asynchronous execution with parallel execution
- introduce race conditions
- accidentally serialize independent work
- overload dependencies with excessive concurrency
- create deadlocks
- misuse Promise.all
- block event loops
- lose errors from background tasks
- create unbounded queues
- corrupt shared state
- design unsafe retry behavior

The core question is:

> Which work can overlap safely, which work must remain ordered, and what resources limit the amount of overlap?

---

## 3. Core Concepts

### Asynchrony

An operation is asynchronous when the caller can continue without waiting for that operation to finish.

Conceptually:

    Start operation A
          |
          +----> continue other work
          |
          v
    A completes later

### Concurrency

Two or more tasks are in progress during overlapping time periods.

    Task A: █████████
    Task B:     █████████
    Task C:          ███████

They may still execute on one CPU resource through interleaving.

### Parallelism

Two or more computations execute simultaneously.

    CPU 1: █████████
    CPU 2: █████████

Parallelism requires multiple execution resources or suitable hardware/runtime support.

---

## 4. Concurrency vs Parallelism

Consider:

    Task A
    Task B

Concurrency means the system can manage both tasks during the same period.

Parallelism means A and B actually execute simultaneously.

A single-threaded event loop can provide substantial concurrency for I/O-bound work without executing JavaScript instructions in parallel.

This distinction is fundamental to Node.js engineering.

---

## 5. Synchronous Execution

Synchronous execution generally means the caller waits for the current operation before continuing.

Example:

    const data = readFileSync(path);
    process(data);

Conceptually:

    read
      |
      v
    finish
      |
      v
    process

Synchronous APIs can be appropriate in controlled contexts, but blocking operations on request-serving paths can reduce throughput.

---

## 6. Asynchronous Execution

Example:

    const data = await readFile(path);
    process(data);

The exact runtime behavior is more sophisticated than simply "the thread sleeps."

The important model is:

    Start I/O
       |
       v
    execution can yield
       |
       v
    other work progresses
       |
       v
    I/O completes
       |
       v
    continuation resumes

Asynchrony allows resources to be used for other work while external operations are pending.

---

## 7. Event Loop Mental Model

A simplified Node.js model:

    JavaScript execution
          |
          v
      Event loop
          |
          +---- timers
          +---- I/O readiness
          +---- callbacks
          +---- promise continuations
          |
          v
    JavaScript execution

This is intentionally simplified.

Node.js also relies on operating-system facilities and libuv for asynchronous operations, and some work can involve thread pools or other execution resources.

The key principle is:

> The event loop coordinates JavaScript execution and asynchronous progress; it does not make CPU-heavy JavaScript parallel.

---

## 8. Promise States

A promise represents an eventual result.

Conceptually:

    pending
      |
      +----> fulfilled
      |
      +----> rejected

Example:

    const result = await operation();

The caller receives either:

- a successful value
- an error

Promises are therefore a control-flow abstraction for asynchronous results.

---

## 9. Sequential Async Operations

Example:

    const user = await getUser(id);
    const account = await getAccount(user.accountId);
    const history = await getHistory(account.id);

This is correct when each operation depends on the previous result.

The dependency graph is:

    getUser
       |
       v
    getAccount
       |
       v
    getHistory

Do not parallelize operations merely because Promise.all exists.

---

## 10. Concurrent Async Operations

Suppose these are independent:

    const [users, products] = await Promise.all([
      getUsers(),
      getProducts()
    ]);

Conceptually:

    getUsers  ────────+
                      |
    getProducts ──────+----> combine results

This can reduce total latency.

But it increases simultaneous load on the dependencies.

Therefore concurrency is a resource decision, not merely a syntax decision.

---

## 11. Promise.all Failure Semantics

Promise.all rejects when one of its input promises rejects.

Example:

    await Promise.all([
      operationA(),
      operationB(),
      operationC()
    ]);

If B fails, the combined operation rejects.

However, already-started operations do not automatically become undone.

This is important.

    A starts ✓
    B starts ✓
    C starts ✓
    B fails ✗

A and C may still be running or may already have produced side effects.

Promise.all is not a distributed transaction.

---

## 12. Promise.allSettled

When independent operations should all be observed:

    const results = await Promise.allSettled([
      operationA(),
      operationB(),
      operationC()
    ]);

This gives each result individually.

Useful for:

- batch processing
- independent enrichment
- reporting
- best-effort workflows

It should not be used to hide failures that are actually required for correctness.

---

## 13. Race Conditions

A race condition occurs when correctness depends on timing or ordering between concurrent operations.

Example:

    initial balance = 100

    Request A reads 100
    Request B reads 100

    A writes 50
    B writes 20

The final state may lose one update.

Conceptually:

    Shared state
       ^
       |
    A ---+
         |
    B ---+

The problem is not simply "two requests exist."

The problem is unsafe concurrent access to shared state.

---

## 14. Shared Mutable State

Shared mutable state increases concurrency complexity.

Example:

    let counter = 0;

    async function increment() {
      const current = counter;
      await delay();
      counter = current + 1;
    }

Two calls can observe the same current value and overwrite each other.

Safer approaches may include:

- atomic operations
- database constraints
- transactions
- locks
- serialized processing
- immutable state
- ownership transfer

Choose based on the actual boundary.

---

## 15. Atomicity

An operation is atomic when it appears indivisible from the relevant observer's perspective.

Example:

    UPDATE accounts
    SET balance = balance - 10
    WHERE id = ...

Database systems provide mechanisms for atomic state transitions.

Atomicity can eliminate classes of race conditions without application-level locks.

---

## 16. Locks

A lock restricts concurrent access to a shared resource.

Conceptually:

    acquire lock
       |
       v
    modify state
       |
       v
    release lock

Locks can protect correctness.

But they can also introduce:

- contention
- deadlocks
- reduced throughput
- operational complexity

A lock is not automatically the best solution.

---

## 17. Deadlocks

A deadlock occurs when tasks wait indefinitely for resources held by each other.

Example:

    Task A holds Lock 1
    Task B holds Lock 2

    A waits for Lock 2
    B waits for Lock 1

    A → waiting
    B → waiting

Neither can proceed.

Deadlocks can be reduced through:

- consistent lock ordering
- timeouts
- smaller critical sections
- avoiding unnecessary locks

---

## 18. Critical Sections

A critical section is code that accesses shared state requiring synchronization.

Example:

    acquire()
      |
      v
    update shared state
      |
      v
    release()

Keep critical sections as small as practical.

Long critical sections increase contention and reduce concurrency.

---

## 19. Backpressure

If producers create work faster than consumers can process it:

    Producer rate > Consumer rate
          |
          v
       Queue grows
          |
          v
    Memory / latency pressure
          |
          v
        Failure

Backpressure means controlling production so the system does not overwhelm downstream capacity.

Mechanisms include:

- bounded queues
- concurrency limits
- rate limiting
- flow control
- load shedding
- streaming backpressure

Backpressure is essential for scalable systems.

---

## 20. Concurrency Limits

This is dangerous:

    await Promise.all(
      items.map(processItem)
    );

If items contains 100,000 elements, you may create an enormous amount of concurrent work.

A safer architecture uses bounded concurrency:

    queue
      |
      +--> worker 1
      +--> worker 2
      +--> worker 3
      +--> worker 4

The number of simultaneous operations is controlled.

Concurrency limits protect:

- CPU
- memory
- database connections
- network dependencies
- external APIs
- model providers

---

## 21. Rate Limiting vs Concurrency Limiting

### Rate limit

Controls how many operations start within a time period.

Example:

    100 requests / second

### Concurrency limit

Controls how many operations are active simultaneously.

Example:

    max 20 active requests

They solve different problems.

A slow dependency may require concurrency control even when the request rate is acceptable.

---

## 22. Queues

Queues decouple producers and consumers.

    Producer
       |
       v
      Queue
       |
       v
    Consumer

Benefits:

- smoothing traffic spikes
- asynchronous processing
- retry support
- workload isolation
- independent scaling

Costs:

- additional infrastructure
- eventual consistency
- delayed completion
- duplicate delivery concerns
- operational complexity

---

## 23. Worker Pools

A worker pool uses a fixed number of workers.

    Queue
      |
      +--> Worker 1
      +--> Worker 2
      +--> Worker 3
      +--> Worker 4

This provides bounded parallelism.

Worker pools are useful for:

- CPU-heavy jobs
- background processing
- image generation
- document processing
- AI pipelines
- database batch work

---

## 24. Node.js Worker Threads

Node.js can use worker threads for CPU-intensive JavaScript.

Conceptually:

    Main thread
        |
        +----> Worker 1
        +----> Worker 2

This can prevent CPU-heavy work from monopolizing the main JavaScript execution path.

Worker threads introduce:

- communication overhead
- memory cost
- lifecycle management
- serialization or transferable data considerations

Use them when measurement shows CPU work is a bottleneck.

---

## 25. Processes vs Threads

### Process

Benefits:

- stronger isolation
- independent memory
- failure containment

Costs:

- higher communication overhead
- more resource usage

### Thread

Benefits:

- shared process memory
- lower communication cost in some cases
- useful for parallel computation

Costs:

- shared-state complexity
- weaker isolation

Containers and microservices add another process/network boundary.

---

## 26. Parallelism and CPU Cores

If a machine has multiple CPU cores, truly parallel CPU work can occur when work is distributed across suitable execution resources.

Conceptually:

    Core 1 → Task A
    Core 2 → Task B
    Core 3 → Task C
    Core 4 → Task D

Parallelism can improve throughput for CPU-bound work.

But it can also increase:

- synchronization
- memory bandwidth pressure
- context switching
- coordination cost

More workers do not guarantee better performance.

---

## 27. Async Does Not Mean Faster

Asynchronous execution primarily changes waiting behavior.

For example:

    await database.query()

may improve resource utilization because the application can process other work while waiting.

But it does not make the database query itself inherently faster.

Similarly:

    async CPU-heavy calculation

does not automatically make the calculation parallel.

Always distinguish:

- latency
- throughput
- concurrency
- parallelism

---

## 28. Latency vs Throughput

### Latency

How long one operation takes.

Example:

    request = 200 ms

### Throughput

How much work the system completes per unit time.

Example:

    1,000 requests / second

Concurrency can improve throughput and sometimes latency, but excessive concurrency can worsen both through contention and queueing.

---

## 29. Queueing Effects

A simplified system:

    arrival rate λ
         |
         v
       Queue
         |
         v
    service rate μ

If arrival rate approaches or exceeds service capacity:

    λ >= μ

queue length and latency can grow rapidly.

This is why systems need:

- bounded concurrency
- backpressure
- capacity planning
- load shedding

---

## 30. Cancellation and Timeouts

Concurrent work should have bounded lifetimes.

Example:

    request
      |
      +--> database
      +--> external API
      +--> model
      |
      v
    timeout / cancellation

Without cancellation, work may continue after the user has disconnected.

That wastes:

- CPU
- memory
- database connections
- API quotas
- model tokens

Cancellation is therefore both a reliability and cost-control mechanism.

---

## 31. Structured Concurrency

Structured concurrency is a design principle where child work has a clear parent lifetime.

Conceptually:

    Parent request
       |
       +--> child task A
       +--> child task B
       +--> child task C
              |
              v
        parent completes
        only after policy-defined children complete

The goal is to avoid orphaned asynchronous work.

This principle becomes especially useful in agent runtimes and complex AI workflows.

---

## 32. Concurrency in AI Systems

An AI application may concurrently perform:

    User request
       |
       +--> retrieve documents
       +--> fetch user context
       +--> query tools
       +--> call model
       +--> stream response

But each branch has constraints.

For example:

- vector database connection limits
- model rate limits
- tool rate limits
- token budgets
- memory
- downstream latency

AI orchestration therefore needs explicit concurrency policies.

---

## 33. Production Considerations

For concurrent systems define:

- maximum concurrency
- queue capacity
- timeout
- cancellation
- retry policy
- rate limits
- resource ownership
- failure isolation
- ordering requirements
- idempotency
- observability

Do not allow concurrency to grow without bounds.

---

## 34. Trade-offs

| Approach | Benefit | Cost |
|---|---|---|
| Sequential execution | Simple ordering | Higher latency |
| Concurrent execution | Lower latency / higher utilization | More resource pressure |
| Parallel execution | CPU throughput | Coordination cost |
| Locks | Correct shared-state access | Contention/deadlocks |
| Queues | Decoupling/buffering | Eventual consistency |
| Worker pools | Bounded parallelism | Pool management |
| More workers | Potential throughput | Saturation/coordination |
| Cancellation | Resource savings | More control-flow complexity |

---

## 35. When to Use

Use concurrency when:

- operations are independent
- waiting dominates execution
- downstream systems can handle the load

Use parallelism when:

- computation is CPU-bound
- multiple execution resources are available
- coordination cost is justified

Use queues when:

- work does not need to complete within the request
- traffic is bursty
- workload isolation matters

Use locks or atomic operations when:

- shared state must remain consistent

Use bounded worker pools when:

- work volume can exceed immediate processing capacity

---

## 36. When NOT to Use

Do not:

- parallelize dependent operations
- start unbounded promises
- add locks when atomic database operations solve the problem
- create queues for trivial synchronous work
- add worker threads without CPU evidence
- assume more workers always improve throughput
- ignore downstream rate limits

---

## 37. Common Mistakes

### Mistake 1 — Async = parallel

It is not.

### Mistake 2 — Promise.all everywhere

Independent operations can still overload dependencies.

### Mistake 3 — No concurrency limit

Large batches can exhaust resources.

### Mistake 4 — Ignoring cancellation

Orphaned work wastes resources.

### Mistake 5 — Shared mutable state without synchronization

This creates race conditions.

### Mistake 6 — Locking everything

Locks can reduce throughput and create deadlocks.

### Mistake 7 — Ignoring queue growth

An unbounded queue simply moves the failure somewhere else.

---

## 38. Failure Modes

| Failure | Root cause |
|---|---|
| Race condition | Unsafe shared state |
| Deadlock | Circular resource dependency |
| Queue explosion | Producer faster than consumer |
| Database overload | Excessive concurrency |
| Event-loop blocking | CPU-heavy synchronous work |
| Orphaned task | Missing cancellation |
| Duplicate side effect | Concurrent/retried operation |
| Starvation | Poor scheduling/resource allocation |
| Thundering herd | Many tasks retry simultaneously |
| Memory exhaustion | Unbounded concurrent work |

---

## 39. Security

Concurrency can create security bugs.

Examples:

- race conditions in authorization
- double-spending
- duplicate privilege changes
- concurrent password reset use
- TOCTOU vulnerabilities
- resource-exhaustion attacks

Security-sensitive state transitions should use appropriate atomicity and authorization controls.

Never assume:

    check permission
        ↓
    later perform action

is safe if another operation can change the relevant state between those steps.

---

## 40. Performance

Measure:

- concurrency
- queue depth
- task latency
- throughput
- CPU utilization
- memory utilization
- dependency saturation
- event-loop latency
- lock contention

The goal is not maximum concurrency.

The goal is optimal useful concurrency.

---

## 41. Scalability

A system scales when additional workload can be handled without uncontrolled degradation.

A common progression is:

    Direct synchronous work
          ↓
    Async I/O
          ↓
    Bounded concurrency
          ↓
    Queue
          ↓
    Worker pool
          ↓
    Horizontal scaling

Each stage introduces more complexity.

Do not jump to the next stage without a workload reason.

---

## 42. Cost

Concurrency can increase cost through:

- more database connections
- more worker replicas
- more memory
- more API calls in flight
- more model calls
- more retries
- more infrastructure

For AI systems, uncontrolled parallel tool/model calls can rapidly consume token and provider budgets.

Concurrency limits are therefore also cost controls.

---

## 43. Debugging

When a concurrent system behaves incorrectly, reconstruct the timeline.

Example:

    t1 A reads state
    t2 B reads state
    t3 A writes
    t4 B writes

Then ask:

1. What shared state existed?
2. Which operations overlapped?
3. What ordering was assumed?
4. Which operation should have been atomic?
5. Was a lock or transaction needed?
6. Could the workflow be redesigned to avoid shared mutation?

Useful production evidence includes:

- timestamps
- request IDs
- trace IDs
- queue IDs
- worker IDs
- database transaction IDs
- concurrency metrics

---

## 44. Scenario-Based Questions

### Scenario 1 — Promise.all Incident

An endpoint calls 20 external services concurrently. Under load, the API provider starts returning rate-limit errors.

Questions:

1. Was concurrency bounded?
2. Should all 20 calls be simultaneous?
3. Which calls are critical?
4. Should some calls be sequential or queued?
5. How should rate limits influence orchestration?

### Scenario 2 — Lost Update

Two users modify the same account at the same time.

Questions:

1. What race condition exists?
2. Can the database perform an atomic update?
3. Is optimistic locking appropriate?
4. When would a transaction be needed?

### Scenario 3 — Queue Growth

A worker processes 50 jobs/sec while producers generate 100 jobs/sec.

Questions:

1. What happens to queue depth?
2. How long can the queue survive?
3. Should producers be slowed?
4. Should workers scale?
5. What happens when scaling reaches its limit?

### Scenario 4 — CPU Blocking

A Node.js API becomes unresponsive while generating large reports.

Questions:

1. Is the operation CPU-bound?
2. Is the event loop blocked?
3. Should the work move to a worker?
4. Should the request become an asynchronous job?
5. How should job progress be exposed?

### Scenario 5 — AI Agent Concurrency

An agent launches 30 tool calls simultaneously.

Questions:

1. Are all calls actually independent?
2. What are the provider limits?
3. Could the tools mutate shared state?
4. Should concurrency be bounded?
5. How are partial failures handled?
