# 00.10 — Testing & Verification Fundamentals

## 1. Why This Exists

Software is not complete when it compiles or appears to work once.

Engineering requires evidence that behavior is correct, failures are handled, changes do not unexpectedly break existing behavior, and important assumptions remain true.

Testing is one part of a broader verification discipline:

> Build confidence through executable evidence.

This chapter establishes the foundation for:

- unit testing
- integration testing
- API testing
- contract testing
- end-to-end testing
- property-based testing
- regression testing
- performance testing
- security testing
- AI evaluation
- production verification

---

## 2. Problem It Solves

Without systematic verification, systems accumulate:

- regressions
- hidden edge-case failures
- incorrect assumptions
- fragile refactors
- environment-specific bugs
- untested failure paths
- false confidence

Testing is not only about finding bugs.

It is also about making software behavior explicit.

---

## 3. Core Concept

A test establishes:

    Given
      |
      v
    When
      |
      v
    Then

Example:

    Given an expired token
    When the API receives a protected request
    Then authentication is rejected

A strong test communicates a behavior contract.

---

## 4. Verification vs Validation

### Verification

Asks:

> Did we build the system according to its intended requirements?

Examples:

- schema validation
- unit tests
- integration tests
- type checking

### Validation

Asks:

> Did we build the right thing for the actual problem?

Examples:

- user acceptance
- product experiments
- usability testing
- production metrics

Both matter.

A technically correct system can still solve the wrong problem.

---

## 5. Test Pyramid

A common model is:

    End-to-End
        /\
       /  \
    Integration
      /    \
     /      \
    Unit Tests

Unit tests are usually:

- fast
- isolated
- numerous

Integration tests verify component interactions.

End-to-end tests verify complete user workflows.

The exact ratio should follow system risk rather than a rigid formula.

---

## 6. Unit Testing

A unit test verifies a small unit of behavior.

Example:

    calculateTotal(items)

Test:

    input:
      [10, 20]

    expected:
      30

Good unit tests are generally:

- deterministic
- focused
- fast
- isolated
- readable

They should test behavior rather than implementation details.

---

## 7. Integration Testing

Integration tests verify multiple components working together.

Examples:

- service + PostgreSQL
- API + Redis
- worker + queue
- application + object storage
- model gateway + provider adapter

Integration tests catch problems that isolated unit tests cannot.

Examples:

- incorrect SQL
- schema mismatch
- serialization problems
- transaction behavior
- configuration errors

---

## 8. End-to-End Testing

E2E tests exercise a complete workflow.

Example:

    Register
      ↓
    Login
      ↓
    Create organization
      ↓
    Create project
      ↓
    Invite member
      ↓
    Verify access

E2E tests provide strong confidence but are usually:

- slower
- more expensive
- more environment-dependent
- more difficult to debug

Use them for critical user journeys rather than every internal branch.

---

## 9. Test Isolation

A test should not unexpectedly depend on another test.

Bad:

    test A creates database state
    test B assumes test A ran first

Better:

    setup
    test
    cleanup

Isolation improves:

- determinism
- parallel execution
- debugging
- repeatability

---

## 10. Determinism

A deterministic test produces the same result under the same conditions.

Sources of nondeterminism include:

- current time
- randomness
- network dependencies
- concurrency
- external services
- environment variables
- unordered iteration
- generated identifiers

Control nondeterminism with:

- fake clocks
- seeded randomness
- deterministic fixtures
- isolated dependencies
- controlled concurrency

---

## 11. Test Doubles

Common test doubles include:

### Stub

Provides predetermined responses.

### Mock

Verifies interactions or replaces behavior.

### Fake

A working simplified implementation.

### Spy

Records calls for later inspection.

Use the simplest double that provides useful isolation.

Do not mock everything.

---

## 12. Mocking vs Real Dependencies

Mocking can make tests fast and isolated.

But excessive mocking can produce:

> Tests that pass while the real system fails.

For example:

    MockedDatabase.query()

may not reveal:

- invalid SQL
- missing indexes
- schema differences
- transaction behavior

Use real dependencies at appropriate integration boundaries.

---

## 13. Fixtures

Fixtures are controlled test data.

Example:

    user:
      id: user-123
      role: admin

Good fixtures should be:

- understandable
- minimal
- reusable when appropriate
- independent

Avoid giant fixture objects containing unrelated fields.

---

## 14. Test Data Builders

Builders can create valid test data while allowing specific fields to vary.

Conceptually:

    createUser({
      role: "admin"
    })

The builder supplies sensible defaults.

This reduces repetitive setup while keeping the test focused on the behavior under examination.

---

## 15. Boundary Testing

Important tests often live at boundaries.

Examples:

- empty input
- null values
- maximum values
- malformed payloads
- unauthorized requests
- duplicate requests
- timeout
- dependency failure

Boundary testing catches assumptions that normal examples hide.

---

## 16. Equivalence Classes

Instead of testing every possible input, group inputs with similar expected behavior.

For example, age validation:

    invalid:
      < 0

    valid:
      0–120

    invalid:
      > 120

Test representative values from each class and important boundaries.

---

## 17. Edge Cases

Always consider:

- empty collection
- one element
- duplicate values
- maximum size
- minimum size
- missing fields
- invalid types
- unexpected ordering
- concurrent operations
- repeated requests

The edge cases should follow the domain rather than a generic checklist alone.

---

## 18. Property-Based Thinking

Example-based test:

    input: [1, 2, 3]
    output: 6

Property-based test:

> The sum of a collection should equal the sum after partitioning the collection into parts.

Properties test general behavior across many generated inputs.

Useful properties include:

- idempotency
- commutativity
- monotonicity
- round-trip correctness
- invariants
- serialization/deserialization consistency

---

## 19. Invariant Testing

If an algorithm has an invariant, tests should verify it where practical.

Example:

For a queue:

    size >= 0

For a balanced data structure:

    structural constraints remain valid

For financial records:

    debit and credit totals satisfy the accounting invariant

Invariants can expose failures earlier than final-output assertions.

---

## 20. Regression Testing

A regression occurs when previously correct behavior becomes incorrect.

When a production bug is found:

    reproduce bug
        ↓
    write failing test
        ↓
    fix implementation
        ↓
    verify test
        ↓
    retain regression test

This converts an incident into permanent engineering knowledge.

---

## 21. Test Naming

A useful test name describes behavior.

Weak:

    test1()

Better:

    rejects_expired_access_token()

Even better when supported by the framework:

    rejects an expired access token

A reader should understand the behavior without reading the implementation.

---

## 22. Assertions

An assertion should communicate what must be true.

Prefer:

    expect(result.status).toBe("active")

over broad assertions that provide little diagnostic value.

Good assertions make failures easy to understand.

---

## 23. Testing Error Paths

Error paths require explicit tests.

Examples:

- dependency timeout
- invalid credentials
- database constraint violation
- duplicate request
- malformed payload
- rate limit
- unavailable provider
- queue publish failure

Do not test only the happy path.

Production systems spend significant time handling failure.

---

## 24. Testing Retries

Retries are especially dangerous to test incorrectly.

Verify:

- maximum retry count
- backoff behavior
- jitter where applicable
- retryable vs non-retryable errors
- cancellation
- timeout
- idempotency
- final failure behavior

A retry test should prove that one failed dependency does not create uncontrolled repeated work.

---

## 25. Testing Idempotency

For an idempotent operation:

    request(key)
    request(key)

should not unexpectedly create two effects.

Test:

1. first request
2. repeated request
3. concurrent repeated requests where relevant
4. persistence of idempotency state
5. behavior after partial failure

This is critical for payments, jobs, webhooks, and distributed systems.

---

## 26. Testing Transactions

Database integration tests should verify:

- commit
- rollback
- constraint failures
- isolation assumptions
- concurrent updates where relevant

A unit test around a repository function cannot prove actual database transaction behavior.

Use the real database for behavior that depends on database semantics.

---

## 27. Contract Testing

Contract tests verify that two independently developed components agree on a contract.

Example:

    Producer
       |
    JSON contract
       |
    Consumer

Useful for:

- service APIs
- event schemas
- external integrations
- internal SDKs

Contract testing can detect breaking changes before deployment.

---

## 28. Schema and Migration Testing

Database changes should be tested for:

- forward migration
- rollback strategy where supported
- existing data
- constraints
- indexes
- application compatibility

A migration that works on an empty database may still fail against production data.

---

## 29. API Testing

API tests should verify:

- status codes
- authentication
- authorization
- request validation
- response schema
- error format
- pagination
- idempotency
- rate limiting where applicable

Test both valid and invalid requests.

---

## 30. Security Testing

Security tests can verify:

- authentication bypass resistance
- authorization boundaries
- tenant isolation
- input validation
- injection defenses
- sensitive-data exposure
- rate limiting
- session invalidation

Example multi-tenant invariant:

> Tenant A must never retrieve Tenant B's resources.

This should be an explicit automated test.

---

## 31. Performance Testing

Functional correctness is not sufficient.

Performance tests measure:

- latency
- throughput
- resource consumption
- concurrency behavior
- saturation point

Important measurements include:

- p50
- p95
- p99
- error rate
- CPU
- memory

Do not confuse benchmark results from a laptop with production capacity.

---

## 32. Load, Stress and Soak Testing

### Load testing

Tests expected traffic.

### Stress testing

Pushes the system beyond expected limits to discover failure behavior.

### Soak testing

Runs sustained workload for a long period.

Soak testing can reveal:

- memory leaks
- connection leaks
- queue accumulation
- gradual degradation

---

## 33. Concurrency Testing

Concurrency creates bugs that sequential tests may miss.

Test:

- simultaneous updates
- duplicate jobs
- race conditions
- locking behavior
- queue consumers
- idempotency
- transaction conflicts

Repeat concurrent tests where nondeterministic races are possible.

---

## 34. Testing Distributed Systems

Distributed tests should consider:

- network delay
- timeouts
- duplicate messages
- reordered messages
- partial failures
- unavailable dependencies
- stale data
- retries

Do not assume:

    request sent → request completed exactly once

Distributed systems require explicit failure assumptions.

---

## 35. Chaos and Fault Injection

Fault injection deliberately introduces failures.

Examples:

- database unavailable
- Redis unavailable
- network timeout
- provider returns 500
- queue delayed
- worker killed

The purpose is to verify resilience mechanisms.

Fault injection should be controlled and observable.

---

## 36. Testing AI Systems

Traditional tests remain necessary for AI applications.

Test:

- API behavior
- validation
- authorization
- persistence
- orchestration
- retries
- tool execution
- deterministic business logic

Then separately evaluate model behavior.

Do not replace ordinary software tests with LLM evaluation.

---

## 37. AI Evaluation

AI evaluation may measure:

- correctness
- relevance
- groundedness
- factuality
- safety
- tool selection
- structured-output validity
- latency
- cost

AI outputs can be nondeterministic.

Use:

- curated datasets
- deterministic assertions where possible
- statistical evaluation
- thresholds
- human review for appropriate cases

Evaluation is covered more deeply in later AI phases.

---

## 38. Test Flakiness

A flaky test passes and fails without a relevant code change.

Common causes:

- timing assumptions
- shared state
- random data
- race conditions
- external services
- order dependence

Do not simply rerun flaky tests forever.

Investigate and remove the underlying source of nondeterminism.

---

## 39. Test Coverage

Coverage measures which code or paths were exercised.

Examples:

- line coverage
- branch coverage
- function coverage
- statement coverage

High coverage does not guarantee correctness.

A test suite can execute every line while asserting almost nothing meaningful.

Use coverage as a signal, not a quality score.

---

## 40. Mutation Testing

Mutation testing changes code intentionally to see whether tests detect the change.

Example:

    if (age >= 18)

mutated to:

    if (age > 18)

If all tests still pass, the test suite may not adequately verify the boundary.

Mutation testing measures the strength of assertions rather than merely execution coverage.

---

## 41. Verification in CI

A typical pipeline:

    commit
      |
    lint
      |
    typecheck
      |
    unit tests
      |
    integration tests
      |
    build
      |
    security checks
      |
    deployment verification

Fast feedback should happen early.

Expensive tests can run later or in parallel where appropriate.

---

## 42. Production Verification

Testing does not stop at deployment.

Production verification can include:

- health checks
- smoke tests
- synthetic transactions
- canary releases
- feature flags
- metric checks
- log verification
- rollback validation

Deployment success means:

> the artifact was deployed.

It does not automatically mean:

> the system is healthy.

---

## 43. Trade-offs

| Approach | Benefit | Cost |
|---|---|---|
| Unit tests | Fast feedback | Limited integration confidence |
| Integration tests | Real interaction confidence | Slower |
| E2E tests | High workflow confidence | Expensive/flaky risk |
| Mocks | Isolation | Can diverge from reality |
| Real dependencies | Realistic behavior | More setup |
| Property tests | Broad input coverage | More complex failures |
| Mutation testing | Strong test-quality signal | Additional runtime |
| Load testing | Capacity evidence | Infrastructure effort |
| Chaos testing | Resilience evidence | Operational risk |

---

## 44. When to Use

Use unit tests for:

- pure logic
- business rules
- transformations
- algorithms

Use integration tests for:

- database behavior
- queues
- caches
- service interactions
- infrastructure semantics

Use E2E tests for:

- critical user workflows
- authentication flows
- high-value business journeys

Use property-based testing for:

- broad input spaces
- invariants
- parsers
- algorithms

Use performance testing when:

- latency matters
- throughput matters
- scale is uncertain
- a performance regression would be costly

---

## 45. When NOT to Use

Avoid:

- testing implementation details unnecessarily
- mocking every dependency
- asserting exact incidental log messages
- enormous E2E suites for trivial behavior
- chasing arbitrary coverage percentages
- ignoring flaky tests
- using production data carelessly in tests
- treating tests as a substitute for observability

---

## 46. Common Mistakes

### Mistake 1 — Happy-path-only testing

Failures are part of the contract.

### Mistake 2 — Testing implementation details

Refactoring breaks tests even though behavior remains correct.

### Mistake 3 — Excessive mocks

Tests become disconnected from reality.

### Mistake 4 — No regression test for incidents

The same bug can return.

### Mistake 5 — Coverage obsession

Execution does not equal verification.

### Mistake 6 — Ignoring concurrency

Sequential correctness does not prove concurrent correctness.

---

## 47. Failure Modes

| Failure | Cause |
|---|---|
| False confidence | Weak assertions |
| Flaky CI | Nondeterminism |
| Slow pipeline | Excessive expensive tests |
| Environment failures | Hidden dependencies |
| Regression | Missing behavioral test |
| Production mismatch | Over-mocking |
| Security regression | Missing boundary tests |
| Data corruption | Missing transaction/concurrency tests |
| AI quality regression | No evaluation dataset |

---

## 48. Security

Test suites themselves can introduce security problems.

Protect:

- credentials
- tokens
- production data
- personal information
- API keys
- generated artifacts

Security testing should also verify:

- authorization
- tenant isolation
- input handling
- secret exposure
- dependency vulnerabilities

Never commit real secrets to fixtures.

---

## 49. Performance

Testing infrastructure can affect measured performance.

Control:

- environment
- dataset size
- warm-up
- concurrency
- connection pools
- caching state
- network conditions

Record enough metadata to reproduce a benchmark.

Compare like with like.

---

## 50. Scalability

A test strategy should scale with the system.

As the system grows:

    local tests
       ↓
    CI
       ↓
    integration environment
       ↓
    staging
       ↓
    canary
       ↓
    production verification

Parallelize independent tests where possible.

Keep fast feedback paths fast.

---

## 51. Cost

Testing consumes:

- compute
- CI minutes
- databases
- cloud infrastructure
- developer time
- model/API usage

AI testing can be especially expensive if every test invokes a paid model.

Use:

- local models where appropriate
- recorded fixtures
- deterministic components
- small evaluation datasets for fast checks
- larger evaluations on controlled schedules

Cost should not eliminate verification of high-risk behavior.

---

## 52. Debugging Failed Tests

When a test fails:

1. Read the first meaningful failure.
2. Reproduce locally.
3. Determine whether the failure is deterministic.
4. Identify the smallest failing input.
5. Inspect the boundary where behavior diverged.
6. Compare expected vs actual state.
7. Determine whether code or test assumptions are wrong.
8. Fix the root cause.
9. Add or improve regression coverage if needed.

Do not blindly update the expected output just to make the test green.

## 53. Scenario-Based Questions

### Scenario 1 — Payment Bug

A payment was charged twice.

Questions:

1. What test should have existed?
2. How would you test idempotency?
3. How would you test concurrent duplicate requests?
4. What integration behavior must be verified?

### Scenario 2 — Tenant Isolation

A user from Organization A can access a resource belonging to Organization B.

Questions:

1. What boundary failed?
2. What automated test would detect this?
3. Should the test be unit, integration, or E2E?
4. How would you prevent regression?

### Scenario 3 — Flaky Queue Test

A worker test randomly fails because a job sometimes finishes before an assertion.

Questions:

1. What assumption is wrong?
2. How should synchronization be handled?
3. Should the test use sleeps?
4. How can the test become deterministic?

### Scenario 4 — AI Regression

A prompt change improves one dataset but reduces answer quality on another.

Questions:

1. What evaluation dataset is needed?
2. Which metrics should be tracked?
3. How should regression thresholds work?
4. When is human evaluation appropriate?

### Scenario 5 — Slow CI

The repository has 8,000 tests and CI takes 45 minutes.

Questions:

1. Which tests are slow?
2. Can independent tests run in parallel?
3. Are some E2E tests redundant?
4. What feedback should run on every commit?

- business rules
- edge cases
- failures

    API → PostgreSQL → Redis
