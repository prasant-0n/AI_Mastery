# 00.09 — Interfaces, Modules & Separation of Concerns

## 1. Why This Exists

Software systems become difficult to change when every component knows too much about every other component.

Interfaces, modules, and separation of concerns provide the structural discipline needed to build systems that can evolve.

The central principle is:

> A component should expose what other components need to know while hiding details they do not need to know.

This matters across:

- backend services
- frontend applications
- libraries
- databases
- distributed systems
- AI pipelines
- agent runtimes
- infrastructure
- testing

---

## 2. Problem It Solves

Poor boundaries create:

- tightly coupled code
- cascading changes
- difficult testing
- duplicated logic
- circular dependencies
- unclear ownership
- accidental side effects
- fragile deployments
- difficult debugging

Good boundaries reduce the number of assumptions that one part of the system makes about another.

---

## 3. Core Concept

A module should have:

- a clear responsibility
- an explicit interface
- controlled dependencies
- hidden implementation details
- predictable behavior

Conceptually:

    Consumer
       |
       v
    Interface
       |
       v
    Implementation
       |
       v
    External dependency

The consumer should depend on the contract rather than unnecessary implementation details.

---

## 4. Interface

An interface defines how another component interacts with a component.

An interface may specify:

- inputs
- outputs
- errors
- side effects
- timing expectations
- invariants
- compatibility rules

Example:

    PaymentGateway
      charge()
      refund()
      getStatus()

The caller should not need to know whether the implementation uses:

- Stripe
- another provider
- a database
- a mock
- a local simulator

---

## 5. Contracts

A useful interface contract answers:

### Input

What is accepted?

### Output

What is returned?

### Errors

What can fail?

### Side Effects

What changes externally?

### Invariants

What must remain true?

### Performance

What latency or throughput assumptions exist?

### Compatibility

How can the contract evolve?

A contract is stronger than a function signature alone.

---

## 6. Abstraction

Abstraction hides unnecessary implementation details.

Example:

    sendEmail(message)

may hide:

    template rendering
    provider selection
    connection management
    retries
    logging
    metrics

Abstraction is useful when it reduces cognitive load without hiding important behavior.

Bad abstraction:

> A generic framework that hides everything and makes debugging impossible.

Good abstraction:

> A stable boundary that hides implementation details while preserving important behavior.

---

## 7. Encapsulation

Encapsulation controls access to internal state and behavior.

Conceptually:

    Public API
       |
       +---- controlled access ----+
                                    |
                               Private state

Benefits:

- prevents accidental mutation
- protects invariants
- limits coupling
- centralizes validation

Encapsulation can exist through:

- language visibility mechanisms
- closures
- modules
- classes
- service boundaries
- API contracts

---

## 8. Modules

A module is a unit of organization with a defined responsibility and boundary.

Examples:

    auth/
    users/
    billing/
    notifications/

A module should expose a small public surface.

Example:

    auth/
      index.ts        ← public boundary
      service.ts
      repository.ts
      validators.ts
      internal/

Consumers should not depend directly on internal implementation files unless that dependency is intentional.

---

## 9. Cohesion

Cohesion measures how strongly the responsibilities inside a module belong together.

High cohesion:

    auth/
      authenticate()
      refreshToken()
      revokeSession()

Low cohesion:

    utils/
      authenticate()
      formatCurrency()
      sendEmail()
      calculateTax()
      resizeImage()

High cohesion usually makes code easier to understand and modify.

---

## 10. Coupling

Coupling describes how strongly components depend on one another.

High coupling:

    A → B → C → D

A change in D may require changes throughout the chain.

Lower coupling:

    A → stable contract ← B

The goal is not zero coupling.

Some coupling is necessary.

The goal is:

> intentional, controlled coupling around stable boundaries.

---

## 11. Dependency Direction

Dependency direction matters.

A useful rule is:

    Stable abstractions
          ↑
    volatile implementations

For example:

    Application
        |
        v
    Repository Interface
        |
        v
    PostgreSQL Repository

The application should not need PostgreSQL-specific details everywhere.

---

## 12. Dependency Injection

Dependency injection means supplying dependencies from outside rather than constructing them internally.

Instead of:

    class UserService {
      db = new PostgresDatabase()
    }

prefer conceptually:

    class UserService {
      constructor(db) {
        this.db = db
      }
    }

Benefits:

- testability
- replaceability
- explicit dependencies
- easier configuration

Costs:

- additional wiring
- more abstraction
- possible overengineering

---

## 13. Dependency Inversion

High-level business logic should avoid depending directly on volatile implementation details.

Example:

    OrderService
         |
         v
    PaymentGateway
         |
       /         /      Stripe    Mock

The business logic depends on the gateway contract.

---

## 14. Separation of Concerns

Different responsibilities should be separated when combining them would create unnecessary coupling.

Example backend:

    Controller
        |
        v
    Application Service
        |
        v
    Repository
        |
        v
    Database

Potential responsibilities:

### Controller

Transport concerns.

### Service

Business rules.

### Repository

Persistence concerns.

### Database

Data storage.

This does not mean every project must contain exactly these layers.

The boundary should follow actual responsibilities.

---

## 15. Transport vs Domain vs Persistence

A common architectural separation is:

    HTTP Request
         |
      Controller
         |
      DTO / Command
         |
      Domain Logic
         |
      Repository
         |
      Database

Avoid leaking transport-specific structures deep into domain logic.

For example, business logic should not need to know that an input originated from Express middleware.

---

## 16. DTOs and Domain Models

A DTO represents data crossing a boundary.

A domain model represents concepts and rules inside the application.

They may look similar but serve different purposes.

Benefits of separation:

- API changes do not automatically change domain logic
- external data can be validated
- internal invariants remain protected
- versioning becomes easier

Do not create unnecessary mappings when the boundary provides no real value.

---

## 17. Ports and Adapters

Ports and adapters separate business logic from external systems.

Conceptually:

    External World
       |   |   |
    Adapter Adapter Adapter
          |   /
          Ports
            |
        Application
            |
         Domain

Adapters may include:

- HTTP
- PostgreSQL
- Redis
- queues
- object storage
- AI providers
- email providers

This architecture can make external dependencies replaceable.

---

## 18. Hexagonal Architecture

Hexagonal architecture is another way to express ports-and-adapters thinking.

The central application exposes ports.

External technologies connect through adapters.

Important principle:

> The domain should not become structurally dependent on infrastructure details.

This is useful when business logic needs to survive technology changes.

---

## 19. Layered Architecture

A common layered structure:

    Presentation
         |
    Application
         |
      Domain
         |
    Infrastructure

Advantages:

- familiar
- clear organization
- easy onboarding

Risks:

- artificial layers
- excessive pass-through code
- business logic leaking into controllers
- domain depending on infrastructure

Layers are boundaries, not bureaucracy.

---

## 20. Module Boundaries

A good module boundary usually has:

- clear ownership
- minimal public API
- explicit dependencies
- independent tests
- predictable failure behavior

Ask:

1. What does this module own?
2. What does it expose?
3. What does it depend on?
4. What must remain private?
5. What can change without affecting consumers?

---

## 21. Public vs Internal APIs

Not every exported function should be considered public.

Define intentional public APIs.

Example:

    module/
      public.ts
      internal/
        parser.ts
        cache.ts
        helpers.ts

Consumers use:

    public.ts

rather than reaching into:

    internal/parser.ts

This reduces accidental coupling.

---

## 22. API Stability

Once a contract is consumed, changing it can create failures.

Breaking changes include:

- removing fields
- changing types
- changing semantics
- changing error behavior
- changing authentication requirements

Safer evolution may involve:

- additive changes
- versioning
- deprecation
- compatibility adapters
- migration periods

---

## 23. Semantic Compatibility

Two interfaces can have the same types but different behavior.

Example:

    getUser(id)

Version A:

    returns null if missing

Version B:

    throws an exception

The type signature may look similar, but the contract changed.

Therefore compatibility includes semantics, not just syntax.

---

## 24. Interface Granularity

An interface can be too large.

Example:

    UserSystem
      create()
      delete()
      billing()
      sendEmail()
      generateReport()
      exportData()
      ...

Large interfaces increase coupling.

Prefer focused contracts where consumers depend only on what they need.

---

## 25. Composition Over Inheritance

Composition builds behavior by combining components.

    OrderService
      |
      +-- PricingPolicy
      +-- PaymentGateway
      +-- InventoryService

Inheritance creates a stronger structural relationship.

Use inheritance when the subtype relationship and shared contract are genuinely meaningful.

Prefer composition when behavior needs to vary independently.

---

## 26. Circular Dependencies

A circular dependency looks like:

    A → B
    ↑   |
    |   ↓
    D ← C

Circular dependencies can cause:

- initialization problems
- unclear ownership
- difficult testing
- difficult refactoring

Break cycles by:

- extracting shared contracts
- changing dependency direction
- introducing an event
- moving responsibility
- combining components when they are actually one concept

---

## 27. Shared Utilities

A common failure is creating a giant utility module.

Bad:

    utils/
      everything.ts

Better:

    date/
    validation/
    crypto/
    pagination/
    identifiers/

But do not fragment every two-line helper into its own package.

The goal is meaningful boundaries.

---

## 28. Event-Based Decoupling

Some dependencies can be replaced by events.

Instead of:

    OrderService
       |
       +--> EmailService
       +--> AnalyticsService
       +--> NotificationService

use:

    OrderService
         |
         v
    OrderCreated
       / |       /  |   Email Analytics Notification

This can reduce synchronous coupling.

Trade-offs include:

- eventual consistency
- event ordering
- duplicate delivery
- observability complexity
- debugging complexity

---

## 29. AI System Boundaries

AI applications need explicit boundaries too.

Example:

    API
     |
    Orchestrator
     |
     +-- Retrieval
     +-- Model Gateway
     +-- Tool Executor
     +-- Memory
     +-- Evaluation

Do not let every module call the model directly.

A model gateway can centralize:

- provider selection
- timeouts
- retries
- token accounting
- logging
- safety controls
- routing

---

## 30. Agent Boundaries

An agent system may separate:

    Agent Runtime
        |
        +-- Planner
        +-- Context Builder
        +-- Model
        +-- Tool Registry
        +-- Tool Executor
        +-- State Store
        +-- Guardrails

This makes failures easier to localize.

For example:

> Tool execution failed

is more actionable than:

> Agent failed.

---

## 31. Testing Through Boundaries

Good boundaries enable focused tests.

Example:

    OrderService
       |
    PaymentGateway

The service can be tested with a fake gateway.

Tests can then verify:

- business rules
- failure handling
- retries
- idempotency

without requiring the real payment provider.

Avoid mocks that reproduce implementation details rather than behavior.

---

## 32. Production Considerations

Boundary design affects:

- deployment
- observability
- ownership
- security
- failure isolation
- scaling
- testing
- migration

A module boundary inside one process and a service boundary across networks have different operational costs.

Do not turn every module into a microservice.

---

## 33. Monolith vs Microservices

A modular monolith can provide strong internal boundaries without network overhead.

    Modular Monolith
    +---------------------+
    | Auth | Orders | AI  |
    |------|--------|-----|
    | clear module APIs   |
    +---------------------+

Microservices introduce:

- network calls
- independent deployment
- service discovery
- distributed tracing
- retries
- partial failure

Choose service boundaries based on actual requirements.

---

## 34. Trade-offs

| Design choice | Benefit | Cost |
|---|---|---|
| Strong interfaces | Lower coupling | More design work |
| Dependency injection | Testability | Wiring complexity |
| DTO/domain separation | Boundary stability | Mapping overhead |
| Layered architecture | Clear structure | Possible ceremony |
| Ports/adapters | Replaceability | More abstraction |
| Events | Decoupling | Eventual consistency |
| Microservices | Independent deployment | Distributed complexity |
| Composition | Flexible behavior | More objects/wiring |
| Large shared module | Simple initially | High coupling later |

---

## 35. When to Use

Use explicit interfaces when:

- multiple implementations exist
- external dependencies may change
- testing benefits from substitution
- a boundary carries important business semantics

Use modules when:

- responsibilities have clear ownership
- a subsystem has internal complexity
- multiple consumers need a stable API

Use dependency injection when:

- dependencies vary by environment
- tests need controlled substitutes
- lifecycle/configuration must be externalized

Use events when:

- consumers do not need synchronous results
- loose coupling is valuable
- eventual consistency is acceptable

---

## 36. When NOT to Use

Avoid:

- abstractions with no meaningful variation
- interfaces created only to increase line count
- excessive dependency injection
- unnecessary DTO mappings
- microservices for purely organizational reasons
- event-driven architecture where synchronous behavior is simpler
- deep inheritance hierarchies
- generic utility layers that hide ownership

The simplest boundary that protects the important invariant is often enough.

---

## 37. Common Mistakes

### Mistake 1 — Interface for everything

An interface is useful only when it communicates a meaningful contract.

### Mistake 2 — Leaky abstractions

Implementation details escape through the abstraction.

### Mistake 3 — Fat modules

One module owns unrelated responsibilities.

### Mistake 4 — Anemic boundaries

Everything is public and consumers manipulate internal state directly.

### Mistake 5 — Dependency inversion without purpose

Abstractions increase complexity without providing replaceability or testability.

### Mistake 6 — Microservice by default

A process boundary is not automatically a better architectural boundary.

---

## 38. Failure Modes

| Failure | Cause |
|---|---|
| Cascading changes | Excessive coupling |
| Circular imports | Incorrect dependency direction |
| Hard-to-test code | Hidden dependencies |
| Leaky abstraction | Contract exposes implementation |
| Breaking consumers | Unmanaged API evolution |
| Duplicate business rules | Poor ownership boundaries |
| Distributed failure | Unnecessary network boundary |
| Event inconsistency | Asynchronous semantics ignored |
| Mock-heavy tests | Poor interface design |

---

## 39. Security

Boundaries are security boundaries when they cross trust zones.

Examples:

    Browser → API
    API → database
    Service → service
    Agent → tool
    Application → model provider

At each boundary validate:

- input
- authorization
- tenant context
- authentication context
- output
- resource limits

Never assume an internal module is trustworthy merely because it is internal.

---

## 40. Performance

Every abstraction has potential runtime cost, but most ordinary module boundaries are compile-time or in-process concerns.

Network boundaries are different.

    Function call
        ↓
    Module call
        ↓
    Process call
        ↓
    Network call

Latency, serialization, failure probability, and operational overhead generally increase as the boundary becomes more distributed.

Measure before optimizing.

---

## 41. Scalability

A good module boundary can allow independent scaling later.

For example:

    API
      |
    AI Module
      |
    Queue
      |
    AI Workers

The queue creates a controlled scaling boundary.

However, a boundary that is too tightly coupled may prevent independent scaling.

Design for logical independence first; introduce infrastructure separation when justified.

---

## 42. Cost

Boundary choices affect:

- developer time
- infrastructure
- network traffic
- observability
- deployment complexity
- testing effort
- operational burden

Microservices may increase infrastructure and operational cost even when compute usage is unchanged.

AI boundaries can also reduce model cost by centralizing:

- caching
- routing
- token budgets
- provider selection
- request deduplication

---

## 43. Debugging

When a system fails across modules:

1. Identify the failing boundary.
2. Record input to the boundary.
3. Record output/error.
4. Identify the responsible component.
5. Trace dependency direction.
6. Check whether the contract was violated.
7. Determine whether the failure is local or propagated.
8. Reproduce with the smallest boundary-crossing case.

Useful observability fields:

- request ID
- correlation ID
- module/service
- operation
- dependency
- latency
- status
- error code
- tenant/context where appropriate

## 44. Scenario-Based Questions

### Scenario 1 — Giant Controller

A controller contains validation, business rules, SQL, email sending, and response formatting.

Questions:

1. What responsibilities are mixed?
2. Where would you place business logic?
3. What should the controller know?
4. How would you refactor without changing behavior?

### Scenario 2 — Payment Provider Replacement

The application directly calls a provider SDK from 30 files.

Questions:

1. What coupling exists?
2. What interface would you introduce?
3. How would you migrate safely?
4. How would tests change?

### Scenario 3 — Circular Dependency

Auth imports Users and Users imports Auth.

Questions:

1. Why is the cycle problematic?
2. Which responsibility actually owns the shared concept?
3. Could a smaller contract break the cycle?
4. Could an event be appropriate?

### Scenario 4 — AI Provider Routing

Several application modules call different LLM providers directly.

Questions:

1. What concerns are duplicated?
2. Where should routing live?
3. Where should token accounting live?
4. How would you preserve provider-specific capabilities?

### Scenario 5 — Modular Monolith

A team wants to split every module into a microservice.

Questions:

1. What operational costs are introduced?
2. Which boundaries actually require independent deployment?
3. Could a modular monolith satisfy the requirements?
4. What evidence would justify extraction?
