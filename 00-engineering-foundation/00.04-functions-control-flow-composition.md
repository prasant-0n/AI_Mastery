# 00.04 — Functions, Control Flow & Composition

## 1. Why This Exists

Functions are one of the primary units of reasoning in software.

A production system is built by composing small computations into larger behaviors:

    Input
      |
      v
    Function
      |
      v
    Result

Then:

    Function A
       |
       v
    Function B
       |
       v
    Function C

If functions have unclear responsibilities, hidden state, unpredictable side effects, or poor contracts, the entire system becomes difficult to test, debug, and evolve.

This chapter establishes the foundations for writing and composing functions before moving into larger module, backend, and distributed-system design.

---

## 2. Problem It Solves

Weak function design commonly produces:

- giant functions
- deeply nested control flow
- hidden side effects
- unclear inputs and outputs
- duplicated business rules
- difficult tests
- accidental coupling
- error-handling confusion
- difficult refactoring

The goal is to learn how to make computation understandable and composable.

A useful question is:

> What responsibility does this function own, what does it need, what does it produce, and what can it change?

---

## 3. Core Concept

A function can be modeled as:

    Inputs
       |
       v
    Transformation
       |
       v
    Output

For a pure function:

    output = f(input)

For an effectful function:

    input
      |
      v
    computation
      |
      +----> external effect
      |
      v
    output

The distinction matters because pure computation and side effects have different testing, failure, and scaling characteristics.

---

## 4. Function Responsibility

A function should have a clear reason to change.

Example:

    createOrder()

is easier to reason about when it coordinates order creation rather than also:

- formatting HTML
- sending unrelated analytics
- resizing images
- authenticating users
- generating invoices
- managing HTTP headers

A function does not have to be tiny.

The important property is **cohesive responsibility**.

---

## 5. Inputs and Outputs

A good function makes its contract visible.

Example:

    function calculateTotal(
      subtotal: number,
      taxRate: number
    ): number {
      return subtotal + subtotal * taxRate;
    }

The contract tells us:

- required inputs
- expected types
- output type
- absence of external state

This makes the function easier to test and reuse.

---

## 6. Explicit Dependencies

Compare:

    function createUser(user) {
      database.insert(user);
    }

with:

    function createUser(user, repository) {
      return repository.insert(user);
    }

The second version makes the dependency explicit.

Explicit dependencies improve:

- testing
- replacement
- reasoning
- observability
- separation of concerns

Dependency injection does not require a framework. Passing a dependency as an argument is already dependency injection.

---

## 7. Hidden Dependencies

Hidden dependencies include:

- global variables
- singleton state
- environment variables read deep inside business logic
- implicit database connections
- current time
- random number generators
- global caches

Example:

    function createToken(user) {
      return generateToken(user, globalSecret);
    }

The function signature hides an important dependency.

A more explicit design can pass the required capability or isolate configuration at the application boundary.

---

## 8. Control Flow

Control flow determines the order in which operations occur.

Common forms include:

- sequence
- condition
- iteration
- function call
- early return
- exception/error propagation
- asynchronous continuation

Basic sequence:

    A
    ↓
    B
    ↓
    C

Conditional:

    A
    |
    +---- condition true ----> B
    |
    +---- condition false ---> C

Iteration:

    input collection
         |
         v
    repeat operation
         |
         v
    result

Understanding control flow is essential for debugging.

---

## 9. Sequential Composition

Sequential composition means:

    A(); 
    B();
    C();

The output or side effects of earlier operations can affect later operations.

For example:

    validate();
    authorize();
    charge();
    persist();

The ordering is part of the correctness model.

Charging before authorization would be a different system.

Therefore:

> Control flow is not merely syntax; it expresses business semantics.

---

## 10. Conditional Logic

Conditional logic should represent meaningful decisions.

Example:

    if (!user) {
      return notFound();
    }

    if (!user.isActive) {
      return forbidden();
    }

    return continueProcessing(user);

Early returns can reduce nesting and make the main path easier to see.

But excessive early exits can also make complex state transitions harder to follow. Use a consistent style appropriate to the function.

---

## 11. Guard Clauses

A guard clause rejects invalid states early.

Example:

    function processOrder(order) {
      if (!order) {
        throw new Error("Order required");
      }

      if (order.status !== "pending") {
        throw new Error("Order is not pending");
      }

      return execute(order);
    }

Conceptually:

    Invalid state
       |
       +----> stop

    Valid state
       |
       v
    continue

Guard clauses are particularly useful at boundaries.

---

## 12. Loops and Iteration

Iteration expresses repeated work.

Examples:

- for
- for...of
- while
- array methods
- async iteration

Choose based on semantics.

For example:

    for (const user of users) {
      processUser(user);
    }

is often clearer when processing each item sequentially.

Do not automatically use map merely because it is concise.

A transformation should communicate that a new collection is being produced.

---

## 13. Map, Filter, Reduce

Functional collection operations can make transformations explicit.

### Map

Transforms every element:

    const names = users.map(user => user.name);

### Filter

Selects elements:

    const active = users.filter(user => user.active);

### Reduce

Combines elements:

    const total = prices.reduce(
      (sum, price) => sum + price,
      0
    );

These are useful when the operation naturally matches the semantic intent.

Do not use reduce for every problem merely to appear functional.

---

## 14. Composition

Composition means building larger behavior from smaller operations.

For example:

    parse
      ↓
    validate
      ↓
    normalize
      ↓
    calculate
      ↓
    persist

Each step can have a focused responsibility.

A composed system is easier to test because individual transformations can be tested independently.

---

## 15. Function Composition Example

Consider:

    const trim = (value: string) => value.trim();

    const lowercase = (value: string) => value.toLowerCase();

Then:

    const normalizeEmail = (email: string) =>
      lowercase(trim(email));

Conceptually:

    input
      |
      v
    trim
      |
      v
    lowercase
      |
      v
    output

This is simple composition.

---

## 16. Pipeline Thinking

Backend processing often naturally forms pipelines.

Example:

    Request
      ↓
    Parse
      ↓
    Validate
      ↓
    Authenticate
      ↓
    Authorize
      ↓
    Business logic
      ↓
    Persistence
      ↓
    Response

A pipeline makes responsibility and ordering visible.

It also gives you explicit failure boundaries.

---

## 17. Side Effects at the Boundary

A useful architecture is:

    Pure computation
          |
          v
    Effect boundary

Example:

    validateOrder()
          |
          v
    calculatePrice()
          |
          v
    saveOrder()
          |
          v
    publishEvent()

The first operations can often be deterministic and easy to test.

The final operations interact with external systems.

This separation makes failure analysis easier.

---

## 18. Function Contracts

A function contract should answer:

1. What inputs are accepted?
2. What outputs are produced?
3. What state can change?
4. What errors can occur?
5. What external dependencies exist?
6. What invariants must hold?

Example:

    createOrder(input)

Contract:

    Input:
      validated order data

    Output:
      created order

    Effects:
      database write
      event publication

    Errors:
      validation
      authorization
      persistence failure

A contract makes assumptions visible.

---

## 19. Preconditions, Postconditions, Invariants

### Preconditions

What must be true before execution.

Example:

    order.status === "pending"

### Postconditions

What should be true after successful execution.

Example:

    order.status === "confirmed"

### Invariants

What must remain true throughout a system or operation.

Example:

    order.total >= 0

These concepts become extremely useful in:

- database design
- financial systems
- distributed systems
- state machines
- testing

---

## 20. State Machines

Many business workflows are better represented as explicit states.

Example:

    pending
       |
       v
    paid
       |
       v
    shipped
       |
       v
    delivered

Invalid transitions should be rejected.

For example:

    delivered → pending

may be invalid depending on the domain.

Encoding state transitions explicitly prevents business logic from becoming scattered conditionals.

---

## 21. Error Control Flow

Errors are part of control flow.

Consider:

    validate()
    authorize()
    process()
    persist()

If validation fails:

    validate()
       |
       X
       |
       +----> error response

The remaining operations should not execute.

Good error handling distinguishes:

- expected business errors
- validation errors
- infrastructure failures
- programmer errors
- unexpected failures

Chapter 00.05 will go deeper into failure boundaries.

---

## 22. Exceptions vs Result Values

There are multiple ways to represent failure.

### Exceptions

    try {
      await operation();
    } catch (error) {
      handle(error);
    }

Useful when exceptional control flow is appropriate.

### Explicit result

Conceptually:

    Result<Success, Error>

Example:

    {
      ok: true,
      value: data
    }

or:

    {
      ok: false,
      error: reason
    }

Neither approach is universally correct.

Choose based on language conventions, team standards, error frequency, and architectural boundaries.

---

## 23. Async Function Composition

Asynchronous functions add another dimension to control flow.

Example:

    const user = await findUser(id);
    const order = await createOrder(user);
    await publishEvent(order);

This is sequential.

If operations are independent:

    const [users, products] = await Promise.all([
      fetchUsers(),
      fetchProducts()
    ]);

The second approach allows concurrent progress.

But concurrency must respect:

- dependency relationships
- rate limits
- resource limits
- ordering requirements
- failure semantics

Do not parallelize blindly.

---

## 24. Sequential vs Concurrent Composition

Sequential:

    A
    ↓
    B
    ↓
    C

Potentially concurrent:

    A ----+
          |
    B ----+----> C

Use concurrency when A and B are independent and the system can safely support the additional load.

The optimization is only valid if the dependency graph allows it.

---

## 25. Recursion

Recursion means a function invokes itself.

Useful for:

- tree traversal
- divide-and-conquer algorithms
- recursive data structures
- parsers

Example:

    function walk(node) {
      for (const child of node.children) {
        walk(child);
      }
    }

Risks include:

- excessive depth
- stack overflow
- difficult debugging
- repeated work

Choose iterative approaches when depth may be unbounded or very large.

---

## 26. Higher-Order Functions

A higher-order function accepts or returns another function.

Example:

    function withLogging(fn) {
      return (...args) => {
        console.log("calling");
        return fn(...args);
      };
    }

This enables:

- middleware
- decorators
- callbacks
- reusable policies
- functional composition

But excessive higher-order abstraction can make control flow difficult to trace.

---

## 27. Middleware as Function Composition

Backend middleware is a practical example of composition.

Conceptually:

    request
      ↓
    logging
      ↓
    authentication
      ↓
    authorization
      ↓
    handler
      ↓
    response

Each middleware owns one concern.

This pattern becomes central in Node.js backend engineering.

---

## 28. Closures

A closure is a function together with access to variables from its surrounding lexical scope.

Example:

    function createCounter() {
      let count = 0;

      return () => ++count;
    }

The returned function retains access to count.

Closures are useful for:

- encapsulation
- factories
- callbacks
- configuration
- private state

But they can also retain memory longer than expected.

This connects directly to Chapter 00.03.

---

## 29. Abstraction Level

A function should operate at an appropriate abstraction level.

Avoid mixing:

    SQL query construction
    HTTP response formatting
    business rules
    password hashing
    HTML generation

inside one function.

Instead:

    Controller
       ↓
    Service
       ↓
    Repository

The exact layers vary by architecture, but each function should communicate at a coherent level.

---

## 30. Production Considerations

For production functions, consider:

- input validation
- explicit dependencies
- error behavior
- timeouts
- retries
- cancellation
- idempotency
- observability
- resource limits
- concurrency
- authorization

A function that calls an external service should not assume that the service will always respond successfully.

---

## 31. Trade-offs

| Approach | Benefit | Cost |
|---|---|---|
| Small focused functions | Easier testing | More indirection |
| Large cohesive function | Fewer layers | Harder reuse/testing |
| Pure functions | Predictable | External effects must be separated |
| Mutation | Often efficient | Shared-state risk |
| Early returns | Less nesting | Can fragment complex flows |
| Abstraction | Reuse/decoupling | Indirection |
| Higher-order functions | Flexible composition | Harder tracing |
| Concurrency | Lower latency / higher throughput | Resource and failure complexity |

The goal is not maximum decomposition.

The goal is **coherent composition**.

---

## 32. When to Use

Use function decomposition when:

- a function has multiple independent responsibilities
- a portion of logic can be tested independently
- the same transformation is reused
- a business rule deserves a named concept
- error boundaries need separation

Use composition when:

- operations form a meaningful pipeline
- responsibilities are sequential
- each step has a clear contract

Use concurrency when:

- operations are independent
- latency matters
- downstream systems can handle the load

---

## 33. When NOT to Use

Do not:

- split every two lines into a function
- create abstractions without a responsibility
- use functional constructs only for shorter syntax
- parallelize dependent operations
- hide critical business logic behind generic helpers
- create deep call chains that make debugging difficult

Readable code is more important than clever code.

---

## 34. Common Mistakes

### Mistake 1 — God functions

One function handles everything.

### Mistake 2 — Hidden dependencies

Functions depend on global state without documenting it.

### Mistake 3 — Mixed abstraction levels

A function contains HTTP, business logic, SQL, and infrastructure details together.

### Mistake 4 — Accidental concurrency

Independent-looking operations actually share state or have ordering requirements.

### Mistake 5 — Unbounded recursion

Input depth can exceed the call stack.

### Mistake 6 — Generic helper explosion

Small utilities hide important business behavior.

### Mistake 7 — Catching everything

A broad catch can hide programming errors and destroy useful diagnostic information.

---

## 35. Failure Modes

| Failure | Root concept |
|---|---|
| Incorrect order of operations | Control-flow bug |
| Duplicate side effect | Retry/composition issue |
| Hidden state mutation | Poor function contract |
| Race condition | Unsafe concurrency |
| Stack overflow | Unbounded recursion |
| Memory retention | Closure/lifetime issue |
| Swallowed error | Incorrect error control flow |
| Partial operation | Missing failure boundary |
| Inconsistent state | Broken invariant |
| Difficult testing | Excessive coupling |

---

## 36. Security

Function boundaries can enforce security.

For example:

    request
      ↓
    validate
      ↓
    authenticate
      ↓
    authorize
      ↓
    business operation

Never rely on a controller or client alone if a sensitive operation can be reached through another execution path.

Authorization should be enforced at the appropriate business/security boundary.

Also treat model-generated function arguments as untrusted input.

---

## 37. Performance

Function calls themselves are usually not the first performance concern in application systems.

More important questions are:

- how much work does the function perform?
- how much data does it process?
- how many times is it called?
- does it allocate excessively?
- does it perform I/O?
- does it block?
- does it create unnecessary serialization?

Optimize based on measured bottlenecks rather than removing useful abstractions simply to reduce function count.

---

## 38. Scalability

Function composition becomes system composition.

For example:

    HTTP handler
       ↓
    Service
       ↓
    Repository
       ↓
    Database

Later:

    API
       ↓
    Queue
       ↓
    Worker
       ↓
    External service

The same principles remain:

- explicit contracts
- clear ownership
- controlled side effects
- meaningful boundaries
- observable failures

Good local function design prepares you for distributed design.

---

## 39. Cost

Poor function composition can increase cost indirectly through:

- duplicate database calls
- unnecessary API calls
- repeated serialization
- redundant model calls
- excessive retries
- unnecessary computation

In AI systems, a poorly composed pipeline may accidentally call an LLM multiple times.

Therefore composition should make expensive effects visible.

---

## 40. Debugging

When a composed operation fails:

    A → B → C → D

Do not immediately inspect everything.

Identify:

1. Which step first produced an unexpected result?
2. What input entered that step?
3. What contract did the step expect?
4. What output did it produce?
5. Did a side effect occur?
6. Did the next step receive the expected data?

This turns debugging into a boundary-by-boundary investigation.

---

## 41. Scenario-Based Questions

### Scenario 1 — Giant Controller

A controller is 500 lines and handles validation, authorization, database queries, email, and response formatting.

Questions:

1. How would you decompose it?
2. Which responsibilities belong at boundaries?
3. What should the service own?
4. What should the repository own?
5. Which parts can become pure functions?

### Scenario 2 — Incorrect Parallelization

Two database operations are moved into Promise.all and production starts showing inconsistent results.

Questions:

1. Were the operations actually independent?
2. Did they share state?
3. Was ordering required?
4. Did the database transaction semantics change?
5. How would you reproduce the issue?

### Scenario 3 — Hidden Dependency

A unit test fails only in the full application but passes in isolation.

Questions:

1. Could global state be involved?
2. Could environment configuration be hidden?
3. Could a singleton retain state?
4. How would you make the dependency explicit?

### Scenario 4 — Agent Workflow

An AI agent pipeline is:

    classify → retrieve → reason → tool → summarize

The tool is called twice unexpectedly.

Questions:

1. Which function or state transition owns tool invocation?
2. Is the pipeline deterministic?
3. Can retries duplicate the side effect?
4. Where should idempotency or deduplication exist?

### Scenario 5 — Error Handling

A service catches every error and returns HTTP 500.

Questions:

1. Which errors are expected business failures?
2. Which are infrastructure failures?
3. Which errors should be retried?
4. Which should be logged with stack traces?
5. What information should reach the client?
