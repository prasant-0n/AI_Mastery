# 00.14 — Engineering Trade-offs

## 1. Why This Exists

Software engineering rarely provides a single perfect solution.

Most meaningful decisions involve competing objectives:

- simplicity vs flexibility
- latency vs consistency
- memory vs CPU
- reliability vs cost
- speed of delivery vs maintainability
- abstraction vs complexity
- autonomy vs control
- performance vs correctness
- isolation vs operational overhead

Engineering maturity is the ability to make these trade-offs explicit and defend them with evidence.

The core principle is:

> Optimize for the system's actual constraints, not an abstract idea of perfection.

## 2. Problem It Solves

Poor engineering decisions often come from:

- choosing technology because it is popular
- optimizing without measurements
- ignoring operational cost
- solving hypothetical problems
- overengineering
- underestimating failure modes
- treating architectural preferences as universal rules

A good decision explains not only what was chosen, but also what was deliberately not chosen and why.

## 3. Core Concept

A trade-off is a decision where improving one property affects another.

Example:

    More caching
        ↓
    lower database load
        ↓
    but
        ↓
    possible stale data
    + cache complexity
    + invalidation cost

The question is not:

> Is caching good?

The question is:

> Given this workload and consistency requirement, is the benefit worth the added complexity?

## 4. Decision Framework

Use:

    Problem
      ↓
    Constraints
      ↓
    Requirements
      ↓
    Options
      ↓
    Evaluation criteria
      ↓
    Evidence
      ↓
    Trade-offs
      ↓
    Decision
      ↓
    Consequences
      ↓
    Revisit trigger

This converts opinion into engineering reasoning.

## 5. Requirements First

Separate:

### Functional requirements

What must the system do?

### Non-functional requirements

How must it behave?

Examples:

- latency
- throughput
- availability
- consistency
- security
- scalability
- cost
- maintainability

Do not choose architecture before understanding these constraints.

## 6. Hard vs Soft Constraints

### Hard constraint

Must be satisfied.

Example:

> Data must remain isolated between tenants.

### Soft constraint

Desirable but negotiable.

Example:

> API should usually respond within 200 ms.

Knowing the difference prevents optimization of secondary goals at the expense of mandatory requirements.

## 7. Constraints

Record constraints explicitly:

- team size
- engineering skill
- budget
- traffic
- data volume
- latency
- regulatory requirements
- deployment environment
- existing infrastructure
- deadline
- operational maturity

A technically elegant solution that violates constraints is not a useful solution.

## 8. Decision Criteria

Typical criteria include:

| Criterion | Question |
|---|---|
| Correctness | Does it preserve required behavior? |
| Reliability | How does it fail? |
| Performance | Does it meet latency/throughput goals? |
| Scalability | How does it behave as load grows? |
| Security | What risks does it introduce? |
| Maintainability | Can the team operate and change it? |
| Cost | What does it consume? |
| Complexity | How much new machinery is required? |
| Reversibility | Can the decision be changed later? |

Not every criterion deserves equal weight.

## 9. Reversible vs Irreversible Decisions

Some decisions are cheap to change.

Examples:

- internal helper structure
- local variable naming
- implementation details

Other decisions are expensive to reverse:

- database architecture
- public API contracts
- data model
- service boundaries
- cloud migration
- storage format

Spend more analysis effort on difficult-to-reverse decisions.

## 10. Local vs System-Level Optimization

A local improvement can hurt the whole system.

Example:

    Faster service code
        ↓
    more database requests
        ↓
    database saturation
        ↓
    worse system latency

Optimize the system objective, not an isolated component.

## 11. Correctness Before Optimization

A useful ordering is:

    correctness
        ↓
    reliability
        ↓
    measurable performance
        ↓
    cost optimization

The exact priority depends on the system.

For example, financial correctness is generally a stronger requirement than shaving a few milliseconds.

## 12. Performance vs Simplicity

Suppose two designs satisfy the requirement.

### Design A

Simple implementation with 100 ms latency.

### Design B

Complex caching and batching with 50 ms latency.

If the requirement is 200 ms, Design B may add complexity without meaningful value.

Performance improvements should have a target.

## 13. Memory vs CPU

Common trade-off:

    more memory
        ↔
    less CPU

Examples:

- memoization
- caching
- materialized results
- indexes

Ask:

- Is memory available?
- Is CPU the bottleneck?
- How long does cached data remain valid?
- What happens when memory pressure occurs?

## 14. Latency vs Throughput

A system can optimize:

### Latency

How quickly one operation completes.

### Throughput

How many operations complete over time.

Batching may improve throughput while increasing individual-request latency.

The correct choice depends on workload requirements.

## 15. Consistency vs Availability

Distributed systems may require choices around:

- immediate consistency
- eventual consistency
- availability during partition/failure

Do not treat eventual consistency as automatically better.

Ask:

- Which data requires strong consistency?
- Which data can be stale?
- What user-visible behavior results?
- How is reconciliation handled?

## 16. Synchronous vs Asynchronous

### Synchronous

    request
      ↓
    dependency
      ↓
    response

Benefits:

- simple control flow
- immediate result

Costs:

- caller waits
- dependency failure directly affects latency

### Asynchronous

    request
      ↓
    queue
      ↓
    worker

Benefits:

- decoupling
- buffering
- independent scaling

Costs:

- eventual completion
- operational complexity
- duplicate/reordered processing

## 17. Build vs Buy

A decision should consider:

- engineering effort
- vendor cost
- customization
- reliability
- security
- lock-in
- operational burden
- time to market

Build when differentiated control is valuable.

Buy or adopt when the capability is commodity and maintaining it internally provides little strategic value.

## 18. Managed vs Self-Hosted

Managed infrastructure can reduce:

- operations
- patching
- capacity management
- maintenance

Self-hosting can increase:

- control
- customization
- portability

But self-hosting transfers operational responsibility to your team.

## 19. Monolith vs Microservices

A monolith can provide:

- simple deployment
- low network overhead
- easy local development
- straightforward transactions

Microservices can provide:

- independent deployment
- independent scaling
- stronger organizational boundaries

Microservices also introduce:

- network failure
- distributed tracing
- service coordination
- deployment complexity
- operational overhead

The boundary should follow actual requirements.

## 20. SQL vs NoSQL

Consider:

- query patterns
- consistency
- relationships
- schema evolution
- transaction requirements
- scale
- operational expertise

Do not select a database solely because it is popular for a technology stack.

## 21. Cache vs Source of Truth

A cache is usually an optimization, not the authoritative source.

Conceptually:

    source of truth
          |
        cache
          |
       consumer

Ask:

- what happens on cache miss?
- what happens on stale data?
- how is invalidation handled?
- what happens when cache is unavailable?

A design that cannot survive cache failure may have accidentally made the cache part of the core dependency path.

## 22. Abstraction vs Simplicity

Abstractions can:

- reduce coupling
- improve testability
- hide implementation details

They can also:

- obscure behavior
- increase indirection
- create maintenance burden

Add an abstraction when it protects a meaningful boundary or enables a real variation.

## 23. Flexibility vs Complexity

Designing for every hypothetical future requirement creates complexity today.

A useful question:

> What evidence suggests this flexibility will be needed?

Prefer extensibility around likely change points.

Do not build an entire plugin architecture for a feature that may never exist.

## 24. Generalization vs Specialization

General systems can support more use cases.

Specialized systems can be:

- faster
- simpler
- easier to optimize

Choose based on actual workload diversity.

## 25. Reliability vs Cost

Higher reliability often requires:

- redundancy
- replication
- failover
- backups
- monitoring
- testing
- operational processes

Each adds cost.

Define the required reliability level first.

Then design toward it.

## 26. Availability vs Data Correctness

Some systems can tolerate temporary unavailability.

Others cannot tolerate incorrect state.

For example:

    recommendation feed
    vs
    financial ledger

The acceptable failure mode differs.

Do not optimize availability by allowing unacceptable corruption.

## 27. Security vs Convenience

Security controls may add friction:

- authentication
- authorization
- MFA
- encryption
- rate limits
- audit logging

The right question is not whether security is convenient.

It is:

> What threat does the control mitigate, and what user/system cost does it introduce?

## 28. Developer Velocity vs Control

Managed tooling and standardized platforms can increase velocity.

Custom infrastructure can provide more control.

Evaluate:

- frequency of changes
- team expertise
- operational risk
- lock-in
- required customization

## 29. Technical Debt

Technical debt is not simply "bad code."

It can be a deliberate trade:

    shortcut now
        ↓
    faster delivery
        ↓
    future maintenance cost

The problem occurs when debt is:

- undocumented
- unmanaged
- compounding
- blocking future work

Track important debt explicitly.

## 30. Opportunity Cost

Engineering time spent on one improvement cannot be spent elsewhere.

Example:

    optimize rare endpoint
        vs
    improve critical reliability issue

The decision should consider impact, frequency, and risk.

## 31. Reversibility

A useful decision question:

> If this decision is wrong, how expensive is it to undo?

Prefer reversible experiments for uncertain assumptions.

Examples:

- feature flags
- adapters
- canary releases
- dual writes where carefully controlled
- shadow traffic
- pilot deployments

Avoid irreversible changes without sufficient evidence.

## 32. Evidence Quality

Not all evidence is equal.

Stronger evidence may include:

- production measurements
- controlled benchmarks
- representative tests
- incident data
- user behavior
- reproducible experiments

Weaker evidence may include:

- personal preference
- anecdote
- popularity
- assumptions about future scale

Make confidence proportional to evidence quality.

## 33. Benchmarking

A benchmark should specify:

- workload
- dataset
- environment
- concurrency
- warm-up
- measurement method
- repetitions
- metrics

Compare alternatives under equivalent conditions.

Do not benchmark only the fastest successful case.

## 34. Decision Records

Record important decisions using:

    Context
    Problem
    Constraints
    Options
    Decision
    Trade-offs
    Consequences
    Revisit trigger

This prevents future engineers from rediscovering the same reasoning.

## 35. AI-Specific Trade-offs

AI systems introduce additional dimensions:

- quality vs latency
- model capability vs cost
- context size vs token cost
- retrieval depth vs noise
- autonomy vs safety
- hosted model vs local model
- deterministic workflow vs agent autonomy
- accuracy vs inference speed

Evaluate AI decisions using measurable objectives.

## 36. Model Selection

A larger model may improve quality while increasing:

- latency
- cost
- infrastructure demand

A smaller model may be sufficient for:

- classification
- extraction
- routing
- simple transformations

Choose based on task requirements and evaluation evidence.

## 37. RAG Trade-offs

More retrieved context can:

- increase recall
- increase token cost
- increase irrelevant information
- increase latency

The goal is not:

> Retrieve as much as possible.

The goal is:

> Retrieve enough useful evidence for the task.

## 38. Agent Autonomy vs Control

More autonomous agents may solve broader tasks.

But autonomy can increase:

- tool calls
- cost
- latency
- failure surface
- security risk
- unpredictability

For deterministic workflows, a constrained workflow may be preferable.

Use autonomy where it creates measurable value.

## 39. Production Decision Review

Before a significant change ask:

### Correctness

What must remain true?

### Failure

How can it fail?

### Security

What new attack surface exists?

### Performance

What workload does it handle?

### Scalability

What happens as usage grows?

### Cost

What resources increase?

### Operations

How will we monitor and recover it?

### Reversibility

How do we roll it back?

## 40. Trade-off Matrix

A simple comparison can help:

| Option | Correctness | Complexity | Performance | Cost | Reversibility |
|---|---|---|---|---|---|
| A | requirement | low | sufficient | low | high |
| B | requirement | medium | higher | medium | medium |
| C | requirement | high | highest | high | low |

Do not turn this into a fake precision exercise.

The matrix organizes reasoning; it does not replace evidence.

## 41. When to Use

Use explicit trade-off analysis when:

- architecture changes
- infrastructure selection
- database decisions
- reliability design
- performance optimization
- security controls
- AI model selection
- service extraction
- costly migrations

For trivial implementation choices, lightweight reasoning is sufficient.

## 42. When NOT to Use

Avoid:

- creating elaborate decision documents for trivial choices
- optimizing hypothetical future requirements
- comparing dozens of tools without constraints
- using arbitrary numerical scores to create false certainty
- treating benchmarks as universal truth
- delaying obvious low-risk decisions indefinitely

## 43. Common Mistakes

### Mistake 1 — One-size-fits-all rules

"Microservices are always better."

"Always use caching."

"Always use async."

Such rules ignore context.

### Mistake 2 — Ignoring operational cost

Architecture is also an operational commitment.

### Mistake 3 — Optimizing one metric

Reducing latency while increasing failure rate is not automatically an improvement.

### Mistake 4 — Premature flexibility

Supporting hypothetical requirements creates unnecessary complexity.

### Mistake 5 — No revisit trigger

Decisions should have conditions under which they are reconsidered.

## 44. Failure Modes

| Failure | Root cause |
|---|---|
| Overengineering | Hypothetical requirements |
| Underengineering | Constraints ignored |
| Cost explosion | Resource trade-offs ignored |
| Reliability failure | Operational burden underestimated |
| Performance regression | Wrong bottleneck optimized |
| Vendor lock-in | Reversibility ignored |
| Security gap | Threat model omitted |
| AI cost growth | Token/model economics ignored |

## 45. Security

Trade-off analysis must include security explicitly.

For each option ask:

- What new trust boundary exists?
- What data is exposed?
- What privileges are required?
- What happens if a dependency is compromised?
- Can abuse be rate-limited?
- Can actions be audited?

Security should not be an afterthought added after architecture is finalized.

## 46. Performance

Performance trade-offs should use:

- representative workloads
- realistic data sizes
- p95/p99 latency
- throughput
- resource utilization

Do not optimize based solely on average latency.

## 47. Scalability

Ask how the decision changes with:

    10 users
    1,000 users
    1 million users

But do not automatically design for the largest number.

Estimate realistic growth and identify the point where the architecture needs to change.

## 48. Cost

Consider total cost:

    infrastructure
    +
    operations
    +
    engineering time
    +
    vendor fees
    +
    migration cost
    +
    failure cost

AI systems additionally require:

    model inference
    +
    embeddings
    +
    retrieval
    +
    storage
    +
    observability

## 49. Debugging

When an architectural decision causes problems:

1. Identify the original constraint.
2. Identify the assumption that changed.
3. Compare expected and actual behavior.
4. Measure the affected system property.
5. Identify second-order effects.
6. Determine whether the decision or implementation is wrong.
7. Record the new evidence.
8. Update the decision if necessary.

Do not rewrite history to make an old decision look obviously wrong.

## 50. Scenario-Based Questions

### Scenario 1 — Add Redis

An API is slow because of repeated database reads.

Questions:

1. Is caching actually the right solution?
2. What is the source of truth?
3. What consistency is required?
4. What happens when Redis is unavailable?
5. How will cache invalidation work?

### Scenario 2 — Microservices

A small team wants to split a monolith into 15 services.

Questions:

1. What problem is the split solving?
2. Which boundaries have independent scaling needs?
3. What network failures are introduced?
4. What operational capabilities are required?

### Scenario 3 — AI Model Upgrade

A larger model improves evaluation quality but doubles latency and cost.

Questions:

1. Which workloads actually require the larger model?
2. Could routing use different models?
3. What quality threshold is required?
4. What measurements should drive the decision?

### Scenario 4 — Strong Consistency

A feature requires immediate consistency but the proposed architecture uses asynchronous events.

Questions:

1. Which invariant requires strong consistency?
2. Can only part of the workflow remain synchronous?
3. What user-visible behavior occurs during lag?
4. What alternative architecture satisfies the invariant?

### Scenario 5 — Build vs Buy

A team considers building an internal search platform.

Questions:

1. Is search strategically differentiated?
2. What is the engineering and operational burden?
3. What customization is actually required?
4. What vendor lock-in risks exist?

### Fundamentals

1. What is an engineering trade-off?
2. Why are there rarely perfect solutions?
3. What is opportunity cost?
4. What makes a decision reversible?
5. What is technical debt?

### Engineering

1. How do you compare architectural alternatives?
2. How do you decide between simplicity and performance?
3. How do you evaluate build vs buy?
4. How do you choose between synchronous and asynchronous processing?
5. How do you decide whether to introduce an abstraction?

### Production

1. How do you evaluate reliability vs cost?
2. How do you reason about database choice?
3. How do you evaluate service extraction?
4. How do you make architecture decisions reversible?
5. How do you use production evidence in architectural decisions?

### AI

1. How do you choose an LLM for a workload?
2. How do you balance quality, latency, and cost?
3. When should an AI workflow be deterministic rather than agentic?
4. How do you evaluate RAG retrieval depth?
5. How do you decide between hosted and local inference?

### System Design

1. Design a decision process for selecting a data store.
2. Compare a modular monolith and service-based architecture for a growing SaaS.
3. Design an AI model gateway that balances quality, latency, and cost.
4. Design a reliability strategy under a fixed infrastructure budget.

## 52. Coding / Design Exercises

### Exercise 1 — Architecture Decision Record

Write an ADR comparing two database approaches.

Include:

- requirements
- constraints
- options
- trade-offs
- decision
- consequences
- revisit trigger

### Exercise 2 — Performance Trade-off

Implement two solutions to the same problem:

- memory-efficient
- CPU-efficient

Benchmark both under realistic workloads.

### Exercise 3 — Cache Decision

Design a cache for a read-heavy endpoint and document:

- invalidation
- consistency
- failure
- TTL
- memory limits
- cost

### Exercise 4 — AI Routing

Design a model router that selects between small and large models based on:

- task complexity
- quality requirements
- latency budget
- cost budget

### Exercise 5 — Reversibility

Design a feature so that a major implementation can be replaced without changing its public API.

## 54. Mastery Test

Without referring to this chapter:

1. Take a real architecture problem and identify its hard constraints.
2. Compare at least three possible approaches.
3. Identify second-order effects for each.
4. Explain which decisions are reversible.
5. Design a cache while preserving source-of-truth correctness.
6. Compare synchronous and asynchronous alternatives.
7. Analyze a model-selection decision using quality, latency, and cost.
8. Write an ADR for a significant engineering decision.
9. Define measurable conditions that would cause the decision to be revisited.
10. Defend the decision in a mock system-design interview.

Target: **L2 explanation + L3 decision execution + L4 consequence analysis + L5 design/defense.**
